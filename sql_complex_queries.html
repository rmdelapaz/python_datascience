🧩 Lesson 5.2: Complex Queries

One table answers small questions. The interesting ones need several tables at once, and this lesson gives you the tools to combine them without losing or inventing rows.

🎯 Learning Objectives

  • Walk a hierarchy of any depth with a recursive CTE
  • Build categories and side-by-side counts with CASE, and combine results with UNION, INTERSECT and EXCEPT

🗺️ How the Tables Connect

A relational database stores each fact once. A customer's city is in customers, not repeated on every order. A product's category is in products, not on every order line. That keeps data consistent, and it means real questions ("revenue by category", "return rate by customer tier") always need more than one table. The tables are linked by keys: a column in one table that holds the identifier of a row in another.

💡 Mental Model: Two Stacks of Index Cards

Picture a stack of order cards and a stack of customer cards. A join goes through the order cards one at a time, finds the customer card with the same customer_id, and staples the two together into one wider card. Every kind of join is the same stapling. They differ only in what happens to a card that finds no partner: throw it away, or keep it with a blank where the partner would be.

Pinecrest's data has cards with no partner on purpose, because real data always does. Keep these four numbers in view. The whole lesson turns on them.

Setup: A Read-Only Connection

This lesson only reads, so open the database in read-only mode. It is a second way, besides working on a copy, to guarantee the shipped file stays as documented: the engine itself refuses any change.

import sqlite3

pd.set_option("display.width", 150)
pd.set_option("display.max_columns", 20)

def show(sql, params=()):
    """Run a query and print the result as a table."""
    print(pd.read_sql(sql, conn, params=params).to_string(index=False))

🔗 INNER JOIN: Only the Matches

A join is written in the FROM clause: name the first table, then JOIN the second ON the condition that pairs their rows. Short aliases (o for orders, c for customers) save typing, and prefixing each column with its alias says which table it comes from.

show("""
    SELECT o.order_id, o.order_date, o.order_total,
           c.first_name, c.last_name, c.city
    FROM orders AS o
    JOIN customers AS c ON c.customer_id = o.customer_id
    ORDER BY o.order_id
    LIMIT 4
""")

Output

 order_id order_date  order_total first_name last_name      city
   100001 2024-01-01        434.9     Xavier  Madrigal   Phoenix
   100002 2024-01-01        278.9       Aiko    Larkin      Bend
   100003 2024-01-01         75.9     Kareem      Pike  Missoula
   100004 2024-01-01        399.8      Emeka     Kumar Flagstaff

Each order row now carries its customer's name and city. Plain JOIN means INNER JOIN: a row appears in the result only if it found a partner. So how many rows came through?

show("""
    SELECT (SELECT COUNT(*) FROM orders) AS orders_in_table,
           COUNT(*)                      AS rows_after_inner_join
    FROM orders AS o
    JOIN customers AS c ON c.customer_id = o.customer_id
""")

Output

 orders_in_table  rows_after_inner_join
           20302                  19563

⚠️ An Inner Join Drops Rows Without Telling You

739 orders vanished: the ones whose customer account was closed. No error, no warning. If you now summed revenue you would be short by those orders. After every join, compare the row count with what you expected. It is the same habit as checking .shape after a pandas merge.

🧲 Outer Joins: Keeping the Unmatched

A LEFT JOIN keeps every row of the left table (the one named first). Where there is no partner, the right table's columns are filled with NULL.

show("""
    SELECT COUNT(*)                 AS all_rows,
           COUNT(c.customer_id)     AS with_customer,
           SUM(c.customer_id IS NULL) AS without_customer
    FROM orders AS o
    LEFT JOIN customers AS c ON c.customer_id = o.customer_id
""")

Output

 all_rows  with_customer  without_customer
    20302          19563               739

All 20,302 orders are back, and 739 of them have an empty customer side. That NULL is useful: filtering for it finds the rows with no partner. This pattern is called an anti-join, and it answers "which ones are missing?" questions.

# Customers who have never placed an order: start FROM customers, keep those with no order
show("""
    SELECT c.loyalty_tier, COUNT(*) AS never_ordered
    FROM customers AS c
    LEFT JOIN orders AS o ON o.customer_id = c.customer_id
    WHERE o.order_id IS NULL
    GROUP BY c.loyalty_tier
""")

# Products that have never sold
show("""
    SELECT p.sku, p.name, p.launch_date
    FROM products AS p
    LEFT JOIN order_items AS i ON i.sku = p.sku
    WHERE i.order_item_id IS NULL
    ORDER BY p.launch_date, p.sku
""")

RIGHT JOIN and FULL OUTER JOIN

RIGHT JOIN is the mirror image: keep everything from the table named second. FULL OUTER JOIN keeps the unmatched rows of both sides.

show("""
    SELECT COUNT(*)                   AS all_rows,
           SUM(o.order_id IS NULL)    AS customers_without_orders,
           SUM(c.customer_id IS NULL) AS orders_without_customer
    FROM customers AS c
    FULL OUTER JOIN orders AS o ON o.customer_id = c.customer_id
""")

show("""
    SELECT COUNT(*) AS rows_from_right_join
    FROM customers AS c
    RIGHT JOIN orders AS o ON o.customer_id = c.customer_id
""")

Output

 all_rows  customers_without_orders  orders_without_customer
    21360                      1058                      739
 rows_from_right_join
                20302

The arithmetic is worth doing once by hand: 19,563 matched pairs + 1,058 customers alone + 739 orders alone = 21,360. The right join keeps the matched pairs and the orders alone: 20,302, the same rows as orders LEFT JOIN customers.

On a SQLite older than 3.39, build the full outer join from parts: a left join, plus the rows only the other side has, stacked with UNION ALL (covered below). It gives the same 21,360 rows.

show("""
    SELECT COUNT(*) AS all_rows
    FROM (
        SELECT c.customer_id, o.order_id
        FROM customers AS c
        LEFT JOIN orders AS o ON o.customer_id = c.customer_id

        UNION ALL

        SELECT NULL, o.order_id
        FROM orders AS o
        LEFT JOIN customers AS c ON c.customer_id = o.customer_id
        WHERE c.customer_id IS NULL
    )
""")

Output

 all_rows
    21360

✅ In Practice You Need Two

Most working analysts write JOIN and LEFT JOIN all day and the others a few times a year. A right join can always be rewritten as a left join by swapping the table order, and most people do, because "start from the table I care about, then attach things to it" reads naturally.

⛓️ Joining Several Tables

Joins chain. Orders and products have a many-to-many relationship (an order holds many products, a product appears on many orders), and order_items is the table in the middle that makes it work. To get revenue by category you travel orders to order_items to products.

show("""
    SELECT p.category,
           COUNT(*)                                AS lines,
           ROUND(SUM(i.quantity * i.unit_price), 2) AS item_revenue
    FROM orders AS o
    JOIN order_items AS i ON i.order_id = o.order_id
    LEFT JOIN products AS p ON p.sku = i.sku
    WHERE o.status = 'completed'
    GROUP BY p.category
    ORDER BY item_revenue DESC
""")

Output

    category  lines  item_revenue
 Accessories  11080     567699.20
    Sleeping   3386     516302.45
       Tents   2110     447114.75
     Apparel   4554     435424.65
    Footwear   4142     391188.90
       Packs   3103     387082.35
Camp Kitchen   7298     367311.60
    Climbing   3157     272994.05
        Snow   2391     216940.15
         NaN    567      34228.25

Look at the last row. Because the join to products is a LEFT JOIN, the lines for discontinued SKUs stayed, with NULL for a category (pandas prints it as NaN). That is $34,228.25 of real revenue that an inner join would have silently dropped. COALESCE(p.category, 'Discontinued') would give the row a proper label; you will meet COALESCE in the NULL section.

💡 Choosing the Join Type, One Link at a Time

Ask of each link: "if a row has no partner here, do I still want it?" Every order line has an order (the README says so), so JOIN is safe for that link. Not every line has a product, and you want its revenue anyway, so that link is a LEFT JOIN.

The Fan-Out Trap

Joining a table to its "many" side repeats the "one" side. An order with three lines appears three times after joining order_items, and so does its order_total.

show("""
    SELECT (SELECT ROUND(SUM(order_total), 2) FROM orders WHERE status = 'completed') AS true_revenue,
           ROUND(SUM(o.order_total), 2)                                              AS after_join,
           COUNT(*)                                                                  AS rows_summed,
           COUNT(DISTINCT o.order_id)                                                AS orders
    FROM orders AS o
    JOIN order_items AS i ON i.order_id = o.order_id
    WHERE o.status = 'completed'
""")

Output

 true_revenue  after_join  rows_summed  orders
   3624306.27 10073626.41        41788   18762

$10.1 million instead of $3.6 million: each order's total was added once per line. The result looks plausible and is nearly three times too large. Rule: sum a column at the level where it lives. Sum order_total from orders alone, or sum quantity * unit_price from the lines, but never an order-level amount after joining to lines. When you need both levels, aggregate the lines first in a subquery or CTE, then join the one-row-per-order result.

🪞 Self Joins and Cross Joins

Self Join: A Table Joined to Itself

In employees, the manager_id column holds the employee_id of another row in the same table. To put an employee and their manager on one line, join the table to itself, using two aliases so the engine (and you) can tell the two roles apart.

show("""
    SELECT e.first_name || ' ' || e.last_name AS employee,
           e.title,
           m.first_name || ' ' || m.last_name AS manager
    FROM employees AS e
    LEFT JOIN employees AS m ON m.employee_id = e.manager_id
    ORDER BY e.employee_id
    LIMIT 7
""")

Output

     employee                   title      manager
   Clara Soto Chief Executive Officer          NaN
 Tamar Kimura            VP of Retail   Clara Soto
  Arjun Silva        VP of E-commerce   Clara Soto
Elise Delgado        VP of Operations   Clara Soto
 Elena Mistry  Regional Manager, West Tamar Kimura
 Naoko Acosta  Regional Manager, East Tamar Kimura
   Helga Shah           Store Manager Elena Mistry

|| glues text together. The join is a LEFT JOIN so that the CEO, Clara Soto, whose manager_id is NULL, is not dropped. A self join reaches exactly one level up. For the whole reporting tree you need a recursive CTE.

Cross Join: Every Combination

A CROSS JOIN has no ON: it pairs every row of one table with every row of the other. That sounds useless until you need a complete grid, for example every store in every year, so that a combination with no sales shows up as a zero instead of being absent.

show("""
    SELECT s.store, y.year
    FROM (SELECT DISTINCT store FROM orders) AS s
    CROSS JOIN (SELECT DISTINCT strftime('%Y', order_date) AS year FROM orders) AS y
    ORDER BY s.store, y.year
    LIMIT 4
""")

Output

    store year
Asheville 2024
Asheville 2025
     Bend 2024
     Bend 2025

Five stores times two years gives ten rows. The two things in parentheses are queries used as tables, which is the next topic.

🪆 Subqueries

A subquery is a SELECT in parentheses inside another query. Where you put it decides what it must return.

One Value: A Scalar Subquery

A subquery that returns one row and one column can stand anywhere a single value can. Here it supplies the average order, so you never hard-code it.

show("""
    SELECT COUNT(*)                   AS very_large_orders,
           ROUND(AVG(order_total), 2) AS their_average
    FROM orders
    WHERE order_total > 5 * (SELECT AVG(order_total) FROM orders)
""")

Output

 very_large_orders  their_average
                39        1842.99

A List: IN (subquery)

A subquery that returns one column can feed IN. Who placed the bulk orders (totals above $2,000)?

show("""
    SELECT first_name, last_name, city, state
    FROM customers
    WHERE customer_id IN (SELECT customer_id FROM orders WHERE order_total > 2000)
    ORDER BY last_name
""")

show("SELECT COUNT(DISTINCT customer_id) AS bulk_buyers FROM orders WHERE order_total > 2000")

A Table: A Subquery in FROM

A subquery in FROM acts as a temporary table. This is how you aggregate an aggregate: first count orders per customer, then summarize those counts.

show("""
    SELECT COUNT(*)              AS buyers,
           ROUND(AVG(n_orders), 2) AS avg_orders,
           MAX(n_orders)         AS most_orders
    FROM (
        SELECT customer_id, COUNT(*) AS n_orders
        FROM orders
        GROUP BY customer_id
    ) AS per_customer
""")

Output

 buyers  avg_orders  most_orders
   3942        5.15           41

Correlated Subqueries and EXISTS

A correlated subquery refers to the row of the outer query it is being evaluated for, so think of it as running once per outer row. This one finds each category's most expensive product by asking, for every product, "what is the top price in your category?"

show("""
    SELECT p.category, p.name, p.price
    FROM products AS p
    WHERE p.price = (SELECT MAX(p2.price) FROM products AS p2 WHERE p2.category = p.category)
    ORDER BY p.price DESC
    LIMIT 4
""")

Output

category                              name  price
   Tents   Quillback Cascade 4-Person Tent 616.95
Sleeping Tallgrass Lookout 0F Sleeping Bag 513.95
 Apparel Larkspur Ridge Tundra Down Jacket 375.95
   Packs  Cedar Notch Skyline 65L Backpack 335.95

EXISTS (subquery) is true if the subquery returns at least one row; what it selects is irrelevant, so people write SELECT 1. NOT EXISTS is the second way to write an anti-join, and it has an advantage over NOT IN that the NULL section will make clear.

show("""
    SELECT COUNT(*) AS never_sold
    FROM products AS p
    WHERE NOT EXISTS (SELECT 1 FROM order_items AS i WHERE i.sku = p.sku)
""")

Output

 never_sold
          8

🪜 CTEs: Naming the Steps

Subqueries nest, and nested queries must be read inside out. A common table expression (CTE) fixes that. WITH name AS (query) gives a query a name before the main query, and you then use the name like a table. Several CTEs can follow one another, each building on the ones above, so a long query reads top to bottom like a notebook: step, step, step, answer.

Does the documented loyalty rule hold (Silver at $600 or more of completed spending, Gold at $1,500 or more)? Step one computes each customer's spend; step two attaches the tier; the final query summarizes.

show("""
    WITH spend AS (
        SELECT customer_id,
               COUNT(*)         AS orders,
               SUM(order_total) AS total_spent
        FROM orders
        WHERE status = 'completed'
        GROUP BY customer_id
    ),
    with_tier AS (
        SELECT c.loyalty_tier, s.orders, s.total_spent
        FROM spend AS s
        JOIN customers AS c ON c.customer_id = s.customer_id
    )
    SELECT loyalty_tier,
           COUNT(*)                   AS customers,
           ROUND(MIN(total_spent), 2) AS lowest_spend,
           ROUND(MAX(total_spent), 2) AS highest_spend,
           ROUND(AVG(orders), 1)      AS avg_orders
    FROM with_tier
    GROUP BY loyalty_tier
    ORDER BY lowest_spend
""")

Output

loyalty_tier  customers  lowest_spend  highest_spend  avg_orders
       Basic       1710          7.50         599.91         2.1
      Silver       1294        600.43        1499.56         5.1
        Gold        734       1502.00        7945.54        10.8

The rule holds exactly: no Silver customer below $600, no Gold below $1,500, no Basic at $600 or above. Notice how the CTE also solved the fan-out problem: spend has one row per customer before it is joined to anything.

💡 CTE or Subquery?

They are interchangeable for most purposes, and the engine usually treats them the same way. Choose by readability: a short one-off value reads fine as a subquery; anything with a meaning worth naming, or used more than once, reads better as a CTE. A CTE exists only for the one statement it is part of.

🌳 Recursive CTEs: Walking a Hierarchy

The self join gave you each employee's manager: one level. "Everyone under the VP of Retail, however deep" or "how many levels are there?" cannot be answered with a fixed number of joins, because you do not know the depth in advance. A recursive CTE is a CTE that refers to itself, and it is SQL's way of looping.

It always has two parts joined by UNION ALL:

  • the anchor: an ordinary query that produces the starting rows (the CEO);
  • the recursive part: a query that joins the table to the rows found in the previous round to produce the next round (the people who report to them).
graph TD A["Anchor: rows with no manager"] --> B["Result so far"] B --> C{"Anyone report to the newest rows?"} C -->|yes| D["Add them, one level deeper"] D --> B C -->|no| E["Stop and return everything"] 
ORG_CTE = """
    WITH RECURSIVE org (employee_id, name, title, level, path) AS (
        -- anchor: the top of the tree
        SELECT employee_id,
               first_name || ' ' || last_name,
               title,
               1,
               first_name || ' ' || last_name
        FROM employees
        WHERE manager_id IS NULL

        UNION ALL

        -- recursive part: people whose manager is already in org
        SELECT e.employee_id,
               e.first_name || ' ' || e.last_name,
               e.title,
               org.level + 1,
               org.path || ' > ' || e.first_name || ' ' || e.last_name
        FROM employees AS e
        JOIN org ON e.manager_id = org.employee_id
    )
"""

show(ORG_CTE + "SELECT level, COUNT(*) AS people FROM org GROUP BY level ORDER BY level")

Output

 level  people
     1       1
     2       4
     3       7
     4      14
     5       8
     6      21

Six levels, 55 people in all. Trace the first rounds: the anchor returns Clara Soto at level 1. The recursive part finds the four people whose manager_id is Clara's id and gives them level 2. It runs again on those four and finds seven at level 3, and so on, until a round finds nobody and the loop ends. The CTE is stored in a Python string here so that the next queries can reuse it.

The path column accumulates names on the way down. Sorting by it prints the tree in reading order, and a little indentation makes it an org chart. Here is the e-commerce branch:

show(ORG_CTE + """
    SELECT level,
           substr('            ', 1, 3 * (level - 2)) || name AS employee,
           title
    FROM org
    WHERE path LIKE 'Clara Soto > Arjun Silva%'
    ORDER BY path
""")

Output

 level           employee                      title
     2        Arjun Silva           VP of E-commerce
     3          Chidi Sen                Web Manager
     4       Isaac Nakata              Web Developer
     4       Zane Pacheco              Web Developer
     3    Santiago Nakata          Marketing Manager
     4        Hugo Volkov Email Marketing Specialist

And one person's chain of command is simply their path:

show(ORG_CTE + "SELECT path FROM org WHERE name = 'Bodhi Kato'")

Clara Soto > Tamar Kimura > Elena Mistry > Helga Shah > Mabel Getty > Bodhi Kato

⚠️ A Recursive CTE Can Run Forever

If the data contains a cycle (A manages B, B manages A), the recursion never runs out of new rows. While developing, add a guard such as WHERE org.level < 20 to the recursive part, or a LIMIT on the final query. Recursive CTEs work the same way in PostgreSQL, where the keyword RECURSIVE is required; SQLite accepts the query with or without it.

🔀 CASE: If-Then Logic

CASE is SQL's if / elif / else. It checks conditions in order and returns the value of the first one that is true. It is an expression, so it can go anywhere a value can: in SELECT, GROUP BY, ORDER BY, or inside an aggregate.

show("""
    SELECT CASE
               WHEN order_total < 50  THEN '1. under $50'
               WHEN order_total < 200 THEN '2. $50 to $199'
               WHEN order_total < 500 THEN '3. $200 to $499'
               ELSE                        '4. $500 and up'
           END                        AS size_band,
           COUNT(*)                   AS orders,
           ROUND(SUM(order_total), 2) AS revenue
    FROM orders
    WHERE status = 'completed'
    GROUP BY size_band
    ORDER BY size_band
""")

Output

      size_band  orders    revenue
   1. under $50    2552   81356.13
 2. $50 to $199    9507 1104332.66
3. $200 to $499    5674 1750591.58
 4. $500 and up    1029  688025.90

Because the conditions are tested in order, the second one does not need to say "50 or more". This is the SQL counterpart of pd.cut. Orders of $500 and up are under 6% of orders and about 19% of revenue. With no ELSE, unmatched rows get NULL.

Conditional Aggregation: Counts Side by Side

Put a CASE inside SUM and you count only the rows that meet a condition. Several of these in one query turn row values into columns, a small pivot table.

show("""
    SELECT channel,
           COUNT(*)                                             AS orders,
           SUM(CASE WHEN status = 'returned'  THEN 1 ELSE 0 END) AS returned,
           SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled,
           ROUND(100.0 * SUM(CASE WHEN status = 'returned' THEN 1 ELSE 0 END) / COUNT(*), 1) AS return_pct
    FROM orders
    GROUP BY channel
""")

Output

channel  orders  returned  cancelled  return_pct
 online   12854       890        360         6.9
  store    7448       253         37         3.4

⚠️ Why 100.0 and Not 100

Dividing one integer by another gives an integer in SQLite and PostgreSQL: 890 / 12854 is 0. Multiplying by 100.0 first makes the arithmetic floating point. A percentage column that is all zeros is this bug every time.

show("SELECT 890 / 12854 AS int_division, 100 * 890 / 12854 AS still_int, 100.0 * 890 / 12854 AS correct")

Output

 int_division  still_int  correct
            0          6 6.923915

⭕ Set Operations

Joins combine tables side by side, adding columns. Set operations combine query results top to bottom, and treat them as sets of rows. The two queries must return the same number of columns, of compatible types; the column names come from the first.

OperatorReturnspandas idea
UNION ALLAll rows of both, duplicates keptpd.concat([a, b])
UNIONAll rows of both, duplicates removedconcat then drop_duplicates
INTERSECTRows that are in bothinner merge on all columns
EXCEPTRows of the first that are not in the seconda[~a["k"].isin(b["k"])]

A classic retention question: of the customers who bought in 2024, how many came back in 2025, and how many did not?

BUYERS_2024 = "SELECT customer_id FROM orders WHERE order_date < '2025-01-01'"
BUYERS_2025 = "SELECT customer_id FROM orders WHERE order_date >= '2025-01-01'"

for label, operator in [("either year", "UNION"), ("both years", "INTERSECT"),
                        ("2024 but not 2025", "EXCEPT"), ("stacked, duplicates kept", "UNION ALL")]:
    n = conn.execute(f"SELECT COUNT(*) FROM ({BUYERS_2024} {operator} {BUYERS_2025})").fetchone()[0]
    print(f"{operator:<10} {label:<26} {n:>6,}")

Output

UNION      either year                 3,942
INTERSECT  both years                  2,488
EXCEPT     2024 but not 2025             431
UNION ALL  stacked, duplicates kept   20,302

3,942 different buyers over the two years; 2,488 bought in both; 431 bought in 2024 and did not return. UNION ALL removes nothing, so it returns one row per order: 20,302. (The f-string here assembles fixed pieces of SQL written in this notebook. No outside value goes into the text, so the rule from Lesson 5.1 is intact.)

💡 Prefer UNION ALL Unless You Need Duplicates Removed

UNION has to compare every row with every other to remove duplicates, which costs time on large results. When the two halves cannot overlap, or you want to keep repeats, UNION ALL is both faster and clearer about your intent.

🕳️ The Logic of NULL

NULL means "unknown", not zero and not an empty string. Because it is unknown, any comparison with it is also unknown: is an unknown value equal to 5? Unknown. Is it different from 5? Also unknown. SQL has three truth values (true, false, unknown), and WHERE keeps a row only when the condition is true.

show("""
    SELECT NULL = NULL          AS null_equals_null,
           NULL <> 1            AS null_differs_from_1,
           1 + NULL             AS one_plus_null,
           NULL IS NULL         AS null_is_null,
           COALESCE(NULL, 'x')  AS coalesce_result
""")

Output

null_equals_null null_differs_from_1 one_plus_null  null_is_null coalesce_result
            None                None          None             1               x

The first three answers are themselves NULL (shown as None). Only IS NULL gives a straight answer. Three consequences cause most NULL bugs.

1. = NULL Never Matches; Use IS NULL

show("""
    SELECT (SELECT COUNT(*) FROM orders WHERE promo_code = NULL)  AS equals_null,
           (SELECT COUNT(*) FROM orders WHERE promo_code IS NULL) AS is_null
""")

Output

 equals_null  is_null
           0    18154

2. A Condition and Its Opposite Do Not Add Up to Everything

show("""
    SELECT COUNT(*)                        AS all_orders,
           SUM(promo_code = 'TRAIL15')     AS trail15,
           SUM(promo_code <> 'TRAIL15')    AS not_trail15,
           SUM(promo_code IS NULL)         AS no_code
    FROM orders
""")

Output

 all_orders  trail15  not_trail15  no_code
      20302      359         1789    18154

359 orders used TRAIL15. "Not TRAIL15" finds only 1,789, not the other 19,943, because for the 18,154 orders with no promo code the comparison is unknown and the row is skipped. If you mean "every order that did not use TRAIL15", say promo_code <> 'TRAIL15' OR promo_code IS NULL, or compare COALESCE(promo_code, 'none').

COALESCE(a, b, ...) returns its first argument that is not NULL. It is the SQL fillna.

3. NOT IN with a NULL in the List Returns Nothing

Which employees manage nobody? "Those whose id is not in the list of manager ids" sounds right.

show("""
    SELECT
      (SELECT COUNT(*) FROM employees
       WHERE employee_id NOT IN (SELECT manager_id FROM employees))                 AS not_in,
      (SELECT COUNT(*) FROM employees
       WHERE employee_id NOT IN (SELECT manager_id FROM employees
                                 WHERE manager_id IS NOT NULL))                    AS not_in_fixed,
      (SELECT COUNT(*) FROM employees AS e
       WHERE NOT EXISTS (SELECT 1 FROM employees AS x
                         WHERE x.manager_id = e.employee_id))                      AS not_exists
""")

Output

 not_in  not_in_fixed  not_exists
      0            32          32

The first version returns zero, which is plainly wrong. The list of manager ids contains one NULL (the CEO's). x NOT IN (1, 2, NULL) means "x differs from 1 and from 2 and from an unknown value", and that last part is never true. Either filter the NULLs out of the list, or use NOT EXISTS, which does not have the problem. Thirty-two people manage nobody.

✅ pandas Was Kinder, and Now You Know Why to Check

In pandas, df["promo_code"] != "TRAIL15" is True for missing values, so the two halves add up. SQL's stricter logic is not a flaw, but it does mean one extra question for every filter you write on a column that can be empty: "what should happen to the rows with no value?" Asking it out loud is the whole skill.

Two last facts. Aggregates skip NULL, so AVG(weight_kg) averages the 228 products that have a weight, not all 242. And when sorting, SQLite puts NULL first in ascending order while PostgreSQL puts it last; ORDER BY rating NULLS LAST makes the choice explicit on both (SQLite 3.30 or later).

⚠️ Common Mistakes

Three of the most expensive mistakes already appeared where they belong: the fan-out trap, integer division, and NOT IN with a NULL. None of them raises an error, which is why they got a demonstration each. Here are four more.

1. A Column Name That Exists in Both Tables

conn.execute("""
    SELECT order_id, city
    FROM orders AS o
    JOIN customers AS c ON c.customer_id = o.customer_id
    WHERE customer_id = 10034
""")

Error

OperationalError: ambiguous column name: customer_id

What it means: both tables have a customer_id, and the engine will not guess which you meant. Fix: prefix it: WHERE o.customer_id = 10034. Prefixing every column in a query that has a join is a habit that prevents this entirely.

2. Forgetting the ON Condition

show("""
    SELECT (SELECT COUNT(*) FROM employees)  AS employees,
           COUNT(*)                          AS rows_without_on
    FROM employees AS e
    JOIN employees AS m
""")

Output (no error, wrong result)

 employees  rows_without_on
        55             3025

What happened: SQLite accepts a JOIN with no ON and treats it as a cross join: 55 × 55 = 3,025 rows. On orders and order_items the same slip would produce over 900 million rows and a frozen notebook. PostgreSQL rejects it as a syntax error. Fix: every JOIN gets an ON; if a query is suddenly slow or its counts are huge, look for a missing or wrong join condition first.

3. Filtering the Right Table in WHERE Undoes a LEFT JOIN

Goal: every customer, with their number of orders in December 2025 (zero for most).

show("""
    WITH wrong AS (
        SELECT c.customer_id, COUNT(o.order_id) AS dec_orders
        FROM customers AS c
        LEFT JOIN orders AS o ON o.customer_id = c.customer_id
        WHERE o.order_date >= '2025-12-01'              -- filter in WHERE
        GROUP BY c.customer_id
    ),
    correct AS (
        SELECT c.customer_id, COUNT(o.order_id) AS dec_orders
        FROM customers AS c
        LEFT JOIN orders AS o ON o.customer_id = c.customer_id
                             AND o.order_date >= '2025-12-01'   -- filter in ON
        GROUP BY c.customer_id
    )
    SELECT (SELECT COUNT(*) FROM wrong)                         AS customers_wrong,
           (SELECT COUNT(*) FROM correct)                       AS customers_correct,
           (SELECT COUNT(*) FROM correct WHERE dec_orders = 0)  AS with_zero_orders
""")

Output

 customers_wrong  customers_correct  with_zero_orders
             898               4850              3952

What happened: the left join produced NULL order columns for customers with no orders, and then WHERE o.order_date >= ... threw those rows out, because a comparison with NULL is not true. Only 898 customers survived. Fix: a condition on the right table of a left join belongs in the ON clause. Conditions on the left table stay in WHERE.

4. Selecting a Column That Is Not Grouped

SQLite lets you write SELECT store, order_date, COUNT(*) FROM orders GROUP BY store and quietly returns order_date from an arbitrary row of each group. PostgreSQL refuses, with an error saying the column must appear in the GROUP BY clause or be used in an aggregate function. Fix: follow the rule from Lesson 5.1 even where SQLite does not enforce it: every selected column is either grouped or aggregated.

🛠️ Step 3: Footwear or not, online or store (10 min)

List prices rose on 2025-03-01. order_items.unit_price is what was charged at the time; products.price is today's price. show("""

    JOIN products AS p ON p.sku = i.sku
    GROUP BY period
    ORDER BY period
""")

❓ Common Questions at This Stage

Should I join in SQL or merge in pandas?

If the tables are in a database, join there: the engine can use keys and indexes, and only the result travels to your computer. Merge in pandas when the data is already in DataFrames, comes from different sources (a database table and a CSV, say), or when the tables are small and you are exploring. The row-count checks are the same either way.

What is USING (order_id) that I see in other people's queries?

A shorthand for ON a.order_id = b.order_id when the key has the same name in both tables. It works in SQLite and PostgreSQL. This lesson writes ON everywhere because it works for every join, including those where the names differ (manager_id and employee_id).

You may also see joins written with commas: FROM orders o, customers c WHERE .... Is that different?

It is the older style for an inner join, with the join condition in WHERE. It gives the same result, but it mixes join conditions with filters and makes it easy to forget one and get a cross join. Use explicit JOIN ... ON.

How do I debug a long query with several CTEs?

One step at a time, the same way you debug a notebook. Replace the final SELECT with SELECT * FROM first_cte LIMIT 10 and a COUNT(*), check it, then move to the next CTE. Most wrong answers come from one step having more or fewer rows than you assumed.

Is a correlated subquery slow?

It can be, because in principle it runs once per outer row, though engines often find a smarter plan. On 242 products you will never notice. On millions of rows, a join to a grouped CTE usually does the same job faster. Lesson 5.4 shows you how to see what the engine actually does instead of guessing.

📝 Lesson Summary

🎓 Key Takeaways

  • A join pairs rows by key; join types differ only in what happens to rows with no partner
  • JOIN keeps matches only and drops the rest silently; LEFT JOIN keeps all of the first table; LEFT JOIN ... WHERE right.key IS NULL finds what is missing
  • Check the row count after every join, and never sum a "one"-side amount after joining to its "many" side
  • Subqueries return a value, a list or a table depending on where they sit; CTEs give those steps names and a readable order
  • A recursive CTE (anchor, UNION ALL, recursive part) walks a hierarchy of any depth
  • CASE builds categories, and inside SUM or COUNT it builds side-by-side columns; multiply by 100.0 to avoid integer division
  • UNION, INTERSECT and EXCEPT combine results as sets of rows; UNION ALL keeps duplicates
  • NULL is "unknown": test it with IS NULL, replace it with COALESCE, and prefer NOT EXISTS to NOT IN
