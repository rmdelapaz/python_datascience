🔗 Lesson 2.5: Merging and Joining

Bring customers, orders, order lines and products together by their keys, and learn to notice when a merge quietly loses rows or multiplies them.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Combine two tables on a key with merge() and choose between inner, left, right and outer joins
  • Find the keys that have no match on either side with indicator=True, and decide what to do about them
  • State the relationship between two tables (one-to-one, many-to-one, many-to-many) and enforce it with validate=
  • Predict and check the row count of a merge, and avoid double counting after a one-to-many merge

🧩 Why Data Lives in Several Tables

An order in orders.csv says customer 12673 bought something. It does not say that customer's name, state or loyalty tier. Those are in customers.csv, written down once per customer instead of once per order. The products an order contained are in order_items.csv, and what category each product belongs to is in products.csv. Storing each fact in one place keeps data small and consistent. The price is that most interesting questions ("revenue by category", "average order by loyalty tier") need columns from two or three tables at once.

💡 Mental Model: The Claim Ticket

Leave skis for tuning at a Pinecrest store and you get a numbered ticket. The same number is tied to the skis. Nobody needs to write your name on the skis: the number connects the two. A key is that ticket number, a column that appears in both tables. A merge walks down one table and, for each row, finds the rows in the other table holding the same ticket. Two questions decide everything that follows: what if a ticket has no match? and what if a ticket matches more than once?

graph TD C["customers: one row per customer"] -->|"customer_id"| O["orders: one row per order"] O -->|"order_id"| I["order_items: one row per line"] P["products: one row per product"] -->|"sku"| I

Read each arrow as "one row here can match many rows there". One customer has many orders, one order has many lines, and one product appears on many lines. Keep this map in mind: it tells you what every merge in this lesson should do to the number of rows.

🔀 Four Kinds of Join

Start a notebook called lesson_2_5 and load the four core tables.

import numpy as np
import pandas as pd

pd.set_option("display.width", 150)

for name, table in [("orders", orders), ("customers", customers), ("products", products), ("items", items)]:

Before the real data, two tiny tables where you can see every row. left has keys A, B, C. right has B, C, D. So B and C match, A exists only on the left and D only on the right.

left = pd.DataFrame({"sku": ["A", "B", "C"], "qty": [2, 1, 5]})
right = pd.DataFrame({"sku": ["B", "C", "D"], "price": [10.0, 20.0, 30.0]})

print(left.merge(right, on="sku"))

Output

0   B    1   10.0
1   C    5   20.0

left.merge(right, on="sku") matched rows on sku and put the columns of both tables side by side. Only B and C appear: by default merge keeps only keys found in both tables. That default is called an inner join. The how= argument selects the other three kinds.

print(left.merge(right, on="sku", how="left"))
print(left.merge(right, on="sku", how="right"))
print(left.merge(right, on="sku", how="outer"))

Output

how=KeepsKeys in the resultUse it when
"inner"Only keys in both tablesB, CYou want only complete matches, and have counted what you drop

Where a row has no partner, the columns from the other table are filled with NaN. (That is also why qty turned into floats in the last two results: an integer column cannot hold a NaN.) "Left" and "right" simply mean the table before .merge and the table inside the parentheses.

✅ The Working Default: A Left Join

Most merges in analysis are "take my main table and attach some columns". For that job use how="left": your main table keeps every row, and missing matches show up as NaN you can see and count, instead of rows that silently vanish.

🚀 A Real Merge, and the Rows It Lost

Attach each customer's name, state and loyalty tier to their orders. Select only the columns you need from the right-hand table first, key included, so the result is not cluttered with eleven extra columns.

slim_customers = customers[["customer_id", "first_name", "last_name", "state", "loyalty_tier"]]
merged = orders.merge(slim_customers, on="customer_id")

print(merged[["order_id", "customer_id", "order_total", "first_name", "state", "loyalty_tier"]].head(3))

Output

1    100002        10034        278.9       Aiko    OR         Gold
2    100003        12448         75.9     Kareem    MT         Gold

It looks perfect. Every order now carries its customer's details. Now do the one thing you should do after every merge for the rest of your career: count the rows.

print(len(orders), "orders before")

739 orders are gone. No error, no warning. The default inner join dropped every order whose customer_id has no row in customers.csv. Any revenue total computed from merged would be short, and nothing on screen would tell you.

with_names = orders.merge(slim_customers, on="customer_id", how="left")

print(with_names["first_name"].isna().sum())

With how="left" all 20,302 orders survive, and the 739 without a customer record have NaN in the borrowed columns. The four kinds on the real tables:

for how in ["inner", "left", "right", "outer"]:
    result = orders.merge(slim_customers, on="customer_id", how=how)
    print(f"{how:<6}{len(result):>7,} rows")

Output

left   20,302 rows

The inner join is the smallest, the outer join the largest, and the differences between them are exactly the unmatched rows on each side: 20,302 − 19,563 = 739 orders without a customer, and 20,621 − 19,563 = 1,058 customers without an order.

⚠️ Count Before, Count After

Before a merge, say what the row count should be. "I am adding customer columns to orders, so I should still have 20,302 rows." After the merge, check. If the number went down, keys failed to match. If it went up, keys matched more than once. Either way you need to know why before you go on.

🔦 Finding the Unmatched Keys

indicator=True adds a column called _merge that says where each row came from: both, left_only or right_only. Combined with an outer join it is a complete audit of how two tables overlap.

audit = orders.merge(slim_customers, on="customer_id", how="outer", indicator=True)
print(audit["_merge"].value_counts())

Output

_merge
both          19563
right_only     1058
left_only       739
Name: count, dtype: int64

Now the unmatched rows are not a mystery but two tables you can inspect.

orphans = audit[audit["_merge"] == "left_only"]
print(len(orphans), "orders,", orphans["customer_id"].nunique(), "customer ids")
print(round(orphans["order_total"].sum(), 2))

never = audit[audit["_merge"] == "right_only"]
print(len(never), "customers with no orders")
print(never[["customer_id", "first_name", "state", "loyalty_tier", "order_id"]].head(3))

Output

36        10009      Idris    ID        Basic       NaN

The 739 orphan orders belong to 150 customer ids and are worth $154,274. The data README explains them: those are closed accounts whose customer records were removed, while their order history was kept. They are real sales. Dropping them, as the inner join did, would understate revenue by about 4%. On the other side, 1,058 people have an account and no order in these two years, which is a list a marketing team would pay attention to.

When you only need to know which rows have no match, isin() answers without merging at all:

no_account = orders[~orders["customer_id"].isin(customers["customer_id"])]
print(len(no_account))

Output

739

💡 Unmatched Rows Are Findings

Each group of unmatched keys has a cause: closed accounts, discontinued products, a typo in an id, a file that is out of date. Find the cause, then decide: keep the rows with a label such as "closed account", repair the key, or exclude them and say so. What you should never do is let the default decide for you.

📐 Relationships and validate=

What a merge does to the row count depends on whether the key is unique on each side.

print(customers["customer_id"].is_unique)
print(orders["customer_id"].is_unique)
print(orders["customer_id"].value_counts().head(3))

Output

True
False
customer_id
14475    41
14516    39
14680    37
Name: count, dtype: int64

Each customer_id appears once in customers and many times in orders (up to 41 times). From the orders side that is a many-to-one relationship, and it is the safe, common case: each order finds at most one customer, so the row count cannot grow.

RelationshipKey is unique inExampleRows after a left join
one-to-oneboth tablesdaily sales and weather, by date and storeSame as the left table
many-to-onethe right tableorders to customers; order lines to productsSame as the left table
one-to-manythe left tableorders to order linesMore: one per match
many-to-manyneitherorders and web sessions, by customerMany more: every pairing

You can make pandas check your belief. validate= states the relationship you expect, and the merge refuses to run if the keys say otherwise.

checked = orders.merge(slim_customers, on="customer_id", how="left", validate="many_to_one")
print(len(checked))

Output

20302

Passed: every customer_id is unique on the right. State something untrue and you get a MergeError that names the problem:

orders.merge(slim_customers, on="customer_id", how="left", validate="one_to_one")

Error

MergeError: Merge keys are not unique in left dataset; not a one-to-one merge
...

The accepted values are "one_to_one", "one_to_many", "many_to_one" and "many_to_many" (or the short forms "1:1", "1:m", "m:1", "m:m"). Writing validate= on every merge costs a few characters and turns a silent wrong answer into a loud error on the day somebody hands you a customers file with a duplicated id.

💥 When Rows Multiply

One-to-Many: Correct, and Easy to Misuse

Merge orders with their item lines. One order matches several lines, so the result has one row per line.

lines = orders[["order_id", "status", "order_total"]].merge(items, on="order_id", how="left", validate="one_to_many")
print(len(orders), "->", len(lines))
print(lines[lines["order_id"] == 100001])

Output

20302 -> 45490
   order_id     status  order_total  order_item_id       sku  quantity  unit_price
0    100001  completed        434.9              1  SLP-1021         1      371.95
1    100001  completed        434.9              2  KIT-1014         1       62.95

20,302 orders became 45,490 rows, as the map predicted. Look at order 100001: it has two lines, so its order-level values, including order_total 434.90, now appear twice. Nothing is wrong yet. It goes wrong the moment you add up an order-level column in the merged table:

print(round(orders["order_total"].sum(), 2))
print(round(lines["order_total"].sum(), 2))

Output

3950701.45
11039208.35

$11.0 million instead of $4.0 million. Every order's total was counted once per line, so orders with many lines were counted many times. This is the most expensive merge mistake in practice, because the number looks plausible and the code raises nothing.

per_order = lines.drop_duplicates("order_id")
print(round(per_order["order_total"].sum(), 2))

lines["line_total"] = lines["quantity"] * lines["unit_price"]
print(round(lines["line_total"].sum(), 2))

Output

3950701.45
3963530.35

Two honest ways out. Either bring the table back to one row per order before summing an order-level column (the first figure matches the original), or sum a line-level quantity, which is what a table of lines is for. (The line totals come to slightly more than the order totals because order totals include discounts and shipping.)

⚠️ Know What One Row Means

After every merge, finish the sentence "one row of this table is one …". If the answer is "one order line", then order-level and customer-level columns are repeated, and summing or averaging them is wrong. Aggregate each table to the level you need before merging, or only total columns that belong to the row's own level.

Many-to-Many: Usually a Mistake

The web sessions file records visits, some by signed-in customers. Suppose you try to connect orders to sessions through customer_id. First prepare the sessions that have a customer.

import json

with open("data/web_sessions.json", encoding="utf-8") as f:
    sessions = pd.json_normalize(json.load(f)["sessions"])

known = sessions[sessions["customer_id"].notna()][["session_id", "customer_id", "started_at"]].copy()
known["customer_id"] = known["customer_id"].astype("int64")
known["started_at"] = pd.to_datetime(known["started_at"])
print(len(known), known["customer_id"].nunique(), known["customer_id"].is_unique)

Output

853 780 False

853 sessions by 780 customers: the key is not unique here either. A customer can have many orders and many sessions.

pairs = orders[["order_id", "customer_id"]].merge(known, on="customer_id")
print(len(orders), "orders,", len(known), "sessions ->", len(pairs), "rows")

Output

20302 orders, 853 sessions -> 4607 rows
busiest = known["customer_id"].value_counts().index[0]
n_orders = (orders["customer_id"] == busiest).sum()
n_sessions = (known["customer_id"] == busiest).sum()
print(n_orders, "orders x", n_sessions, "sessions =", (pairs["customer_id"] == busiest).sum(), "rows")
print(pairs.loc[pairs["customer_id"] == busiest, ["order_id", "session_id"]].head(6))

Output

8 orders x 4 sessions = 32 rows
      order_id session_id
3319    115454     S00236
3320    115454     S01659
3321    115454     S02132
3322    115454     S02237
3466    116149     S00236
3467    116149     S01659

The merge paired every order of a customer with every session of that customer: 8 orders times 4 sessions makes 32 rows, none of which means anything, since a November visit has no connection to an order from the previous spring. With keys repeated on both sides, row counts multiply, and on large tables a careless many-to-many merge can produce billions of rows and exhaust your memory. validate would have stopped it:

orders[["order_id", "customer_id"]].merge(known, on="customer_id", validate="many_to_one")

Error

MergeError: Merge keys are not unique in right dataset; not a many-to-one merge
...

When you meet a many-to-many relationship, the fix is nearly always to find a better key (here, the order_id that a converted session carries) or to aggregate one side to one row per key first.

🗝️ Awkward Keys

Different Names, and More Than One Column

The daily sales and weather tables describe the same thing, a store on a day, but one calls the place store and the other city. And neither column alone identifies a row: the key is the pair (date, place).

daily = pd.read_csv("data/daily_sales.csv", parse_dates=["date"])
weather = pd.read_csv("data/store_weather.csv", parse_dates=["date"])
print(daily.columns.tolist())
print(weather.columns.tolist())
print(len(daily), len(weather))

['date', 'city', 'high_f', 'low_f', 'precip_in']

sales_weather = daily.merge(

print(len(sales_weather))

Columns with the Same Name

A converted web session carries the order_id it produced, which is a proper one-to-one key to orders. Both tables also have a customer_id column that is not part of the key.

converted = sessions.loc[sessions["converted"], ["session_id", "order_id", "customer_id", "cart.value"]].copy()
converted["order_id"] = converted["order_id"].astype("int64")

web_orders = orders.merge(converted, on="order_id")
print(len(converted), len(web_orders))
print(web_orders.columns.tolist())

Output

230 230
['order_id', 'customer_id_x', 'order_date', 'channel', 'store', 'status', 'payment_method', 'promo_code', 'discount_pct', 'shipping_cost', 'order_total', 'session_id', 'customer_id_y', 'cart.value']

pandas cannot have two columns with one name, so it renamed them customer_id_x (from the left) and customer_id_y (from the right). Those names tell a reader nothing. suffixes= lets you choose:

web_orders = orders.merge(converted, on="order_id", suffixes=("_order", "_session"), validate="one_to_one")
print([c for c in web_orders.columns if "customer" in c])
print((web_orders["customer_id_order"] == web_orders["customer_id_session"]).mean())

Output

['customer_id_order', 'customer_id_session']
1.0

And a free consistency check falls out: in all 230 matched rows, the session's customer is the order's customer.

⚠️ Missing Keys Match Each Other

The sessions were filtered to converted ones first for a reason. The other 2,170 sessions have a missing order_id, and in a pandas merge a missing key matches every other missing key (unlike SQL, where NULL matches nothing):

la = pd.DataFrame({"k": [1.0, np.nan], "left_value": ["a", "b"]})
rb = pd.DataFrame({"k": [np.nan, np.nan], "right_value": ["x", "y"]})
print(la.merge(rb, on="k"))

Output

    k left_value right_value
0 NaN          b           x
1 NaN          b           y

One left row with a missing key matched both right rows with missing keys. Remove or fill missing keys before merging on a column that has them.

📚 Stacking with concat

merge puts tables side by side, matching rows by key. pd.concat() puts tables on top of each other: same columns, more rows. It is what you use when data arrives in pieces, one file per month or per store.

y2024 = orders[orders["order_date"].dt.year == 2024]
y2025 = orders[orders["order_date"].dt.year == 2025]
print(len(y2024), len(y2025))

stacked = pd.concat([y2024, y2025], ignore_index=True)
print(stacked.shape, stacked.equals(orders))

Output

9519 10783
(20302, 11) True

Two yearly pieces stacked back into the original 20,302 rows. ignore_index=True renumbers the rows from 0. Without it each piece keeps its old labels, and you can end up with duplicate index labels. Columns are matched by name, not position, and a column that one piece lacks is filled with NaN:

a = pd.DataFrame({"store": ["Boise", "Bend"], "revenue": [100, 80]})
b = pd.DataFrame({"store": ["Flagstaff"], "revenue": [90], "visitors": [300]})
print(pd.concat([a, b], ignore_index=True))

Output

       store  revenue  visitors
0      Boise      100       NaN
1       Bend       80       NaN
2  Flagstaff       90     300.0

That is helpful when files differ slightly and a trap when a column was renamed in one of them (Revenue and revenue become two half-empty columns). After a concat, check .shape and .isna().sum(). Collect the pieces in a list and call concat once at the end: calling it inside a loop copies the growing table every time, the same cost you measured for np.append in Lesson 1.1.

⏱️ Nearest Match: merge_asof

Sometimes there is no equal key to match on. "For each website visit by a known customer, what was that customer's most recent order before the visit?" The visit's timestamp equals no order date. You want the nearest earlier one. pd.merge_asof() does exactly that: for each left row it takes the last right row whose key is less than or equal to the left key. Both tables must be sorted by that key, and by= restricts matches to the same customer.

history = orders[["customer_id", "order_date", "order_id"]].sort_values("order_date")
visits = known.sort_values("started_at")

last_order = pd.merge_asof(
    visits, history,
    left_on="started_at", right_on="order_date",
    by="customer_id",
)
last_order["days_since_order"] = (last_order["started_at"] - last_order["order_date"]).dt.days
print(last_order[["session_id", "customer_id", "started_at", "order_date", "days_since_order"]].head(4))
print(len(visits), len(last_order), last_order["order_date"].isna().sum())

Output

  session_id  customer_id          started_at order_date  days_since_order
0     S00001        12003 2025-11-01 06:31:45 2025-06-26             128.0
1     S00003        11550 2025-11-01 07:07:11 2025-11-01               0.0
2     S00012        12784 2025-11-01 08:42:25 2025-09-01              61.0
3     S00013        10940 2025-11-01 08:53:22        NaT               NaN
853 853 172

Every one of the 853 visits is kept (it behaves like a left join and never multiplies rows). The first visitor last ordered 128 days earlier, the second ordered the same day, and 172 visits were by customers with no earlier order at all, hence NaT. Typical uses are "the price in force on the order date", "the latest sensor reading before each event", or "the exchange rate at the time of each trade". A tolerance= argument limits how far back a match may reach. For now it is enough to know the tool exists. Working with dates in depth starts in Lesson 2.7.

⚠️ Common Mistakes

Four of these raise an error, which is the easy kind. Mistakes 4 and 5 run without complaint and give a wrong number, so those are the two to remember.

1. Keys of Different Types

text_ids = orders.assign(customer_id=orders["customer_id"].astype("str"))
text_ids.merge(customers, on="customer_id")

Error

ValueError: You are trying to merge on str and int64 columns for key 'customer_id'. If you wish to proceed you should use pd.concat

What it means: the id is text in one table and an integer in the other, and "12673" is not 12673. It typically happens when one file had a stray non-numeric value in the id column. Fix: convert one side so that the dtypes agree (.astype("int64"), or pd.to_numeric as in Lesson 2.3). Ignore the hint about pd.concat: it is not what you want here.

2. A Key Column the Other Table Does Not Have

daily.merge(weather, on=["date", "store"])

Error

KeyError: 'store'

What it means: on= needs the same column names in both tables, and weather calls it city. Fix: left_on= and right_on=, or rename.

3. A Relationship That Is Not What You Said

items.merge(products, on="sku", validate="one_to_many")

Error

What it means: you claimed each sku appears once in items, and it does not: the unique side is products. This is validate doing its job. 4. Averaging a Repeated Column

print(round(orders["order_total"].mean(), 2))

Output

242.67
194.6

What happened: after merging orders with their lines, "average order total" came out as $242.67 instead of $194.60, because orders with more lines are larger and were counted once per line. Fix: compute order-level statistics on the orders table, before the merge.

5. An Inner Join Used as an Accidental Filter

gold = customers[customers["loyalty_tier"] == "Gold"][["customer_id", "loyalty_tier"]]

print(len(gold_orders), round(len(gold_orders) / len(orders), 3))

Output

8491 0.418

What happened: this is fine if you meant it: merging with a table of Gold customers kept only their 8,491 orders, 42% of the total. The mistake is doing it without noticing, then reporting "total orders" from the result. Fix: how="left" when you are adding columns, and a row count after every merge.

6. merge_asof on Unsorted Data

Error

ValueError: left keys must be sorted

What it means: the nearest-match search relies on both tables being in key order. Fix: .sort_values() each table by its on column first.

❓ Common Questions at This Stage

What is the difference between merge, join and map?

merge is the general tool and the only one you need. df.join(other) is a shorthand that matches on the index of the other table and defaults to a left join. series.map(lookup), which you used in Lessons 2.3 and 2.4, fetches a single column through a lookup Series: think of it as a one-column, many-to-one left join. Use map for one borrowed column and merge for several.

Should the bigger table go on the left?

Size does not matter. Put on the left the table whose rows you are keeping: the one that defines what "one row" means in your result. In the project that was the item lines, because the question was about line revenue.

Is this the same as a SQL JOIN?

Yes, the same four kinds with the same meaning: INNER JOIN, LEFT JOIN and so on, with on= playing the part of ON. Two differences are worth knowing: pandas matches missing keys to each other and SQL does not, and SQL has nothing like validate. You will write these joins in SQL in Lesson 5.2, and it will feel familiar.

My merge is slow or runs out of memory. What should I check?

First the relationship: an unintended many-to-many merge is the usual cause, and validate will tell you. Then trim before merging: select only the columns you need from each side, filter rows first, and aggregate to one row per key where you can. Category or integer keys merge faster than long text keys.

📝 Lesson Summary

🎓 Key Takeaways

  • merge matches rows of two tables on a key; how= decides what happens to keys without a match: inner (default), left, right, outer
  • The default inner join drops unmatched rows silently; use how="left" when adding columns to a main table
  • Count rows before and after every merge. Fewer means unmatched keys; more means repeated keys
  • indicator=True shows which rows matched; unmatched keys are findings with causes
  • Know the relationship and state it with validate=; many-to-many multiplies rows and is usually a mistake
  • After a one-to-many merge, columns from the "one" side are repeated: never sum or average them there
  • left_on/right_on for different key names, lists for multi-column keys, suffixes= for clashing names; missing keys match each other
  • concat stacks tables; merge_asof matches the nearest earlier key
