🗂️ Split, Apply, Combine

A table of 20,302 orders is too much to look at. What a manager wants is five lines: one per store. What marketing wants is one line per customer. What finance wants is one line per month. Nearly every business question takes many rows and reduces them to one row per something.

💡 Mental Model: Sorting the Mail

Imagine the day's receipts from all of Pinecrest dumped on one table. To get revenue by store you would do three things without thinking about it. Split: deal the receipts into piles, one pile per store. Apply: add up each pile. Combine: write the totals on one sheet, one line per pile. That is all groupby is, and it has a name: split-apply-combine.

🤔 Why This Matters

Once you see the pattern you find it everywhere: a pivot table in a spreadsheet, GROUP BY in SQL (Module 5), the bars in most bar charts (Module 3), and the group comparisons behind most statistical tests (Module 4). The one-line version you used in Lessons 0.1 and 2.3 was this pattern. Today you take it apart and learn to control every piece.

🚀 Your First GroupBy

Start a notebook called lesson_2_4 and load the clean orders table.

import numpy as np
import pandas as pd

pd.set_option("display.width", 150)
pd.set_option("display.max_columns", 20)

orders = pd.read_csv("data/orders.csv", parse_dates=["order_date"])
print(orders.shape)

Output

(20302, 11)

You already have the tools to compute one store's revenue: filter, then sum. Doing it for every store means a loop.

for store in ["Bend", "Boise"]:
    one_store = orders[orders["store"] == store]
    print(store, round(one_store["order_total"].sum(), 2))

Output

Bend 298263.94
Boise 459714.9

It works, and it is exactly split (the filter) and apply (the sum), done by hand, with the combining left to you. groupby does all three:

revenue = orders.groupby("store")["order_total"].sum()
print(revenue)

📊 Several Summaries at Once

One number per group is rarely enough. .agg() (short for "aggregate") takes a list of function names and returns one column for each.

print(orders.groupby("store")["order_total"].agg(["count", "sum", "mean", "median"]).round(2))

Output

Named Aggregation

Real summaries draw on different columns and deserve clear column names. Named aggregation does both. Each argument reads new_column=("source_column", "function").

summary = orders.groupby("store").agg(
    orders=("order_id", "count"),
    revenue=("order_total", "sum"),
    avg_order=("order_total", "mean"),
    biggest=("order_total", "max"),
    customers=("customer_id", "nunique"),
)
print(summary.round(2))

Output

           orders     revenue  avg_order  biggest  customers

Bend         1725   298263.94     172.91  1004.60        677

Flagstaff    1716   315077.90     183.61  1126.75        601
Online      12854  2630511.36     204.65  4893.00       3456

This is the form to learn by heart. The output has exactly the columns you named, in the order you wrote them, and anyone reading the code can see where each number comes from. It works with dates too:

Rates: The Mean of True and False

"What fraction of each group's orders were returned?" has a neat answer. Make a boolean column. Since True counts as 1 and False as 0, its mean within each group is the rate.

orders["returned"] = orders["status"] == "returned"
orders["used_promo"] = orders["promo_code"].notna()

rates = orders.groupby("channel").agg(
    orders=("order_id", "count"),
    return_rate=("returned", "mean"),
    promo_rate=("used_promo", "mean"),
)
print(rates.round(3))

Output

         orders  return_rate  promo_rate
channel
online    12854        0.069       0.104
store      7448        0.034       0.109

That is a real finding: online orders are returned twice as often as in-store ones (6.9% against 3.4%), while promo codes are used at about the same rate in both channels. Creating a helper column first and then aggregating it is almost always clearer, and faster, than trying to do the logic inside the aggregation.

Your Own Function

When no built-in fits, pass a function that takes a Series (one group's values) and returns a single number.

def spread(s):
    """Difference between the 90th and 10th percentile."""
    return s.quantile(0.9) - s.quantile(0.1)

print(orders.groupby("channel")["order_total"].agg(["median", spread]).round(2))

Output

         median  spread
channel
online    156.4  372.39
store     133.9  342.36

Custom functions are called once per group in ordinary Python, so they are much slower than the built-in names. With 5 groups nobody notices. With 500,000 groups you would. Use the built-in name as a string whenever one exists.

Getting the Key Back as a Column

The group key lands in the index. That is convenient for lookups and awkward when you want an ordinary table to save or to combine with another. Either ask for it up front with as_index=False, or call .reset_index() afterward.

flat = orders.groupby("store", as_index=False)["order_total"].sum()
print(flat)
print(summary.reset_index().columns.tolist())

🔑 More Than One Key

Pass a list of columns and you get one group for every combination that occurs.

counts = orders.groupby(["channel", "status"]).size()

Two channels times three statuses gives six groups. The index now has two levels, channel and status: a MultiIndex. pandas prints the outer label once per block to make it readable. A tuple selects one combination, and an outer label alone selects its whole block.

print(counts.index[:3])
print(counts.loc[("online", "returned")])

If the two-level index feels awkward, flatten it. reset_index() turns every level into an ordinary column, and name= labels the counts.

print(counts.reset_index(name="orders"))

Keys You Compute on the Spot

A key does not have to be a column of the table. Any Series with one value per row will do, for example the year taken from the order date.

by_year = orders.groupby(orders["order_date"].dt.year)["order_total"].sum()
print(by_year.round(2))

Output

order_date

Mix computed keys and column names freely. Here is completed revenue by year and channel, unstacked so that the two years sit side by side and growth is one line of arithmetic. (.rename("year") gives the computed key a clear name.)

completed = orders[orders["status"] == "completed"]
yearly = completed.groupby([completed["order_date"].dt.year.rename("year"), "channel"])["order_total"].sum()
print(yearly.round(2))

table = yearly.unstack("year")
table["growth_pct"] = ((table[2025] / table[2024] - 1) * 100).round(1)

Completed online revenue grew 18.8% from 2024 to 2025, against 9.1% for account-holder orders in the stores. Grouping by month, week or quarter works the same way, and dates have a dedicated tool for it, resample, that Lesson 2.7 covers.

🔀 agg, transform or filter?

Everything so far has been aggregation: many rows in, one row per group out. There are two other things you can do with groups, and the difference between the three is simply the shape of what comes back.

OperationReturnsUse it toExample question
aggOne row per groupSummarizeWhat is each store's average order?
transformOne value per original rowAttach a group statistic to every rowHow does each order compare with its store's average?
filterThe original rows of some groupsKeep or drop whole groupsWhich orders belong to customers with 25 or more orders?

transform: A Group Statistic on Every Row

store_avg = orders.groupby("store")["order_total"].transform("mean")
print(store_avg.shape, orders.shape)
print(store_avg.head(4).round(2))

Output

(20302,) (20302, 13)
0    183.61
1    174.90
2    204.65
3    204.65
Name: order_total, dtype: float64

.transform("mean") computed the same five store averages as before, but instead of returning five rows it broadcast each average back to every row of its group. The result has 20,302 values, in the original row order, with the original index. That means it can go straight into a new column.

orders["store_avg"] = store_avg
orders["vs_store_avg"] = orders["order_total"] / orders["store_avg"]
print(orders[["order_id", "store", "order_total", "store_avg", "vs_store_avg"]].head(4).round(2))

Output

   order_id      store  order_total  store_avg  vs_store_avg
0    100001  Flagstaff        434.9     183.61          2.37
1    100002  Asheville        278.9     174.90          1.59
2    100003     Online         75.9     204.65          0.37
3    100004     Online        399.8     204.65          1.95

Order 100001 was 2.37 times the average Flagstaff order. Order 100003 was about a third of the average online order. Comparing each row with its own group is one of the most common needs in analysis, and transform is the tool. Two more examples, per customer:

orders["customer_orders"] = orders.groupby("customer_id")["order_id"].transform("count")
orders["share_of_customer"] = orders["order_total"] / orders.groupby("customer_id")["order_total"].transform("sum")
print(orders.loc[orders["customer_id"] == 12673, ["order_id", "order_total", "customer_orders", "share_of_customer"]].round(3))

Output

      order_id  order_total  customer_orders  share_of_customer
0       100001       434.90                4              0.408
873     100874       180.90                4              0.170
1145    101146       139.40                4              0.131
6279    106280       310.46                4              0.291

Customer 12673 placed four orders, and now every one of those rows knows it, along with the share of that customer's spending it represents (the four shares add up to 1). Running totals, ranks and moving averages within groups are close cousins of transform. They are called window functions, and Lesson 2.8 is about them.

filter: Keep or Drop Whole Groups

.filter() takes a function that receives one group (as a DataFrame) and returns True to keep all of its rows or False to drop them all.

loyal = orders.groupby("customer_id").filter(lambda g: len(g) >= 25)
print(loyal.shape)
print(loyal["customer_id"].nunique())

Output

(496, 17)
16

The result is not a summary: it is 496 of the original order rows, belonging to the 16 customers who each placed 25 or more orders. Notice that a transform followed by an ordinary boolean filter gives the identical answer:

loyal2 = orders[orders["customer_orders"] >= 25]
print(loyal2.shape, loyal2.equals(loyal))

Output

(496, 17) True

You already built customer_orders, so this version is free, and on large tables it is far faster because no Python function runs per group. Many analysts use the transform-then-mask pattern nearly all the time. .filter() earns its place when the condition is easier to write as a function of the whole group:

big_spend_stores = orders.groupby("store").filter(lambda g: g["order_total"].mean() > 200)
print(big_spend_stores["store"].unique())

Output

<ArrowStringArray>
['Online']
Length: 1, dtype: str

✅ Ask "What Shape Do I Want Back?"

One row per group: agg. The same rows I started with, plus a group number on each: transform. Fewer of the same rows: filter (or a transform and a mask). When you are unsure which you need, say the shape of the answer out loud first.

🕳️ Missing Keys and Categories

Two settings decide which groups appear in the result. Both have sensible defaults, and both will surprise you once.

dropna=: Rows with a Missing Key Vanish

print(orders.groupby("promo_code")["order_total"].agg(["count", "mean"]).round(2))
print(orders.groupby("promo_code").size().sum(), len(orders))

Output

            count    mean
promo_code
GEARUP5       396  180.80
SUMMIT20      254  148.53
TRAIL15       359  167.28
WELCOME10    1139  177.78
2148 20302

Four groups, 2,148 orders. But the table has 20,302. By default, groupby silently drops every row whose key is missing, and 18,154 orders have no promo code. If you were asked "how do orders with a promo code compare with the rest?", the rest is not in this result at all. dropna=False keeps the missing key as its own group.

print(orders.groupby("promo_code", dropna=False)["order_total"].agg(["count", "mean"]).round(2))

Output

            count    mean
promo_code
GEARUP5       396  180.80
SUMMIT20      254  148.53
TRAIL15       359  167.28
WELCOME10    1139  177.78
NaN         18154  197.14

Now the comparison is possible: orders with no code average $197.14, and every promo group averages less. (Tempting conclusion: promo codes shrink orders. Careful: the total is recorded after the discount, and WELCOME10 goes only to first-time buyers. A difference between groups is where an investigation starts, not where it ends.)

⚠️ Check That the Groups Add Up

After a groupby, compare result.sum() of the sizes with len(df). If the groups do not account for every row, some keys were missing. It takes five seconds and catches the most silent error in this lesson.

observed=: Categories That Do Not Occur

In Lesson 2.2 you learned that a category column stores the list of possible values separately from the data. So a category can exist with no rows that use it, and groupby has to decide whether to show it. Take the online orders only and group by a categorical store column:

orders["store_cat"] = orders["store"].astype("category")
online = orders[orders["channel"] == "online"]
print(online.groupby("store_cat").size())

Output

store_cat
Online    12854
dtype: int64

By default (observed=True) you get only the categories that actually occur: one group. Ask for observed=False and every category gets a row, with the empty ones counted as 0:

print(online.groupby("store_cat", observed=False).size())

Output

store_cat
Asheville        0
Bend             0
Boise            0
Flagstaff        0
Online       12854
dtype: int64

Neither is wrong. For a report where "Boise: 0" is information, you want observed=False. For most analysis the default is what you expect. The reason to know about it: with two or three categorical keys, observed=False produces a row for every possible combination, and that can be an enormous table of zeros. Older tutorials set observed=True explicitly because the default used to be the other way around. Writing it out does no harm.

You meet categorical keys most often through pd.cut(), which sorts numbers into labeled bins and returns a categorical Series:

tiers = pd.cut(orders["order_total"], bins=[0, 50, 150, 500, 5000], labels=["under 50", "50 to 150", "150 to 500", "over 500"])
print(tiers.dtype)
print(orders.groupby(tiers).agg(orders=("order_id", "count"), return_rate=("returned", "mean")).round(3))

Output

category
             orders  return_rate
order_total
under 50       2722        0.045
50 to 150      7633        0.046
150 to 500     8816        0.066
over 500       1131        0.073

Bigger orders are returned more often: 4.7% of orders under $50 against 7.6% of orders over $500. pd.cut returns in Lesson 2.9.

One More Default: Groups Are Sorted

print(orders.groupby("store", sort=False)["order_total"].sum().round(2).head(3))

Output

store
Flagstaff     315077.90
Asheville     247133.35
Online       2630511.36
Name: order_total, dtype: float64

Group keys come back sorted. sort=False keeps them in order of first appearance instead, which is slightly faster and occasionally what you want. The order of rows within each group is never changed.

⚠️ Common Mistakes

GroupBy mistakes come in two kinds: the ones with an error message, which are easy, and the ones that quietly return a plausible wrong number. Both kinds are here. Mistakes 3 and 6 are the quiet ones, so read those twice.

1. Aggregating Every Column

orders.groupby("store").mean()

Error

TypeError: dtype 'str' does not support operation 'mean'

What it means: with no column selected, pandas tried to average all of them, including text columns such as channel. Fix: select the columns you mean (or use named aggregation).

print(orders.groupby("store")[["order_total", "shipping_cost"]].mean().round(2))

Output

           order_total  shipping_cost
store
Asheville       174.90           0.00
Bend            172.91           0.00
Boise           177.22           0.00
Flagstaff       183.61           0.00
Online          204.65           2.56

2. Looking for the Key Among the Columns

summary["store"]

Error

KeyError: 'store'

What it means: after a groupby, store is the index, not a column. Fix: use summary.index, or .reset_index(), or group with as_index=False.

print(summary.index.tolist())
print(summary.reset_index()["store"].tolist())

Output

['Asheville', 'Bend', 'Boise', 'Flagstaff', 'Online']
['Asheville', 'Bend', 'Boise', 'Flagstaff', 'Online']

3. The Average of Averages

store_means = orders.groupby("store")["order_total"].mean()
print(store_means.mean().round(2))
print(orders["order_total"].mean().round(2))

Output

182.66
194.6

What happened: no error, two different "average order values". The first averages the five store averages, giving tiny Asheville the same weight as the online shop with nine times as many orders. The second is the true average over all orders. Fix: never average group means unless the groups are the same size. Go back to the rows, or carry sums and counts and divide at the end.

4. Renaming with a Nested Dictionary

orders.groupby("store").agg({"order_total": {"revenue": "sum"}})

Error

SpecificationError: nested renamer is not supported

What it means: this dictionary-inside-a-dictionary syntax appears in old tutorials and was removed from pandas long ago. Fix: named aggregation.

print(orders.groupby("store").agg(revenue=("order_total", "sum")).round(2).head(2))

Output

             revenue
store
Asheville  247133.35
Bend       298263.94

5. A Key That Is Not a Column

orders.groupby("Store")["order_total"].sum()

Error

KeyError: 'Store'

What it means: the same case-sensitive KeyError as ever. The column is store. Fix: print(orders.columns.tolist()).

6. count When You Meant size

print(orders.groupby("payment_method")["promo_code"].count())
print(orders.groupby("payment_method")["promo_code"].size())

Output

payment_method
card              1271
cash               189
digital_wallet     522
gift_card          166
Name: promo_code, dtype: int64
payment_method
card              12392
cash               1614
digital_wallet     4794
gift_card          1502
Name: promo_code, dtype: int64

What happened: "how many orders per payment method?" has the answer in the second block. The first counted only the orders that have a promo code, because .count() skips missing values in the column it is applied to. Fix: .size() for rows; .count() only when "non-missing values of this column" is really the question.

7. Rows Lost to a Missing Key

From Missing Keys and Categories: grouping by promo_code silently ignored 18,154 of 20,302 orders. Fix: dropna=False, and check that group sizes add up to the table.

🛠️ Project: The Store Scorecard

Pinecrest's leadership meets every quarter and wants two tables: a scorecard with one row per sales channel, and a summary with one row per customer that marketing can use. You will build both from orders.csv, using named aggregation, a computed key, transform and pd.cut. Use a new notebook, lesson_2_4_project. Allow about 35 minutes.

🛠️ Step 1: Prepare helper columns (5 min)

Revenue should count completed orders only: a returned or cancelled order brought in nothing. .where(condition, 0.0) keeps the total where the order was completed and puts 0 elsewhere. Two boolean columns will become rates.

import pandas as pd

pd.set_option("display.width", 150)

❓ Common Questions at This Stage

I have seen .groupby(...).apply(...) used for everything. Should I use it?

Treat it as the last resort. .apply() hands each group's whole DataFrame to your function and tries to stitch together whatever comes back, which makes it flexible, slow, and occasionally surprising in the shape of its result. Nearly every task is clearer as an agg, a transform, or a helper column followed by one of those. Reach for apply only when a calculation truly needs several columns of the group at once and cannot be split into steps.

How do I get the top few rows within each group?

Sort the table first, then take the head of each group: orders.sort_values("order_total", ascending=False).groupby("store").head(3) returns each store's three largest orders, as original rows. Ranking rows within groups more generally is a window operation, covered in Lesson 2.8.

Is the two-level index something I have to learn to love?

No. It is useful for lookups and for unstack, and many working analysts call .reset_index() straight after a multi-key groupby and carry on with ordinary columns. Do whichever keeps your next step simple. You will get more practice with it in the next two lessons.

How is this different from a pivot table?

A pivot table is a groupby on two sets of keys with one set spread across the columns: exactly what you did with groupby([...]) followed by .unstack(). pd.pivot_table() wraps that into one call with extras such as totals. If you understand today's lesson, Lesson 2.6 will feel like a convenient shortcut.

📝 Lesson Summary

🎓 Key Takeaways

  • groupby is split-apply-combine: divide the rows by a key, compute on each pile, collect the answers
  • The result's index is the group key; use as_index=False or .reset_index() to get it back as a column
  • Named aggregation, new=("column", "function"), is the clearest way to build a summary table
  • The mean of a boolean column within each group is a rate
  • agg returns one row per group, transform one value per original row, filter the rows of the groups that pass a test
  • Several keys give a MultiIndex; keys can be computed on the spot, such as .dt.year
  • Rows with a missing key are dropped unless dropna=False; unused categories appear only with observed=False
  • size counts rows, count counts non-missing values, nunique counts distinct values; never average averages of unequal groups
