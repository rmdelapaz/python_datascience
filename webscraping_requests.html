🌐 How the Web Talks

So far your data has arrived as files and database tables that someone prepared for you. A great deal of the world's data is not packaged that way. It sits on web pages and behind web services, and it changes every day. In this module you will learn to collect it yourself, and you will start where every browser, phone app and data pipeline starts: with one request and one response.

💡 Mental Model: The Order Counter

Think of a counter at a deli. You hand over a slip that says what you want ("one number 12, to go") with a few notes about yourself ("no onions, name: Sam"). A moment later a tray comes back. On top is a ticket with a number that says how it went: order filled, we are out of that, you are not allowed to order that, the kitchen is on fire. Under the ticket is the food, if there is any.

That is the whole of HTTP, the HyperText Transfer Protocol. The slip is a request. The tray is a response. The server never calls you; it only answers. And it does not remember your last order unless you remind it.

A request and a response have the same three-part shape.

PartIn a requestIn a response
First lineA method (GET to read, POST to send) and a URLA three-digit status code such as 200 or 404
HeadersNotes about the sender: who you are, what formats you acceptNotes about the answer: its type, its encoding, its date
BodyUsually empty for GET; the data you send for POSTThe page, the JSON, the image: the thing you asked for
graph TD A["Your script calls requests.get"] --> B["Request: GET, URL, headers"] B --> C["Server looks for the page"] C --> D["Response: status, headers, body"] D --> E{"Status 200?"} E -->|yes| F["Use the body"] E -->|no| G["Stop and handle it"]

Python's standard library can speak HTTP, but almost everyone uses the requests library because it makes the common things short and the careful things possible. It was installed with the rest of the course environment in Lesson 0.1.

import requests

print(requests.__version__)

Output

2.34.2

🤔 Why This Matters

Every tool in the rest of this module sits on top of what you learn here. Beautiful Soup parses what requests downloads. An API client is requests plus a key. Rate limiting is deciding when to send the next request. When something goes wrong three lessons from now, the answer will be in a status code or a header, and you will know where to look.

🤝 The Ground Rules

Before the first line of fetching code, a word about manners and law, because a program can do in a minute what would take a person a week, and that power cuts both ways. A website is somebody's property, runs on somebody's bill, and often holds information about real people.

⚠️ Six Rules for This Module (and for Your Career)

  1. Read robots.txt and obey it. It is the site owner's published request to programs: where they may go and how fast.
  2. Read the terms of use. If the terms forbid automated collection, the answer is no, however easy the code would be.
  3. Prefer an API or a download when one exists. It is the front door: stable, documented and meant for programs.
  4. Go slowly and say who you are. Pause between requests, and send a User-Agent with a way to contact you.
  5. Never go around a login, a paywall or a block. If you are asked to stop, stop.
  6. Do not collect personal data. Names, emails, profiles and photos of real people are protected by privacy laws in many places, and "it was public" is not a defense you want to test.

This is not legal advice, and the law differs from country to country. As a working rule: facts such as prices and opening hours are usually fine to collect in modest amounts for analysis, while republishing someone's content, overloading their server or gathering information about people can get you or your employer into real trouble. When in doubt, ask the site owner. An email often gets you a cleaner dataset than a scraper would.

🚀 Your First GET

The first page a polite program asks for is the rule book. By convention it is a plain text file named robots.txt. The practice shop keeps its copy one folder up from the shop, and urljoin from the standard library builds that address the same way a browser resolves a link.

from urllib.parse import urljoin

robots_url = urljoin(BASE_URL, "../robots.txt")
print(robots_url)

r = requests.get(robots_url, timeout=10)
print(r.status_code)
print(r.text)

Output

https://rays-python-datascience.netlify.app/practice/robots.txt
200
# Practice rules for the Python Data Science course (fictional shop).
# A real robots.txt lives at the root of a site; this one is a teaching copy
# that the lessons read with urllib.robotparser.
User-agent: *
Disallow: /practice/shop/staff/
Crawl-delay: 1

User-agent: BadBot
Disallow: /

That was a complete HTTP conversation. requests.get() sent a GET request and returned a Response object, which you named r. Its status_code is 200, which means "here you go", and r.text is the body as a string. (The timeout=10 gets its own section below. For now, never leave it out.)

Now read the file as its author meant it:

  • User-agent: * starts a group of rules for every program.
  • Disallow: /practice/shop/staff/ asks programs to stay out of that folder.
  • Crawl-delay: 1 asks for at least one second between requests.
  • A second group tells a program calling itself BadBot that it is not welcome anywhere.

You do not have to interpret the file by eye. The standard library's RobotFileParser answers the two questions that matter: may I fetch this, and how long should I wait?

from urllib.robotparser import RobotFileParser

robots = RobotFileParser()
robots.parse(r.text.splitlines())

print(robots.can_fetch(USER_AGENT, BASE_URL))
print(robots.can_fetch(USER_AGENT, urljoin(BASE_URL, "staff/")))
print(robots.can_fetch("BadBot", BASE_URL))
print(robots.crawl_delay(USER_AGENT))

Output

True
False
False
1

The shop is open to you, the staff folder is not, and the owner would like one second between requests. Nothing in the software will stop you from fetching the staff page. That is the point: robots.txt is a request, and honoring it is your job.

💡 Where robots.txt Normally Lives

On a real site the file is always at the root: https://the-site/robots.txt. The practice shop's copy sits at /practice/robots.txt because the shop shares a website with these lessons. If a site has no robots.txt at all, nothing is disallowed by it, and the other five rules still apply.

🚦 Status Codes

The status code is the server's one-number summary of what happened. You only need to remember the first digit to know whose move it is.

RangeMeaningOnes you will meetWhat to do
2xxSuccess200 OKUse the body
3xxLook elsewhere301, 302 redirectsNothing: requests follows them for you
4xxYour request has a problem400 bad request, 401 not signed in, 403 forbidden, 404 not found, 429 too many requestsFix the request. Asking again unchanged will not help (except 429: wait first)
5xxThe server has a problem500 server error, 503 unavailableWait and try again later

Ask for a page that does not exist and look closely at what comes back.

missing = requests.get(urljoin(BASE_URL, "no-such-page.html"), timeout=10)

print(missing.status_code, missing.reason)
print(missing.ok)
print(missing.headers["Content-Type"])

Output

404 Not Found
False
text/html; charset=utf-8

⚠️ A 404 Is Not an Exception

requests.get() did not raise an error. From its point of view the conversation went perfectly: it asked, and the server answered "not found" and, as the content type shows, put a friendly HTML error page in the body. If your code goes on to parse that body, it will find no products, report zero results, and never tell you why. A failed request looks like success unless you check.

The check is one method. raise_for_status() does nothing for a good response and raises HTTPError for a 4xx or 5xx.

missing.raise_for_status()

Error

HTTPError: 404 Client Error: Not Found for url: https://rays-python-datascience.netlify.app/practice/shop/no-such-page.html

Make it a reflex: get, then raise_for_status(), then use the body. A loud failure at the request is far cheaper than a quiet one three steps later.

📨 Headers and Saying Who You Are

Headers are the notes on the slip and on the ticket: name-and-value pairs that travel with every request and response. The response's headers are in r.headers, which behaves like a dictionary whose keys ignore upper and lower case.

for name in ["Content-Type", "Server", "Cache-Control", "Date"]:
    print(f"{name}: {r.headers.get(name)}")

print(r.headers["content-type"])

Output (your date will differ)

Content-Type: text/html; charset=UTF-8
Server: Netlify
Cache-Control: public,max-age=0,must-revalidate
Date: Sun, 11 Oct 2026 20:33:57 GMT
text/html; charset=UTF-8

Content-Type is the one you will use most. It says what the body is (text/html, application/json, image/png) and often how its text is encoded. More on that in the next section.

What did you send? The response keeps a copy of the request that produced it.

print(r.request.method, r.request.url)
for name, value in r.request.headers.items():
    print(f"{name}: {value}")

Output (your version number may differ)

GET https://rays-python-datascience.netlify.app/practice/shop/
User-Agent: python-requests/2.34.2
Accept-Encoding: gzip, deflate
Accept: */*
Connection: keep-alive

You wrote none of those headers. requests filled them in, including a User-Agent that says only "some Python script". To the person who runs the site, that is an anonymous visitor: if your script misbehaves, their only option is to block it. Introduce yourself instead.

HEADERS = {"User-Agent": USER_AGENT}

r = requests.get(BASE_URL, headers=HEADERS, timeout=10)
print(r.request.headers["User-Agent"])

Output

pinecrest-course-bot/1.0 (learning project; contact: you@example.com)

A good User-Agent names your project and gives a contact. Now an administrator who sees your requests in the server log can write to you before reaching for the block button. You will pass HEADERS with every request from here on.

🛑 Do Not Pretend to Be a Browser

You will find advice online to copy a browser's User-Agent so that a site "cannot tell" you are a script. That is disguising yourself to get around a site's wishes, which breaks rules 4 and 5 at once. If a site turns away honest programs, the honest response is to use its API, ask for permission, or leave it alone.

🔤 Bytes, Text and Encoding

Computers send bytes. A response body is a sequence of numbers from 0 to 255, available untouched as r.content. To give you a string in r.text, requests has to decode those bytes with some encoding, and it chooses the one named in the Content-Type header.

print(type(r.content), type(r.text))
print(r.encoding)
print(len(r.content), "bytes became", len(r.text), "characters")

Output

<class 'bytes'> <class 'str'>
UTF-8
11783 bytes became 11725 characters

There are fewer characters than bytes because some characters need more than one byte in UTF-8. The shop's rating star is one of them:

star = "★"
star_bytes = star.encode("utf-8")
print(star_bytes, len(star_bytes))
print(star_bytes.decode("utf-8"))
print(star_bytes.decode("cp1252"))

Output

b'\xe2\x98\x85' 3
★
â˜…

Three bytes, one star, when decoded with the encoding that wrote them. Decoded with the wrong table (cp1252, an old Western European encoding), the same three bytes become three junk characters. That garbage has a name, mojibake, and you will recognize it for the rest of your life: â˜…, â€™, Ã©.

It happens with web pages when the server does not say which encoding it used. Then requests has to guess, and for HTML its fallback is a Western European encoding. You can reproduce the problem, and the cure, by setting r.encoding yourself:

r.encoding = "cp1252"                    # decode the same bytes with the wrong table
print("★" in r.text, "â˜…" in r.text)

r.encoding = "utf-8"                     # the table that matches the bytes
print("★" in r.text, "â˜…" in r.text)

Output

False True
True False

💡 Three Ways to Stay Out of Trouble

  • If text looks wrong, print r.encoding and the Content-Type header. A missing charset is the usual cause. Python's own http.server, for one, does not send it, so a local copy of the shop shows this exact problem.
  • Set r.encoding = "utf-8" before reading r.text when you know the page is UTF-8 (nearly all modern pages are).
  • Or skip the guess: hand the bytes, r.content, to a parser that reads the page's own <meta charset> tag. Beautiful Soup does this, as you will see in Lesson 6.2.

🧩 Query Parameters and JSON

HTML is written for people. When a site wants to serve programs, it offers an API (application programming interface): URLs that return data, usually as JSON, with no page design in the way. You already know JSON from Lesson 2.2 and from the documents in Lesson 5.5.

Your data folder includes a small practice API. Open a second terminal, go to your project folder, activate the environment, and start it. Leave it running; you will switch back to your notebook to use it.

python data/mock_api.py

Output

Pinecrest mock API on http://127.0.0.1:8000  (limit: 30 requests per 10 s; Ctrl+C to stop)

127.0.0.1 is the address every computer uses for itself, and 8000 is the port, a numbered door on that computer. This server answers only requests from your own machine. It is a real HTTP server all the same, and it logs each request it receives in that terminal, which is worth a glance now and then.

Asking a Narrower Question

The API's /products address returns the whole catalog, a page at a time. To ask for less you add query parameters: the part of a URL after the ?, written as name=value pairs joined by &. Do not glue that string together yourself. Pass a dictionary as params and let requests build it.

API = "http://127.0.0.1:8000"

r = requests.get(f"{API}/products", params={"category": "Tents", "per_page": 3},
                 headers=HEADERS, timeout=10)
r.raise_for_status()

print(r.url)
print(r.headers["Content-Type"])

Output

http://127.0.0.1:8000/products?category=Tents&per_page=3
application/json; charset=utf-8

r.url shows the address that was really requested, with the parameters attached. The content type says JSON, so instead of r.text call r.json(), which parses the body into Python dictionaries and lists.

data = r.json()

print(type(data))
print(list(data))
print(data["total"], "tents in all;", len(data["items"]), "on this page")
print(data["items"][0]["name"], data["items"][0]["price"])

Output

<class 'dict'>
['page', 'per_page', 'total', 'total_pages', 'next', 'items']

The response is a dictionary. Its items key holds a list of product records, and the other keys describe the paging (you will follow next to the end in Lesson 6.4). A list of flat dictionaries is exactly what pd.DataFrame() wants.

import pandas as pd

Why You Let requests Build the URL

r = requests.get(f"{API}/products", params={"category": "Camp Kitchen", "per_page": 1},
                 headers=HEADERS, timeout=10)
print(r.url)
print(r.json()["total"])

Output

http://127.0.0.1:8000/products?category=Camp+Kitchen&per_page=1
29

A URL cannot contain a space, so requests wrote it as +. It also handles &, #, accents and every other character that would otherwise break the address or change its meaning. Hand-built query strings are a classic source of bugs that appear only for some values.

Errors Speak JSON Too

A well-made API explains its errors in the body. The status code tells your program what happened; the message tells you.

r = requests.get(f"{API}/products/TNT-9999", headers=HEADERS, timeout=10)
print(r.status_code)
print(r.json())

Output

404
{'error': {'code': 'not_found', 'message': "No product with SKU 'TNT-9999'."}}

⏳ Timeouts, Always

Here is a fact that surprises people: by default, requests will wait forever. If a server accepts your connection and then goes quiet, a call without timeout never returns. No error, no output, just a notebook cell that says "running" until you notice, or a nightly job that hangs until someone asks where the report is.

The practice API has an address for rehearsing this. /slow waits the number of seconds you ask for before answering.

r = requests.get(f"{API}/slow", params={"seconds": 2}, headers=HEADERS, timeout=10)
print(r.json())

Output

{'waited_seconds': 2.0}

Two seconds is inside the ten you allowed. Now ask it to take five seconds while you are only willing to wait one.

requests.get(f"{API}/slow", params={"seconds": 5}, headers=HEADERS, timeout=1)

Error

ReadTimeout: HTTPConnectionPool(host='127.0.0.1', port=8000): Read timed out. (read timeout=1)

After one second requests gave up and raised ReadTimeout. That is the behavior you want: a clear error you can catch, at a moment you chose.

💡 What the Number Means

timeout=10 is not a limit on the whole download. It is the longest requests will wait for the connection to open, and then the longest it will wait between bytes once the server starts answering. You can set the two separately with a tuple: timeout=(3.05, 10) means up to about 3 seconds to connect and up to 10 seconds of silence while reading. For ordinary pages, a single number between 5 and 30 is a sensible choice.

One Function That Does It Right

You now have four habits: identify yourself, set a timeout, check the status, and expect failure. Typing all four on every call is how they get skipped, so put them in one small function. Everything that can go wrong in requests is a subclass of requests.exceptions.RequestException, with Timeout and HTTPError as the two you will most often want to treat specially.

def fetch(url, **kwargs):
    """GET a URL politely. Returns the response, or None after saying why not."""
    kwargs.setdefault("headers", HEADERS)
    kwargs.setdefault("timeout", 10)
    try:
        resp = requests.get(url, **kwargs)
        resp.raise_for_status()
    except requests.exceptions.Timeout:
        print(f"TIMEOUT   {url}")
    except requests.exceptions.HTTPError as err:
        print(f"HTTP {err.response.status_code}  {url}")
    except requests.exceptions.RequestException as err:
        print(f"FAILED    {url} ({type(err).__name__})")
    else:
        return resp
    return None

print(fetch(BASE_URL))
print(fetch(urljoin(BASE_URL, "no-such-page.html")))
print(fetch(f"{API}/slow", params={"seconds": 5}, timeout=1))

Output

<Response [200]>
HTTP 404  https://rays-python-datascience.netlify.app/practice/shop/no-such-page.html
None
TIMEOUT   http://127.0.0.1:8000/slow
None

The order of the except clauses matters: specific exceptions first, the general RequestException last, as a net for everything else (no network, a mistyped host name, a refused connection). The caller gets either a good response or None, and can never mistake one for the other.

✅ Errors Are the Normal Case

On your own disk, a file is either there or it is not. On a network, things fail for reasons that have nothing to do with your code: a router restarts, a server is busy, a page was removed yesterday. Writing the except branches is not pessimism and it is not a sign you did something wrong. It is what finished network code looks like.

🔗 Sessions

Each call to requests.get() opens a new connection to the server, sends one request, and hangs up. For a handful of pages that is fine. For many pages from the same site, a Session is better in two ways: it keeps the connection open between requests, which is faster for you and lighter for the server, and it remembers settings such as your headers so you state them once.

import time

with requests.Session() as session:
    session.headers.update(HEADERS)
    for page in ["index.html", "page-2.html", "page-3.html"]:
        resp = session.get(urljoin(BASE_URL, page), timeout=10)
        resp.raise_for_status()
        print(page, resp.status_code, len(resp.content), "bytes")
        time.sleep(1)                    # the Crawl-delay from robots.txt

Output

index.html 200 11783 bytes
page-2.html 200 11854 bytes
page-3.html 200 11708 bytes

Three things to notice. session.headers.update() adds your User-Agent to every request the session makes. The with block closes the connection when you are done, exactly like with open(...) closes a file. And time.sleep(1) honors the one-second crawl delay you read at the start of the lesson.

⚠️ A Session Does Not Remember a Timeout

There is no session-wide timeout setting. You still pass timeout= on every call, which is one more reason to wrap your requests in a small function of your own.

A session also keeps cookies, the small values a server hands out so that it can recognize your next request. That is how a site knows you are signed in. The practice shop sets none, and authentication is the subject of Lesson 6.4.

💾 Saving Raw Responses

Downloading and analyzing are two different jobs, and the first is the slow, fragile, impolite-if-repeated one. So do it once. Save exactly what the server sent, then do all your parsing experiments on the saved copy. If your parsing code has a bug, and it will, you fix it and rerun without sending a single new request.

from pathlib import Path

raw_dir = Path("raw")
raw_dir.mkdir(exist_ok=True)

resp = fetch(urljoin(BASE_URL, "price-list.html"))
path = raw_dir / "price-list.html"
path.write_bytes(resp.content)

print(path.as_posix(), path.stat().st_size, "bytes")

Output

raw/price-list.html 38515 bytes

Write resp.content, the bytes, not resp.text. Bytes are what arrived; saving them sidesteps every encoding question and works just as well for images and PDFs. Reading it back needs no network at all:

html = path.read_text(encoding="utf-8")
print(html.count("<tr>"), "table rows, read from disk")

Output

248 table rows, read from disk

A saved copy is also a record. Pages change and disappear, and "this is what the site said on the day I collected it" is something an analyst needs to be able to show. Keep the raw/ folder next to your notebook; the project below adds a log of what is in it.

⚠️ Common Mistakes

Everyone makes these in their first week of network code. Each one is quick to recognize once you have seen its message.

1. Leaving Off the https://

requests.get("rays-python-datascience.netlify.app/practice/shop/", timeout=10)

Error

MissingSchema: Invalid URL 'rays-python-datascience.netlify.app/practice/shop/': No scheme supplied. Perhaps you meant https://rays-python-datascience.netlify.app/practice/shop/?

What it means: the "scheme" is the https:// or http:// at the front. Browsers add it for you; requests will not guess. Fix: write the full URL, and build the others from BASE_URL with urljoin.

2. Calling .json() on Something That Is Not JSON

page = requests.get(BASE_URL, headers=HEADERS, timeout=10)
page.json()

Error

JSONDecodeError: Expecting value: line 1 column 1 (char 0)

What it means: the parser expected JSON and the very first character (line 1, column 1) was the < of an HTML page. This often appears when an API answers with an HTML error page, or when you requested the wrong URL. Fix: check r.status_code and r.headers["Content-Type"], and print r.text[:200] to see what you really received.

3. Parsing an Error Page as if It Were Data

page = requests.get(urljoin(BASE_URL, "page-14.html"), headers=HEADERS, timeout=10)
print(page.status_code, page.text.count("product-card"))

Output (no error, and no data)

404 0

What happened: the catalog has 13 pages. Page 14 is a 404, and its body contains no products, so a loop that counts products quietly records zero. Fix: raise_for_status() after every request, or use a helper like fetch() that does.

4. No Timeout

r = requests.get(f"{API}/slow", params={"seconds": 10})   # waits as long as the server likes

What happens: nothing, for as long as the server stays silent. There is no message to show you because there is no error. Fix: timeout= on every call. If a cell has been "running" for a minute, interrupt it (the stop button in Jupyter, Ctrl+C in a terminal) and look for the call that is missing one.

5. Forgetting to Start the Practice API

If the second terminal is closed, every call to http://127.0.0.1:8000 raises ConnectionError with a long message that ends in Connection refused (on some systems it shows up as a connect timeout instead). Fix: start python data/mock_api.py again and rerun the cell. The same error for a public site usually means you are offline or the host name is misspelled.

🛠️ Step 2: Write polite_get() (8 min)

One function holds every habit from this lesson. It refuses URLs that robots.txt disallows, sets a timeout, catches failures, and pauses after each request. It returns a small dictionary describing what happened, plus the response when there is one.

def polite_get(url):
    """Fetch one URL by the rules. Returns (log_row, response_or_None)."""
    row = {"url": url.replace(BASE_URL, ""), "status": None, "bytes": 0, "note": ""}
    if not robots.can_fetch(USER_AGENT, url):
        row["note"] = "skipped: robots.txt"
        return row, None
    try:
        resp = session.get(url, timeout=10)
        row["status"] = resp.status_code
        resp.raise_for_status()
    except requests.exceptions.Timeout:
        row["note"] = "timeout"
        resp = None
    except requests.exceptions.HTTPError:
        row["note"] = "http error"
        resp = None
    except requests.exceptions.RequestException as err:
        row["note"] = type(err).__name__
        resp = None
    else:
        row["bytes"] = len(resp.content)
    time.sleep(delay)
    return row, resp

row, resp = polite_get(urljoin(BASE_URL, "staff/"))
print(row)

Output

{'url': 'staff/', 'status': None, 'bytes': 0, 'note': 'skipped: robots.txt'}

The staff page was never requested. The check happens before the network is touched, which is the only place it does any good.

🏋️ Exercise 4: A JSON Helper That Explains Itself (Stretch)

Write get_json(url, **kwargs) that returns a pair (data, problem). On success, data is the parsed JSON and problem is None. On failure, data is None and problem is a short string: "timeout", the API's own error message for an HTTP error when it sent one, or "not JSON". Test it on a product that exists, a product that does not, the shop's front page, and /slow with a one-second timeout.

💡 Hint

An HTTPError carries the response as err.response, and that response may have a JSON body of its own. requests.exceptions.JSONDecodeError is what .json() raises for a body that is not JSON.

✅ Solution 
def get_json(url, **kwargs):
    kwargs.setdefault("headers", HEADERS)
    kwargs.setdefault("timeout", 10)
    try:
        resp = requests.get(url, **kwargs)
        resp.raise_for_status()
        return resp.json(), None
    except requests.exceptions.Timeout:
        return None, "timeout"
    except requests.exceptions.HTTPError as err:
        try:
            return None, err.response.json()["error"]["message"]
        except (requests.exceptions.JSONDecodeError, KeyError):
            return None, f"HTTP {err.response.status_code}"
    except requests.exceptions.JSONDecodeError:
        return None, "not JSON"

data, problem = get_json(f"{API}/products/SNW-1001")
print(data["name"], "|", problem)
print(get_json(f"{API}/products/SNW-9999"))
print(get_json(BASE_URL))
print(get_json(f"{API}/slow", params={"seconds": 3}, timeout=1))

Output

Wrenfield Sawtooth Snowshoes | None
(None, "No product with SKU 'SNW-9999'.")
(None, 'not JSON')
(None, 'timeout')

The JSONDecodeError clause can sit after the others because the exceptions are checked in order and only one matches each failure. Notice the nested try: an error response is itself something you parse carefully, because not every server explains its errors in JSON.

❓ Common Questions at This Stage

Is web scraping legal?

It depends on what you collect, how, from whom, and where you live, which is why this lesson gives you rules of conduct instead of a yes or no. Collecting modest amounts of non-personal facts from pages a site offers to everyone, at a gentle pace, while honoring robots.txt and the terms of use, is the low-risk end. Going around logins, ignoring a request to stop, copying creative content or gathering data about people is the high-risk end. For anything commercial or large, ask the site owner or get advice from someone qualified.

pandas can read a URL directly. Why not just use pd.read_csv(url)?

For a public CSV file on a server you trust, that is a fine shortcut. It gives you no say over the User-Agent, the timeout or what happens on an error, and it does not keep the raw file. Fetching with requests, saving the bytes, then reading the saved file with pandas gives you control and a record, for three extra lines.

When would I use POST instead of GET?

GET reads: it should never change anything on the server, and its parameters travel in the URL. POST sends data in the request body, for example to submit a form or to log in. You will send your first POST in Lesson 6.4, with requests.post(url, json={...}). The response object works exactly as it does for GET.

What is the difference between http:// and https://?

HTTPS is the same conversation inside an encrypted connection, so nobody between you and the server can read or alter it. requests handles the encryption and checks the site's certificate for you. Public sites should always be HTTPS. The practice API uses plain HTTP only because it never leaves your own computer.

I have seen urllib and httpx in other tutorials. Should I learn those?

urllib is the standard library's HTTP tool: always available, more typing. httpx is a newer library with a very similar interface to requests plus support for asynchronous code. The concepts in this lesson (methods, status codes, headers, timeouts, sessions) are HTTP itself, so they carry over unchanged to either one.

🎓 Key Takeaways

  • HTTP is request and response: a method, a URL, headers and maybe a body go out; a status code, headers and a body come back
  • Check robots.txt and the terms first, prefer an API, go slowly, identify yourself, never go around a login, and do not collect personal data
  • A 4xx or 5xx status is not an exception until you call raise_for_status(): get, check, then use
  • Send a User-Agent that names your project and gives a contact address
  • r.content is bytes and r.text is those bytes decoded with r.encoding; junk such as â˜… means the wrong encoding
  • Pass query parameters as a params dictionary, and read JSON responses with r.json()
  • Every request gets a timeout; without one, requests waits forever
  • A Session reuses the connection and remembers your headers
  • Save the raw bytes once, then parse the saved copy as many times as you like
