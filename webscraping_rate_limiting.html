🚦 Why Servers Say "Slow Down"

At the end of Lesson 6.4 you were asked how long it would take to download all 20,302 orders. At 100 per page that is 204 requests. Your computer could send them in a couple of seconds. The API will not let it, and it is right not to.

A server has finite capacity, and it is shared. A rate limit is the owner's rule for how much of that capacity one client may use: so many requests per so many seconds. It keeps one eager script from slowing the service for everyone else, protects the owner's bill, and gives every user a predictable share. Public websites have limits too, usually unwritten ones, which is why robots.txt has a Crawl-delay and why you have been pausing between pages since Lesson 6.1.

💡 Mental Model: The Freeway On-Ramp Light

Many freeway on-ramps have a traffic light that lets one car go every few seconds. Nobody enjoys it. But without it, everyone merges at once and the whole freeway slows to a crawl, including the cars from that ramp. With it, traffic keeps flowing and everyone arrives sooner.

A rate limit is that light. A good driver does not race up to it and brake hard on every cycle. They arrive at the pace the light allows, wait when it is red for exactly as long as it says, and do not honk.

Being a good client has two halves, and this lesson teaches both:

  • Politeness: pace yourself so that you rarely hit the limit, obey the server's instructions when you do, and never fetch the same thing twice.
  • Resilience: when something fails for a moment (a busy server, a dropped connection, your own laptop going to sleep), recover without losing work and without making the server's bad moment worse.

class ApiError(Exception):
    """An error response from the API, with its status, code and message."""

    def __init__(self, status, code, message):
        super().__init__(f"{status} {code}: {message}")
        self.status, self.code, self.message = status, code, message


def check(resp):
    """Return the response if it succeeded. Otherwise raise ApiError."""
    if resp.ok:
        return resp
    try:
        error = resp.json()["error"]
        code, message = error["code"], error["message"]
    except (requests.exceptions.JSONDecodeError, KeyError, TypeError):
        code, message = "http_error", resp.reason
    raise ApiError(resp.status_code, code, message)


def fresh_window():
    """Wait out the current rate-limit window so that a demonstration starts from zero."""
    time.sleep(PER)

✅ A Safe Place to Get Rate Limited

You are about to trip a rate limit on purpose, several times. On a real service that would be rude. Here the server is yours, the limit exists to be explored, and seeing a 429 with your own eyes is the fastest way to stop being afraid of one.

📏 Reading the Limit

Well-behaved APIs tell you where you stand on every response, in headers. The names vary a little between services; these three are the most common.

def limit_headers(resp):
    return {k: v for k, v in resp.headers.items() if k.startswith("X-RateLimit")}

r = requests.get(f"{API}/products", params={"per_page": 1}, headers=HEADERS, timeout=10)
print(r.status_code, limit_headers(r))

Output

200 {'X-RateLimit-Limit': '10', 'X-RateLimit-Remaining': '9', 'X-RateLimit-Reset': '5'}
HeaderMeaning
X-RateLimit-LimitRequests allowed per window
X-RateLimit-RemainingRequests you have left in the current window
X-RateLimit-ResetSeconds until the window starts over (some APIs send a clock time instead: read the documentation)

This API counts in fixed windows: your first request starts a 5-second window, you may make 10 requests inside it, and then the count starts again. Now see what happens when you ignore all that and send 13 requests as fast as Python can.

fresh_window()

statuses = []
for i in range(13):
    r = requests.get(f"{API}/products", params={"per_page": 1}, headers=HEADERS, timeout=10)
    statuses.append(r.status_code)

print(statuses)
print("Retry-After:", r.headers["Retry-After"])
print(r.json()["error"]["message"])

Output

[200, 200, 200, 200, 200, 200, 200, 200, 200, 200, 429, 429, 429]
Retry-After: 5
Too many requests. Try again in 5 second(s).

Ten answers, then a wall. 429 Too Many Requests is the server holding up a hand, and it comes with an instruction: the Retry-After header says how many seconds to wait before asking again. The three refused requests were pure waste. They returned no data, they still cost the server work, and on a real service a client that keeps doing this gets its key suspended.

🐢 Pacing Yourself

The best way to handle a 429 is not to cause it. If the limit is 10 requests per 5 seconds, then one request every half second never exceeds it. Add a small margin, because your clock and the server's never agree exactly.

A plain time.sleep(0.55) after each request would do. A tiny class does it better (classes as in Lesson 6.4: __init__ stores the settings and a method uses them): it remembers when the last request went out and sleeps only for whatever is left of the interval. Time your code spends parsing or saving counts toward the wait, so you are never slower than you need to be.

class Throttle:
    """Keep calls at least `interval` seconds apart."""

    def __init__(self, interval):
        self.interval = interval
        self.last = None

    def wait(self):
        if self.last is not None:
            remaining = self.interval - (time.monotonic() - self.last)
            if remaining > 0:
                time.sleep(remaining)
        self.last = time.monotonic()


interval = PER / LIMIT * 1.1
print(f"one request every {interval:.2f} s")

fresh_window()
throttle = Throttle(interval)
statuses = []
started = time.monotonic()
for i in range(13):
    throttle.wait()
    r = requests.get(f"{API}/products", params={"per_page": 1}, headers=HEADERS, timeout=10)
    statuses.append(r.status_code)

print(statuses)
print(f"took about {time.monotonic() - started:.0f} s")

Output

one request every 0.55 s
[200, 200, 200, 200, 200, 200, 200, 200, 200, 200, 200, 200, 200]
took about 7 s

The same 13 requests, thirteen successes, about seven seconds. Compare that with the burst: it got ten answers instantly and then would have had to wait five seconds for the rest anyway. Pacing costs you almost nothing and costs the server much less. Over a long job the steady client and the bursty client finish at nearly the same time. Only one of them was a nuisance.

💡 When You Do Not Know the Limit

Websites rarely publish one. Use the Crawl-delay from robots.txt if there is one. If not, one request per second is a widely used default for small jobs, and slower is kinder for large ones. If responses start getting slower or you see 429 or 503, you are going too fast whatever the rules say.

✋ 429 and Retry-After

Pacing is plan A. You still need plan B, because limits change, other programs may be sharing your key, and some APIs do not tell you the limit in advance. Plan B is simple: when the server says 429, wait as long as it asks, then try again.

def get_polite(url, max_tries=5, **kwargs):
    """GET that waits and retries when the server answers 429."""
    kwargs.setdefault("headers", HEADERS)
    kwargs.setdefault("timeout", 10)
    for attempt in range(1, max_tries + 1):
        resp = requests.get(url, **kwargs)
        if resp.status_code != 429:
            return resp
        wait = float(resp.headers.get("Retry-After", 1))
        print(f"  429 (try {attempt}): waiting {wait:.0f} s, as asked")
        time.sleep(wait)
    return resp


fresh_window()
statuses = [get_polite(f"{API}/products", params={"per_page": 1}).status_code for i in range(25)]
print(statuses.count(200), "of", len(statuses), "succeeded")

Output

  429 (try 1): waiting 5 s, as asked
  429 (try 1): waiting 5 s, as asked
25 of 25 succeeded

Twenty-five requests with no pacing at all, and every one succeeded in the end. The function ran into the limit twice, read the header, waited, and carried on. Three details make it trustworthy:

  • resp.headers.get("Retry-After", 1) has a default. Not every 429 carries the header, and code that assumes it does will crash exactly when things are already going badly.
  • max_tries bounds the loop. If the server keeps refusing, the function returns the last 429 instead of waiting forever.
  • It retries only on 429. Every other response goes straight back to the caller.

⚠️ Retry-After Can Also Be a Date

The standard allows two forms: a number of seconds, as here, or a full date such as Wed, 21 Oct 2026 07:28:00 GMT. Seconds are far more common for rate limits. If an API you use sends dates, email.utils.parsedate_to_datetime() from the standard library converts one.

📈 Exponential Backoff with Jitter

A 429 comes with instructions. Other failures do not. A server that is overloaded or restarting answers 503 Service Unavailable, or 500, or nothing at all until your timeout fires. These are usually temporary, so trying again is reasonable. The question is when.

Retrying immediately is the worst choice: if the server is struggling, an instant retry from every client is exactly the extra load that keeps it down. The standard answer is exponential backoff: wait a little after the first failure, twice as long after the second, twice as long again after the third, up to a ceiling.

def backoff_delay(attempt, base=0.5, cap=8.0):
    """Seconds to wait after failed attempt number `attempt` (counting from 0)."""
    return min(cap, base * 2 ** attempt)

print([backoff_delay(n) for n in range(6)])

Output

[0.5, 1.0, 2.0, 4.0, 8.0, 8.0]

Half a second, one, two, four, then capped at eight. A brief hiccup is retried quickly, and a longer outage gets more and more room.

One problem remains. Imagine a hundred clients that all failed at the same moment. With the schedule above they all retry at 0.5 seconds, all again at 1.5, all again at 3.5: the server is hit by synchronized waves. The cure is jitter, a random amount of spread. A common recipe, "full jitter", waits a random time between zero and the backoff value.

rng = random.Random(42)
print([round(rng.uniform(0, backoff_delay(n)), 2) for n in range(6)])

Output

[0.32, 0.03, 0.55, 0.89, 5.89, 5.41]

The waits still grow on average, but no two clients share a schedule, so the retries arrive as a trickle instead of a wave. (The seeded Random(42) is only so that this page shows the same numbers as your screen; real code uses random.uniform() directly.)

A Flaky Endpoint to Practice On

The practice API's /flaky endpoint fails twice with a 503 and succeeds on the third request, over and over.

    print(r.status_code, "| Retry-After:", r.headers.get("Retry-After"), "|", r.json().get("status", "failed"))

Output

503 | Retry-After: 1 | failed
503 | Retry-After: 1 | failed
200 | Retry-After: None | ok

Now the function that brings the pieces together. It decides, for each failure, whether a retry can help, and how long to wait first.

RETRY_STATUSES = {429, 500, 502, 503, 504}


def get_with_backoff(url, max_tries=5, base=0.5, **kwargs):
    """GET with retries: obeys Retry-After, otherwise backs off exponentially with jitter."""
    kwargs.setdefault("headers", HEADERS)
    kwargs.setdefault("timeout", 10)
    for attempt in range(max_tries):
        try:
            resp = requests.get(url, **kwargs)
            if resp.status_code not in RETRY_STATUSES:
                return resp                         # success, or an error a retry cannot fix
            problem, asked = f"HTTP {resp.status_code}", resp.headers.get("Retry-After")
        except (requests.exceptions.Timeout, requests.exceptions.ConnectionError) as err:
            problem, asked = type(err).__name__, None
        if attempt == max_tries - 1:
            break
        delay = float(asked) if asked else random.uniform(0, backoff_delay(attempt, base))
        print(f"  try {attempt + 1}: {problem}; next try in {delay:.1f} s")
        time.sleep(delay)
    raise RuntimeError(f"gave up after {max_tries} tries (last problem: {problem})")


resp = get_with_backoff(f"{API}/flaky")
print(resp.status_code, resp.json())

Output

  try 1: HTTP 503; next try in 1.0 s
  try 2: HTTP 503; next try in 1.0 s
200 {'status': 'ok', 'attempts_needed': 3}

Two failures, two short waits, success. The caller saw one clean response. (This server sent Retry-After: 1 with its 503, so the function obeyed that instead of rolling its own delay. An instruction from the server always beats your guess.)

graph TD A["Send request"] --> B{"Success?"} B -->|yes| C["Use it"] B -->|no| D{"Temporary?"} D -->|no| E["Stop, fix it"] D -->|yes| F{"Tries left?"} F -->|no| G["Give up clearly"] F -->|yes| H["Wait, retry"] H --> A

"Temporary" means 429, a 5xx status, a timeout or a dropped connection. The wait is whatever Retry-After says, or a backoff delay when the server gives no instruction.

What Not to Retry

A retry only helps when the same request might succeed later. A missing product will still be missing in two seconds. The function returns such answers at once:

resp = get_with_backoff(f"{API}/products/TNT-9999")
print(resp.status_code, resp.json()["error"]["code"])

Output

404 not_found

And when the trouble does not pass, it stops. Ask the slow endpoint for a 3-second answer with a 1-second timeout, and allow three tries:

try:
    get_with_backoff(f"{API}/slow", params={"seconds": 3}, timeout=1, max_tries=3)
except RuntimeError as err:
    print(err)

Output (your delays will differ: they are random)

  try 1: ReadTimeout; next try in 0.4 s
  try 2: ReadTimeout; next try in 0.3 s
gave up after 3 tries (last problem: ReadTimeout)

Each wait was drawn at random, below a ceiling that doubled. After the third timeout the function raised an error that says what it tried and what went wrong. Giving up clearly is part of retrying well. A job that fails at 2 a.m. with a precise message is far better than one that is still "retrying" at 9.

🧩 Retries Built into a Session

You wrote get_with_backoff() to understand what a retry policy is made of. For everyday work you do not have to maintain your own. requests is built on a library called urllib3, which has a well-tested Retry class. You attach it to a Session through an HTTPAdapter, and from then on every request made with that session is retried according to your policy.

from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry


def make_session(total=5, backoff_factor=0.5):
    """A Session that identifies itself and retries temporary failures."""
    retry = Retry(
        total=total,                                   # at most this many retries per request
        backoff_factor=backoff_factor,                 # exponential backoff between them
        status_forcelist=[429, 500, 502, 503, 504],    # retry on these statuses
        allowed_methods=["GET", "HEAD"],               # only for requests that are safe to repeat
        respect_retry_after_header=True,               # obey Retry-After when the server sends it
    )
    adapter = HTTPAdapter(max_retries=retry)
    session = requests.Session()
    session.mount("https://", adapter)
    session.mount("http://", adapter)
    session.headers.update(HEADERS)
    return session


session = make_session()

resp = session.get(f"{API}/flaky", timeout=10)
print(resp.status_code, resp.json())
print("retried after:", [attempt.status for attempt in resp.raw.retries.history])

Output

200 {'status': 'ok', 'attempts_needed': 3}
retried after: [503, 503]

One call, one good response. The history shows that urllib3 quietly absorbed two 503s on the way. Every argument maps onto something you built by hand in the last section:

  • total is your max_tries, counted as retries after the first attempt.
  • backoff_factor sets the exponential schedule. Connection errors and timeouts on connecting are retried as well.
  • status_forcelist is your RETRY_STATUSES.
  • allowed_methods keeps retries to requests that only read. Repeating a POST that places an order could place it twice.
  • session.mount() says which addresses the adapter handles: everything starting with https:// or http://.

The same session shrugs off the rate limit, because 429 is in the list and Retry-After is respected:

fresh_window()
started = time.monotonic()
statuses = [session.get(f"{API}/products", params={"per_page": 1}, timeout=10).status_code
            for i in range(14)]

print(statuses.count(200), "of", len(statuses), "succeeded")
print(f"took about {time.monotonic() - started:.0f} s")

Output (your time may differ by a second)

14 of 14 succeeded
took about 6 s

Fourteen requests into a ten-request window: the eleventh was refused, urllib3 waited the five seconds the server asked for, and the rest went through. When retries run out, you get an exception to catch:

impatient = make_session(total=1)

try:
    impatient.get(f"{API}/flaky", timeout=10)
except requests.exceptions.RetryError as err:
    print(type(err).__name__)
    print(err)

print(impatient.get(f"{API}/flaky", timeout=10).status_code)
impatient.close()

Output

RetryError
HTTPConnectionPool(host='127.0.0.1', port=8000): Max retries exceeded with url: /flaky (Caused by ResponseError('too many 503 error responses'))
200

One retry was not enough for an endpoint that fails twice, so requests raised RetryError. (The final line makes the third request of the cycle, which succeeds, so that /flaky is back at the start of its pattern for your next cell.)

⚠️ Retries Are a Safety Net, Not a Pace

A session that retries 429s will get a burst through eventually, but it does so by hitting the limit again and again. Keep pacing with a Throttle as plan A and let the retry policy catch the rare miss. You still pass timeout= on every call: a retry policy does not set one for you.

🗄️ Caching Responses on Disk

The politest request is the one you never send. While you develop an analysis you run the same cells again and again, and each run asks the server for data it already gave you. A cache ends that: save each response the first time, and read the saved copy from then on. You met the idea in Lesson 6.1 as "save raw responses". Here it becomes automatic.

The only design decision is the file name. It must be the same for the same request and different for a different one, so build it from the URL and the parameters. A hash turns that text into a short, safe name.

CACHE_DIR = Path("cache")


def cache_path(url, params=None):
    key = url + "?" + json.dumps(params or {}, sort_keys=True)
    return CACHE_DIR / (hashlib.sha256(key.encode("utf-8")).hexdigest()[:16] + ".json")


def cached_get_json(session, url, params=None):
    """Return (data, source). Reads the cache when it can; asks the network when it must."""
    path = cache_path(url, params)
    if path.exists():
        return json.loads(path.read_text(encoding="utf-8")), "cache"
    resp = check(session.get(url, params=params, timeout=10))
    CACHE_DIR.mkdir(exist_ok=True)
    path.write_text(resp.text, encoding="utf-8")
    return resp.json(), "network"


for category in ["Tents", "Snow", "Tents", "Tents"]:
    data, source = cached_get_json(session, f"{API}/products", {"category": category, "per_page": 5})
    print(category, data["total"], "from", source)

print(len(list(CACHE_DIR.glob("*.json"))), "files in the cache")

Output

Tents 24 from network
Snow 22 from network
Tents 24 from cache
Tents 24 from cache
2 files in the cache

Four questions, two requests. (If you run that cell a second time, all four will say "cache": the files are still there. Delete the cache folder to start over.) Two things about the function are deliberate:

  • sort_keys=True makes {"a": 1, "b": 2} and {"b": 2, "a": 1} produce the same file name. They are the same request.
  • check() runs before anything is written, so an error response is never saved. A cache that stores a 429 or a 500 will faithfully serve you that failure forever.

⚠️ A Cache Answers "What Was", Not "What Is"

Cached data is as old as the day you fetched it. That is perfect while developing, and for data that never changes, such as last year's orders. It is wrong for anything current. Decide how old is too old for each job (Exercise 4 adds a maximum age), and never put credentials or other people's personal data in a cache folder that might be shared.

📋 Logging

Your functions have been reporting with print(). That is fine in a notebook you are watching. A job that runs for twenty minutes, or overnight, needs a record you can read afterward: what was requested, when, what failed, what was retried. Python's standard logging module is made for this. It stamps each message with a time and a level, and it lets you choose where messages go and how much detail you want, without touching the code that emits them.

log = logging.getLogger("pinecrest")
log.setLevel(logging.INFO)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(asctime)s %(levelname)-7s %(message)s", datefmt="%H:%M:%S"))
log.handlers = [handler]

log.debug("fetched page 3")                       # too detailed for the INFO level: not shown
log.info("starting download: %s pages", 21)
log.warning("rate limited; waiting %s s", 5)
log.error("gave up on page 7 after 5 tries")

Output (your times will differ)

15:19:30 INFO    starting download: 21 pages
15:19:30 WARNING rate limited; waiting 5 s
15:19:30 ERROR   gave up on page 7 after 5 tries
LevelUse it for
DEBUGStep-by-step detail you want only when investigating: every page fetched, every cache hit
INFOMilestones: job started, job finished, how many rows
WARNINGSomething went wrong and was handled: a retry, a rate limit
ERRORSomething failed and was not recovered

The logger's level is a filter: at INFO, the debug() call above was skipped. A handler decides where messages go. This one writes to the notebook; a logging.FileHandler("job.log") writes to a file, and a logger can have both. (Setting log.handlers to a fresh list, instead of calling addHandler(), keeps a rerun cell from attaching a second copy and printing everything twice.)

🛑 Never Log a Secret

Log files get attached to bug reports and emailed to colleagues. Log URLs, status codes, counts and timings. Never log an API key, a token, a password or an Authorization header. If a URL contains a key as a query parameter, that is one more reason Lesson 6.4 told you to prefer headers.

⏯️ Resumable Jobs

Long downloads get interrupted. Your laptop sleeps, the Wi-Fi drops, a page fails on its fifth retry, you press the stop button by mistake. If the job keeps everything in memory until the end, an interruption at page 180 of 204 loses 180 pages, and the rerun sends all those requests again.

A resumable job saves each piece of work as it is completed and, when started, first looks at what is already done. The technique is the cache again, applied to the pages of one job: one file per page, and a page whose file exists is not requested.

def download_pages(session, path, params, out_dir, throttle, max_new=None):
    """Save every page of a paginated endpoint as a JSON file, skipping pages already saved.

    max_new stops the job after that many new pages (used here to imitate an interruption).
    """
    out_dir = Path(out_dir)
    out_dir.mkdir(exist_ok=True)
    page, fetched, skipped = 1, 0, 0
    while True:
        file = out_dir / f"page_{page:04d}.json"
        if file.exists():
            data = json.loads(file.read_text(encoding="utf-8"))
            skipped += 1
        else:
            if max_new is not None and fetched >= max_new:
                log.warning("stopped before page %s", page)
                return {"complete": False, "fetched": fetched, "skipped": skipped}
            throttle.wait()
            resp = check(session.get(f"{API}{path}", params={**params, "page": page}, timeout=10))
            partial = file.with_suffix(".part")
            partial.write_text(resp.text, encoding="utf-8")
            partial.replace(file)                      # the file appears only when it is whole
            data = resp.json()
            fetched += 1
            log.debug("fetched page %s of %s", page, data["total_pages"])
        if page >= data["total_pages"]:
            return {"complete": True, "fetched": fetched, "skipped": skipped}
        page += 1

Read it as a loop over page numbers with one question at the top: do I already have this page? If so, read the file. If not, wait for the throttle, fetch, and save. Each response says how many pages there are, so the loop knows when it has reached the last one.

The two lines with .part matter more than they look. If the program dies halfway through writing a file, a half-written page_0007.json would be mistaken for a finished page on the next run. Writing to a temporary name and then renaming means a page file either exists completely or does not exist.

Try it on the product catalog, 40 per page, and interrupt it after three pages.

log.setLevel(logging.ERROR)                # keep this demonstration quiet
throttle = Throttle(interval)
job = {"per_page": 40}

print(download_pages(session, "/products", job, "product_pages", throttle, max_new=3))
print(sorted(p.name for p in Path("product_pages").iterdir()))

Output

{'complete': False, 'fetched': 3, 'skipped': 0}
['page_0001.json', 'page_0002.json', 'page_0003.json']

The job stopped with three pages on disk. Run it again, with no limit this time, exactly as you would after a real interruption.

print(download_pages(session, "/products", job, "product_pages", throttle))
print(download_pages(session, "/products", job, "product_pages", throttle))

Output

{'complete': True, 'fetched': 4, 'skipped': 3}
{'complete': True, 'fetched': 0, 'skipped': 7}

The second run skipped the three saved pages and fetched the remaining four. The third run fetched nothing at all: the job is complete, and running it again is free. Building the DataFrame is now a separate step that reads only files.

def load_pages(out_dir):
    """Combine the saved pages of a finished job into one DataFrame."""
    items = []
    for file in sorted(Path(out_dir).glob("page_*.json")):
        items.extend(json.loads(file.read_text(encoding="utf-8"))["items"])
    return pd.DataFrame(items)


catalog = load_pages("product_pages")
print(catalog.shape, "| unique SKUs:", catalog["sku"].is_unique)

Output

(242, 13) | unique SKUs: True

💡 Collect, Then Analyze

This is the pattern from the whole module in its final form: one step talks to the network and writes raw files; a second step reads the files and builds the table. The slow, fragile, rate-limited part runs once. The part you will rewrite ten times runs in milliseconds and never bothers the server.

⚠️ Common Mistakes

1. Assuming Retry-After Is Always There

resp = session.get(f"{API}/health", timeout=10)
wait = int(resp.headers.get("Retry-After"))

Error

TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'

What it means: this response had no Retry-After header, so .get() returned None, and int(None) fails. In real code this line sits inside an error handler, so it crashes at the worst moment. Fix: give a default, resp.headers.get("Retry-After", 1), and fall back to backoff.

2. Retrying Without Waiting, or Without a Limit

while True:                                  # do not run this
    resp = requests.get(url, headers=HEADERS, timeout=10)
    if resp.ok:
        break

What happens: against a server that is down or refusing you, this loop sends requests as fast as your machine can, forever. To the server it is indistinguishable from an attack, and it is the quickest way to get an IP address or key banned. Fix: every retry loop needs a wait that grows and a maximum number of tries.

3. Retrying Errors That Cannot Change

A 400, 401, 403 or 404 describes your request, not the server's mood. Retrying one five times with backoff produces the same answer five times, slowly, and hides the real bug behind a wall of retry messages. Fix: retry only 429, 5xx, timeouts and connection errors, as RETRY_STATUSES and the status_forcelist do.

4. Going Parallel to Go Faster

When a job feels slow, it is tempting to split it across several threads or to run three copies of the script. A rate limit applies to you, not to each of your threads: you will hit the same wall three times as often, and on a public website you have tripled your load on someone else's server. Fix: respect the pace, cache, filter on the server, and let the job take the time it takes.

5. Caching Failures

If your cache writes the body before checking the status, one bad moment (a 429, a 500, an HTML error page) is saved and served on every later run, and your "data" quietly becomes an error message. Fix: check first, write second, as cached_get_json() does. If results ever look strange, delete the cache folder and compare.

🏋️ Exercise 2: Pick a Pace

Write polite_interval(limit, per, margin=1.1) that returns the number of seconds to leave between requests. Use it for three services: 10 requests per 5 seconds, 30 per 10 seconds, and 5,000 per hour. For the last one, how many hours would 100,000 requests take?

def polite_interval(limit, per, margin=1.1):
    return per / limit * margin

for limit, per in [(10, 5), (30, 10), (5000, 3600)]:
    print(f"{limit:>5} per {per:>5} s: one request every {polite_interval(limit, per):.3f} s")

print(f"100,000 requests: {hours:.0f} hours")

Add a max_age argument (in seconds) to the caching function: a cached file older than that is ignored and fetched again. Test it with a maximum age of 2 seconds: call it, call it again at once, wait 3 seconds, call it a third time. Print the source each time.

def cached_get_json_fresh(session, url, params=None, max_age=None):
    """Like cached_get_json, but a cached copy older than max_age seconds is fetched again."""
    path = cache_path(url, params)
    if path.exists():
        age = time.time() - path.stat().st_mtime
        if max_age is None or age <= max_age:
            return json.loads(path.read_text(encoding="utf-8")), "cache"
    resp = check(session.get(url, params=params, timeout=10))
    CACHE_DIR.mkdir(exist_ok=True)
    path.write_text(resp.text, encoding="utf-8")
    return resp.json(), "network"


question = {"category": "Footwear", "per_page": 3}

    time.sleep(pause)
    data, source = cached_get_json_fresh(session, f"{API}/products", question, max_age=2)
    print(data["total"], "from", source)

28 from network
28 from cache
28 from network

Fresh enough the second time, too old the third. The right maximum age depends on the data: seconds for stock prices, a day for a product catalog, forever for last year's orders.

❓ Common Questions at This Stage

Should I write my own retry loop or use urllib3's Retry?

Use Retry on a session for ordinary work: it is well tested and handles details you have not thought of. Write your own when you need behavior it does not offer, such as refreshing a token between tries, or when you want to log every attempt in your own format. Either way, you now know what a good policy contains, so you can read and judge someone else's.

Are there libraries that do caching and retrying for me?

Yes. requests-cache adds a transparent cache to a session, and tenacity provides retry decorators for any function. They are worth learning when a project grows. They are not installed in the course environment, and everything in this lesson works with requests and the standard library alone.

The API I use counts requests per day, not per second. Does this still apply?

The ideas do; the numbers change. With a daily quota, the scarce thing is the total, so caching and filtering on the server matter most, and a resumable job lets you spread the work across days. Read the provider's documentation for which headers report the quota and when it resets.

A website I am scraping sends no rate-limit headers at all. How do I know I am being polite?

Follow robots.txt, including any Crawl-delay. Without one, keep to about one request per second or slower, run large jobs at quiet hours, cache everything, and watch for signs of strain: slower responses, 429, 503. Those mean slow down now. And ask yourself again whether an API or a data download exists.

Is it safe to retry a POST?

Not automatically. GET only reads, so repeating it is harmless. A POST may create or change something, and a retry after a timeout can do it twice, because you cannot tell whether the first attempt reached the server. That is why allowed_methods in this lesson lists only GET and HEAD. Some APIs offer an "idempotency key" to make repeated POSTs safe; follow their documentation.

📝 Lesson Summary

🎓 Key Takeaways

  • A rate limit shares a server fairly; X-RateLimit-* headers tell you where you stand
  • Pace first: spacing requests a little under the limit avoids nearly every 429
  • On 429, wait as long as Retry-After says, with a default for when it is missing
  • Retry temporary failures (429, 5xx, timeouts) with exponential backoff and jitter, a maximum number of tries and a clear final error
  • Never retry what cannot change: 400, 401, 403, 404
  • urllib3's Retry on an HTTPAdapter gives a session this behavior in a few lines
  • Cache successful responses so that nothing is fetched twice, and decide how old is too old
  • Make long jobs resumable: one file per unit of work, written completely or not at all
  • Log what the job did, at sensible levels, and never log a secret
