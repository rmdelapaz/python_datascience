5.3

SQL Window Functions

Rank, compare, accumulate: without collapsing the rows.

5.3 · Why it matters

Many questions need the summary and the detail together

  • How does this order compare with its store's average?
  • What was this month compared with last month?
  • Which are the top two products in each category?
  • GROUP BY cannot answer these and keep the rows
5.3 · Mental model

A seat on the train

  • GROUP BY is the conductor's report: "car 3 has 48 passengers"
  • A window leaves you in your seat and lets you look around
  • Partition: your car · Order: the seats · Frame: how far you look
  • You get an answer and keep your seat
PANDAS transform · rank · shift · cumsum · rolling

5.3 · Common mistakes

Right in almost every row

  • A window function in WHERE → misuse of window function
  • LAG without PARTITION BY: one series reads another's last row
  • The default frame with ties: tied rows share a total
  • An ORDER BY that does not decide: ROW_NUMBER is arbitrary on ties
ASK partition? order? frame?

5.4

Query Optimization

Read the plan, form a guess, change one thing, measure.

5.4 · Why it matters

A correct query can still be a slow one

  • Pinecrest's database is small: everything looks instant
  • A thousand times larger, the same page waits minutes
  • SQL says WHAT; the planner decides HOW
  • We ask it how, and change it with evidence
5.4 · Mental model

The book with no index

  • A table: pages in the order they were written
  • Find every "crampons": read from page 1 to the end. A scan.
  • An index: the sorted list at the back. Jump, then turn to the pages. A search.
  • The index is extra paper, updated on every change
5.4 · Code

Reading a plan

plan("SELECT * FROM orders WHERE order_id = ?", (100500,))
plan("SELECT * FROM orders WHERE store = ? ORDER BY order_date", ("Bend",))
SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)
SEARCH orders USING INDEX idx_orders_store_date_total (store=?)
READ SEARCH: jump · SCAN: read every row · TEMP B-TREE: sort separately

5.4 · Code

Leftmost prefix

conn.execute("CREATE INDEX idx_sd ON orders (store, order_date)")
plan("SELECT order_id FROM orders WHERE store = ? AND order_date BETWEEN ? AND ?",
     ("Bend", "2025-07-01", "2025-07-07"))
plan("SELECT order_id FROM orders INDEXED BY idx_sd WHERE order_date = ?", ("2025-07-04",))
conn.execute("DROP INDEX idx_sd")
SEARCH orders USING COVERING INDEX idx_sd (store=? AND order_date>? AND order_date<?)
SCAN orders USING COVERING INDEX idx_sd
RULE (store, order_date) serves store, or store and date. Not date alone.
5.4 · Code

A function hides the column

conn.execute("DROP INDEX idx_orders_store_date_total")
conn.execute("CREATE INDEX idx_sd ON orders (store, order_date)")
plan(FUNC, ("Bend", "2025-07"))                       # strftime('%Y-%m', order_date) = ?
plan(RANGE, ("Bend", "2025-07-01", "2025-08-01"))     # order_date >= ? AND order_date < ?
SEARCH orders USING COVERING INDEX idx_sd (store=?)
SEARCH orders USING COVERING INDEX idx_sd (store=? AND order_date>? AND order_date<?)
FIX A range on the bare column: >= '2025-07-01' AND < '2025-08-01'
5.4 · An index does not help when...

Four cases

  • The column is inside a function or arithmetic
  • The pattern starts with a wildcard: LIKE '%Tent%'
  • Most rows match: status is 92% completed
  • The table is tiny: 242 products fit in a few pages
AND every index slows writes and grows the file
5.4 · Predict, then run

SCAN or SEARCH?

plan("SELECT sku FROM products WHERE name LIKE ?", ("%Tent%",))
PREDICT Only the primary key is indexed.
5.4 · Common mistakes

Speed claims without evidence

  • Assuming the index is used: read the plan
  • Trusting one timing: best of several runs
  • A stale plan after DROP INDEX: cached_statements=0
  • Indexing every column "to be safe"
ALWAYS Work on a copy. Never index data/pinecrest.db itself.
