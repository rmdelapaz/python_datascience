5.1 · Database Connections: self-check

Q1
A query is written SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT. Which clause does the engine work on first?
A) SELECT, because it is written first
B) WHERE, because rows must be filtered before anything else
C) FROM, because the engine has to pick the table before it can filter, group or select
D) ORDER BY, because sorted rows are faster to filter
Why: The engine runs FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. Knowing that order explains most beginner errors, such as an aggregate in WHERE.
A is wrong: SELECT is written first but runs fifth, after the groups exist.
B is wrong: WHERE runs second: it needs a table to filter.
D is wrong: ORDER BY runs near the end, on the finished result.
Q2
What does this print?
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t (x INTEGER, y TEXT)")
conn.executemany("INSERT INTO t VALUES (?, ?)",
                 [(1, "a"), (2, None), (3, "c")])
print(conn.execute("SELECT COUNT(*), COUNT(y), SUM(x) FROM t").fetchone())
(3, 2, 6)
Why: COUNT(*) counts rows (3). COUNT(y) counts rows where y is not NULL (2: Python's None was stored as NULL). SUM(x) is 1 + 2 + 3. The row comes back as a tuple.
Q3
This line raises ProgrammingError: Incorrect number of bindings supplied. The current statement uses 1, and there are 5 supplied. What is the fix?
conn.execute("SELECT COUNT(*) FROM orders WHERE store = ?", "Boise")
A) Pass a one-item tuple: ("Boise",)
B) Write five placeholders: ?????
C) Put the value in the text with an f-string
D) Use double quotes around the ?
Why: The parameters must be a sequence of values. A string is a sequence of its characters, so "Boise" looked like five values. A one-item tuple needs the trailing comma; a list ["Boise"] also works.
B is wrong: The statement needs one value. Five placeholders would ask for five different values.
C is wrong: That removes the error and opens the door to SQL injection. Never.
D is wrong: A quoted ? is the text of a question mark, not a placeholder.
Q4
You want the average order per store for completed orders in 2025, but only for stores whose average is above $190. Which condition belongs in HAVING?
A) status = 'completed'
B) AVG(order_total) > 190
C) order_date >= '2025-01-01'
D) store IN ('Boise', 'Bend')
Why: WHERE filters rows before the groups exist, so it cannot mention an aggregate. A condition on a group's result goes in HAVING, which runs after GROUP BY.
A is wrong: A condition on each row: WHERE.
C is wrong: A condition on each row: WHERE.
D is wrong: It mentions the grouping column but it is still a row filter, and WHERE is the normal place for it.
Q5
A store name typed into a web form arrives in the variable store. Which line passes it to the database safely?
A) conn.execute(f"SELECT * FROM orders WHERE store = '{store}'")
B) conn.execute("SELECT * FROM orders WHERE store = '" + store + "'")
C) conn.execute("SELECT * FROM orders WHERE store = '{}'".format(store))
D) conn.execute("SELECT * FROM orders WHERE store = ?", (store,))
Why: With a placeholder the SQL text and the value travel separately, so the value can never be read as part of the command.
A is wrong: An f-string pastes the visitor's text into the command: SQL injection.
B is wrong: String concatenation is the same mistake with a different spelling.
C is wrong: So is .format(). All three break on a name like O'Brien even with no attacker.
Q6
What does this print?
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t (k INTEGER PRIMARY KEY)")
conn.commit()
try:
    with conn:
        conn.execute("INSERT INTO t VALUES (1)")
        conn.execute("INSERT INTO t VALUES (1)")
except sqlite3.IntegrityError:
    pass
print(conn.execute("SELECT COUNT(*) FROM t").fetchone()[0])
0
Why: Both inserts are in one transaction. The second breaks the primary key, the block raises, and with conn: rolls the whole transaction back, including the first insert. All or nothing.

5.1 · Predict, then run

P1
Output and reasoning
sql = "SELECT COUNT(*) FROM products WHERE name LIKE '%TENT%'"
print(conn.execute(sql).fetchone()[0])
Answer: 18. In SQLite, LIKE ignores case for the letters A to Z, so '%TENT%' matches "Tent". It is 18, not 24 (the size of the Tents category), because six products in that category are shelters and tarps with no "tent" in the name. In PostgreSQL LIKE is case sensitive and this returns 0; use ILIKE there.
P2
Output and reasoning
cur = conn.execute("SELECT order_id FROM orders ORDER BY order_id LIMIT 5")
cur.fetchone()
cur.fetchone()
print(len(cur.fetchall()), cur.fetchone())
Answer: 3 None. The cursor moves forward only: two rows were fetched, three were left for fetchall(), and after that the cursor is spent, so fetchone() returns None.
P3
Output and reasoning
print(conn.execute("SELECT COUNT(*), COUNT(promo_code) FROM orders").fetchone())
Answer: (20302, 2148). COUNT(*) counts all rows; COUNT(promo_code) counts only the rows where the code is not NULL (20,302 - 18,154).

5.2 · Complex Queries: self-check

Q7
orders has 20,302 rows; 739 of them have a customer_id that is not in customers; 1,058 customers have never ordered. How many rows does orders JOIN customers ON c.customer_id = o.customer_id return?
A) 20,302
B) 19,563
C) 21,360
D) 19,244
Why: A plain JOIN is an inner join: only orders that found a customer survive. 20,302 - 739 = 19,563. The 739 rows vanish with no error.
A is wrong: That is the LEFT JOIN count: every order kept, 739 of them with an empty customer side.
C is wrong: That is the FULL OUTER JOIN: 19,563 + 739 + 1,058.
D is wrong: Customers without orders have no order row to lose, so 1,058 is not subtracted.
Q8
What does this print?
conn = sqlite3.connect(":memory:")
conn.executescript("""
    CREATE TABLE o (id INTEGER, total REAL);
    CREATE TABLE i (order_id INTEGER, sku TEXT);
    INSERT INTO o VALUES (1, 100), (2, 50);
    INSERT INTO i VALUES (1, 'a'), (1, 'b'), (1, 'c'), (2, 'd');
""")
sql = "SELECT SUM(o.total) FROM o JOIN i ON i.order_id = o.id"
print(conn.execute(sql).fetchone()[0])
350.0
Why: Order 1 has three lines, so its total of 100 appears three times after the join; order 2 appears once. 300 + 50 = 350, not the true 150. This is the fan-out trap: sum a column at the level where it lives.
Q9
Which query lists the customers who have never placed an order?
A) SELECT c.* FROM customers AS c LEFT JOIN orders AS o ON o.customer_id = c.customer_id WHERE o.order_id IS NULL
B) SELECT c.* FROM customers AS c JOIN orders AS o ON o.customer_id = c.customer_id WHERE o.order_id IS NULL
C) SELECT c.* FROM customers AS c LEFT JOIN orders AS o ON o.customer_id = c.customer_id WHERE o.order_id = NULL
D) SELECT c.* FROM orders AS o LEFT JOIN customers AS c ON c.customer_id = o.customer_id WHERE c.customer_id IS NULL
Why: The anti-join: keep every customer with LEFT JOIN, then keep the rows where the order side is empty. It returns the 1,058 customers with no orders.
B is wrong: An inner join has already thrown away customers with no order, so nothing is left to find.
C is wrong: = NULL is never true. Test for NULL with IS NULL.
D is wrong: That starts from orders: it finds the 739 orders with no customer, the opposite question.
Q10
359 of the 20,302 orders used the code TRAIL15. SELECT COUNT(*) FROM orders WHERE promo_code <> 'TRAIL15' returns 1,789, not 19,943. Why?
A) <> is not a valid operator in SQLite
B) The query needs DISTINCT
C) Text comparison ignores case, so some codes were double counted
D) For the 18,154 orders with no code the comparison with NULL is unknown, and WHERE keeps only rows where the condition is true
Why: NULL means unknown, so NULL <> 'TRAIL15' is unknown and the row is skipped. To mean "every order that did not use TRAIL15", add OR promo_code IS NULL or compare COALESCE(promo_code, 'none').
A is wrong: <> is the standard not-equal operator (!= works too).
B is wrong: DISTINCT removes duplicate rows from a result; it does not bring back skipped rows.
C is wrong: Case has nothing to do with it: 359 + 1,789 + 18,154 = 20,302 accounts for every order.
Q11
What does this print?
conn = sqlite3.connect(":memory:")
print(conn.execute("SELECT 7 / 2, 7 / 2.0, 100 * 1 / 4").fetchone())
(3, 3.5, 25)
Why: Dividing one integer by another gives an integer in SQLite (and PostgreSQL): 7 / 2 is 3. One real number makes the arithmetic real: 3.5. 100 * 1 / 4 is all integers: 25. A percentage column that is all zeros is integer division: multiply by 100.0.
Q12
A recursive CTE walks the employee tree from the CEO down. What makes the recursion stop?
A) The LIMIT that every recursive CTE must have
B) It reaches the row whose manager_id is NULL
C) A round of the recursive part finds no new rows
D) It has run once for every row in the table
Why: Each round joins the table to the rows found in the round before. When a round adds nobody (the newest employees manage no one), the loop ends and everything found so far is returned.
A is wrong: A LIMIT is a useful guard while developing, but it is not required and is not what ends a healthy recursion.
B is wrong: The row with a NULL manager is the anchor, the START of the walk.
D is wrong: The number of rounds is the depth of the tree (six levels here), not the number of rows.

5.2 · Predict, then run

P1
Output and reasoning
sql = "SELECT COUNT(*) FROM employees AS e JOIN employees AS m"
print(conn.execute(sql).fetchone()[0])
Answer: 3025. 55 × 55. SQLite treats a JOIN with no ON as a cross join. No error; PostgreSQL would reject it. On orders and order_items the same slip would produce over 900 million rows.
P2
Output and reasoning
print(conn.execute("SELECT NULL = NULL, NULL IS NULL, COUNT(NULL)").fetchone())
Answer: (None, 1, 0). NULL = NULL is unknown (shown as None), not true. NULL IS NULL is 1 (true). COUNT(NULL) is 0, because COUNT of a value skips NULL.
P3
Output and reasoning
q = "SELECT channel FROM orders"
for op in ["UNION", "UNION ALL"]:
    print(op, conn.execute(f"SELECT COUNT(*) FROM ({q} {op} {q})").fetchone()[0])
Answer: UNION 2 / UNION ALL 40604. UNION removes duplicates, so two copies of a column with two distinct values give 2 rows. UNION ALL stacks everything: 20,302 + 20,302.

Warm-up and Exit Ticket

Warm-up: retrieval from Session 13
  1. Name three of the six lines of an experiment plan. Answer: Any three of: unit, primary metric, guardrail metric, hypotheses (two-sided, alpha), sample size and duration, decision rule.
  2. Conversion went from 8.86% to 10.03%. Say the lift two ways. Answer: +1.17 percentage points (absolute) and +13% (relative). Both are correct; always say which.
  3. Why is "stop the test the first time p is below 0.05" a problem? Answer: Each look is another chance to cross the line by luck. With weekly looks the false-alarm rate was about 12% instead of 5%; with daily looks about 27%.
  4. What does "grain" mean, and what is the grain of order_items? Answer: What one row represents. One product line on an order (45,490 rows for 20,302 orders). Today's joins live or die on this.
  5. Merging 1,800 survey rows with orders on customer_id gave 9,230 rows. What happened, and what guards against it? Answer: Each response was repeated once per order of that customer. Guard: summarize to one row per customer first, and state the relationship with validate=. In SQL the same trap is called fan-out, and you will see it turn $3.7 million into $10.3 million after the break.
Exit ticket
  1. In one sentence each: what does WHERE filter, and what does HAVING filter? Answer: WHERE filters rows before they are grouped (so it cannot mention an aggregate). HAVING filters groups after GROUP BY (so it can).
  2. Why do values go into SQL through placeholders and never through an f-string? Answer: With a placeholder the SQL text and the value travel separately, so a value can never be read as part of the command. An f-string pastes the value into the command: a quote in the input can change the query (SQL injection), and an honest name like O'Brien breaks it.
  3. orders has 20,302 rows and 739 have no matching customer. How many rows from orders JOIN customers, and how many from orders LEFT JOIN customers? Answer: 19,563 and 20,302. The inner join drops the unmatched rows silently; the left join keeps them with NULL on the customer side.
Common wrong answers and what they reveal
  • "WHERE and HAVING are the same thing" (Q4, exit 1). The learner has not connected the clauses to the order they run in. Have them point at the board: where do the groups come into existence?
  • "The f-string is fine if I trust the input" (Q5, exit 2). They see injection only as an attack. Give the honest failure: a customer called O'Brien.
  • Predicting 20,302 for the inner join (Q7, exit 3). They treat a join as a lookup that cannot fail. Ask what happened to the order whose customer card is missing.
  • 150 for the fan-out item (Q8). The right total, which means the learner did not picture the joined rows. Have them write the four rows of the join by hand.
  • "NULL is like zero" (Q10, lab C). Then <> should have matched. Insist on the word "unknown".
  • "The recursion stops at the CEO" (Q12). The learner reads the tree bottom-up. Trace two rounds from the anchor on the board.
