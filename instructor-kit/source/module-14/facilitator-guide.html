Session 14: SQL from Python: Queries and Joins

How to teach the first SQL session: connect to a database from Python, ask one table for exactly what you need, pass values safely, then combine tables with joins, CTEs and CASE without losing or inventing a single row.

How to Use This Guide

  • Module 5 starts here. For most learners this is their first SQL, and both lessons are dense. Every idea has a pandas twin they already own: say the pandas version aloud whenever a query looks foreign.
  • Same rhythm as every session: Frame → Live demo (you type, they follow) → Guided lab (new practice from the kit) → Start the project. The lesson projects are finished at home.
  • Type SQL one clause per line and run it after each clause. Every code block below was run on the course data; the gray block under it is the real output.
  • Labs live in labs/module-14/: starters for learners, solutions for you. Teal blocks are hands-on, amber blocks are watch-outs.
  • Keep sql_database_connections.html and sql_complex_queries.html open in browser tabs for the flow diagrams, the join table and the recursion diagram.
The #1 risk of Session 14: results that are wrong and look right

In pandas a bad merge at least changes .shape in front of you. In SQL an inner join drops 739 orders, a fan-out triples revenue and a comparison with NULL skips 18,154 rows, all without a word. The habit to build all session: say the row count you expect before you run the query, then count. The second risk is safety: one learner will build SQL with an f-string out of habit. Stop the room when you see it.

Known environment traps

An old SQLite. RIGHT JOIN and FULL OUTER JOIN need SQLite 3.39 or later (Lesson 5.2 shows a rewrite that works everywhere); nothing in the demo or the labs needs them. A version below 3.25 means Session 15's window functions will not run: note the learner and get them a newer Python before then. A typo in the file name creates a new, empty database and the error arrives one line later as OperationalError: no such table: orders. Look for a stray small .db file and delete it. The wrong working folder gives the same message for the same reason. The labs avoid both (they find the data through labs_paths and open it read-only). database is locked: two notebooks hold the same working copy and one has an uncommitted write; commit or restart one kernel. Windows will not overwrite pinecrest_work.db while a connection to it is open (PermissionError on the shutil.copy line when rerunning): restart the kernel first. SQLAlchemy 2 refuses bare strings (ObjectNotExecutableError): wrap SQL in text(...).

Five retrieval questions (Lessons 4.6 and 4.7)
  1. Name three of the six lines of an experiment plan. Answer: Any three of: unit, primary metric, guardrail metric, hypotheses (two-sided, alpha), sample size and duration, decision rule.
  2. Conversion went from 8.86% to 10.03%. Say the lift two ways. Answer: +1.17 percentage points (absolute) and +13% (relative). Both are correct; always say which.
  3. Why is "stop the test the first time p is below 0.05" a problem? Answer: Each look is another chance to cross the line by luck. With weekly looks the false-alarm rate was about 12% instead of 5%; with daily looks about 27%.
  4. What does "grain" mean, and what is the grain of order_items? Answer: What one row represents. One product line on an order (45,490 rows for 20,302 orders). Today's joins live or die on this.
  5. Merging 1,800 survey rows with orders on customer_id gave 9,230 rows. What happened, and what guards against it? Answer: Each response was repeated once per order of that customer. Guard: summarize to one row per customer first, and state the relationship with validate=. In SQL the same trap is called fan-out, and you will see it turn $3.7 million into $10.3 million after the break.

Mental model to say

"A CSV file is a photocopied binder. To find last March's returned orders you carry the whole binder to your desk and flip through every page yourself. A database is a library with a librarian at the desk. You hand over a request slip, 'returned orders, March, Boise store, sorted by total', and the librarian brings back only those pages. The request slip is written in SQL, and the librarian is the database engine."

Then the reassurance: "You already know the ideas. Filtering, sorting, grouping and merging are what you did in Module 2. Today you learn to say the same things in a second language.   10. Parameters, and the wrong way demonstrated safely (4m). Say: "Real queries are rarely fixed text. The store comes from a dropdown, the name from a form. How the value gets into the query is the most important safety habit in this module." 
    def count_customers_unsafe(last_name):
    sql = f"SELECT COUNT(*) FROM customers WHERE last_name = '{last_name}'"  # NO
    return conn.execute(sql).fetchone()[0]

    sql = "SELECT COUNT(*) FROM customers WHERE last_name = ?"
    return conn.execute(sql, (last_name,)).fetchone()[0]

Three mistakes to expect
  • A string where a tuple of parameters belongs. conn.execute("... WHERE store = ?", "Boise") raises ProgrammingError: Incorrect number of bindings supplied. The current statement uses 1, and there are 5 supplied. Coach: "How many characters in Boise?" Fix: ("Boise",) with the trailing comma. It appears in the lab's Step 3 on purpose.
  • An aggregate in WHERE (or a selected column that is neither grouped nor aggregated). The message is misuse of aggregate. Coach with the running order on the board: "Point to where WHERE runs. Do the groups exist yet?" SQLite silently allows the ungrouped-column version; PostgreSQL refuses. Hold them to the rule either way.
  • The f-string out of habit. They have built strings with f-strings for two courses, and one will do it in the lab "because the value comes from my own code". Coach: "What happens to that query when the store is called O'Malley's?" The rule has no exceptions for values. Mental model to say

"Picture a stack of order cards and a stack of customer cards. A join goes through the order cards one at a time, finds the customer card with the same customer_id, and staples the two together into one wider card. Every kind of join is the same stapling. They differ only in what happens to a card that finds no partner: throw it away, or keep it with a blank where the partner would be."

Then uncover the four numbers on the board: 739 orders belong to 150 closed accounts that are not in customers · 1,058 customers have never ordered · 609 order lines use 6 discontinued SKUs that are not in products · 8 products have never sold. Ask learners to look at their paper sketch: which side of each link is "one" and which is "many"?

Say what is coming: "Three results today will be wrong with no error message. I will make each mistake on purpose so that you recognize it when it is yours." (An inner join that drops rows, a sum after a fan-out, a comparison with NULL.)

  10. A recursive CTE walks the whole tree (3m). Say: "How many levels does the company have? A recursive CTE is SQL's loop: an anchor, UNION ALL, and a part that joins the table to the rows found last round." 
    ORG_CTE = """
    WITH RECURSIVE org (employee_id, name, level) AS (
        SELECT employee_id, first_name || ' ' || last_name, 1
        FROM employees
        WHERE manager_id IS NULL                  -- anchor: top of the tree
        UNION ALL
        SELECT e.employee_id, e.first_name || ' ' || e.last_name, org.level + 1
        FROM employees AS e
        JOIN org ON e.manager_id = org.employee_id   -- reports of the last round
    )

Three mistakes to expect
  • Not counting after a join. The query runs, a table appears, and nobody asks how many rows it should have. Coach before they run it: "Write the number you expect in a comment. Now run it." The lab's first step forces it (45,490 lines: 44,881 after the inner join, 45,490 after the left join).
  • Summing after a fan-out. In stock_vs_sales both sides are "many" and both sums inflate (154,470 units sold instead of 30,894; 3,693,132 on hand instead of 22,815). Coach: "What is one row after this join? At what level does quantity live?" The cure: aggregate each side to the grain you need first (a CTE), then join.
  • A filter on the right-hand table in WHERE, which undoes the LEFT JOIN, and its cousin = NULL. Listing every customer with their December 2025 orders, WHERE o.order_date >= '2025-12-01' after the left join keeps only 898 customers instead of 4,850, because the NULL order rows fail the comparison. Coach: "Which table is that condition about? Conditions on the right table of a left join go in the ON clause." And = NULL never matches: IS NULL.

Closing

Exit ticket (3 questions; answers)
  1. In one sentence each: what does WHERE filter, and what does HAVING filter? Answer: WHERE filters rows before they are grouped (so it cannot mention an aggregate). HAVING filters groups after GROUP BY (so it can).
  2. Why do values go into SQL through placeholders and never through an f-string? Answer: With a placeholder the SQL text and the value travel separately, so a value can never be read as part of the command. An f-string pastes the value into the command: a quote in the input can change the query (SQL injection), and an honest name like O'Brien breaks it.
  3. orders has 20,302 rows and 739 have no matching customer. How many rows from orders JOIN customers, and how many from orders LEFT JOIN customers? Answer: 19,563 and 20,302. The inner join drops the unmatched rows silently; the left join keeps them with NULL on the customer side.
