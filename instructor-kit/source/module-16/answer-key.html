5.5 · NoSQL with MongoDB: Self-check

Q1
In the sessions collection, utm is absent from direct visits and never set to null. Which query counts exactly the sessions where the field is not there, and would still be right if some documents held utm: null?
A) {"utm": None}
B) {"utm": {"$exists": False}}
C) {"utm": ""}
D) {"utm": {"$size": 0}}
Why: $exists tests whether the field is present at all, which is the precise question.
A is wrong: None matches documents where the field is null and documents where it is missing, so it stops being exact the day a null appears.
C is wrong: That matches only documents whose utm is the empty string. No session has that.
D is wrong: $size is for lists (arrays); utm is an object, and a missing field has no size.
Q2
What does this print?
c = mongomock.MongoClient()["demo"]["notes"]
c.insert_many([{"n": 1, "tags": ["a", "b"]},
               {"n": 2, "tags": ["b"]},
               {"n": 3}])
print(c.count_documents({"tags": "b"}), c.count_documents({"tags": None}))
A) 3 0
B) 2 0
C) 1 1
D) 2 1
Why: A query on a list field matches when any element equals the value, so "b" matches documents 1 and 2. None matches a missing field, so {"tags": None} finds document 3.
A is wrong: Document 3 has no tags at all, so it cannot contain "b".
B is wrong: None in a query also matches documents where the field is missing: that is document 3.
C is wrong: Document 1 counts too: "b" is one of its two tags.
Q3
What does this print?
c = mongomock.MongoClient()["demo"]["sales"]
c.insert_many([{"store": "Bend", "units": 2},
               {"store": "Boise", "units": 5},
               {"store": "Bend", "units": 4}])
rows = c.aggregate([{"$group": {"_id": "$store", "units": {"$sum": "$units"}}},
                    {"$sort": {"units": -1}}])
print([(r["_id"], r["units"]) for r in rows])
[('Bend', 6), ('Boise', 5)]
Why: $group makes one output document per _id value ("$store" means: the value of the field store). {"$sum": "$units"} adds the units: Bend 2 + 4 = 6, Boise 5. $sort with -1 puts the larger total first.
Q4
Which pipeline stage turns every element of a list into its own document, the way explode does in pandas?
A) $unwind
B) $group
C) $project
D) $match
Why: {"$unwind": "$pages"} turned 2,400 sessions into 9,348 page-view documents, each still carrying its session's other fields.
B is wrong: $group goes the other way: many documents in, one per key out.
C is wrong: $project chooses or computes fields; the number of documents stays the same.
D is wrong: $match filters documents; it never splits one.
Q5
What does this print?
c = mongomock.MongoClient()["demo"]["visits"]
c.insert_many([
    {"id": 1, "pages": [{"path": "/cart", "seconds": 10},
                        {"path": "/sale", "seconds": 200}]},
    {"id": 2, "pages": [{"path": "/cart", "seconds": 150}]},
])
loose = {"pages.path": "/cart", "pages.seconds": {"$gte": 100}}
strict = {"pages": {"$elemMatch": {"path": "/cart", "seconds": {"$gte": 100}}}}
print(c.count_documents(loose), c.count_documents(strict))
A) 1 1
B) 2 2
C) 2 1
D) 1 2
Why: Without $elemMatch each condition may be met by a different element: visit 1 has a /cart page and (another) page of 200 seconds, so it matches the loose query. Only visit 2 spent 100 seconds or more on /cart itself.
A is wrong: The loose query also matches visit 1: its two conditions are satisfied by two different pages.
B is wrong: The strict query needs one page that is /cart and at least 100 seconds. Visit 1's /cart page lasted 10.
D is wrong: The counts are the other way round: $elemMatch is the stricter question, so it can never match more.
Q6
What does this print? (The collection holds the three sales documents from Q3.)
rows = list(c.aggregate([{"$group": {"_id": "store", "n": {"$sum": 1}}}]))
print(rows)
A) [{'n': 2, '_id': 'Bend'}, {'n': 1, '_id': 'Boise'}]
B) [{'n': 3, '_id': 'store'}]
C) []
D) A KeyError: there is no field called store
Why: Without the leading $, "store" is just a piece of text, the same for every document, so all three land in one group whose key is the word store.
A is wrong: That is what "_id": "$store" returns. The dollar sign is what says "the value of this field".
C is wrong: Nothing was filtered out; every document went into the single group.
D is wrong: MongoDB raises no error here. A wrong pipeline gives a wrong answer quietly.

6.1 · HTTP with Requests: Self-check

Q7
A script runs r = requests.get(url, timeout=10) and the server answers with status 404. What happens on that line?
A) requests raises HTTPError
B) r is None
C) The call is retried until it succeeds or 10 seconds pass
D) A normal response comes back; r.ok is False and nothing is raised
Why: To requests a 404 is a complete conversation. You get a response whose body is an error page. It only becomes an exception when you call r.raise_for_status().
A is wrong: That happens only when you call raise_for_status().
B is wrong: requests.get returns a Response or raises; it never returns None. (Our own fetch() helper does.)
C is wrong: requests never retries on its own, and timeout is not a retry budget.
Q8
What does this print?
star = "★".encode("utf-8")
print(len("★"), len(star), star.decode("cp1252") == "★")
1 3 False
Why: One character, three bytes in UTF-8. Decoding those three bytes with the wrong table (cp1252) gives three junk characters, not the star, so the comparison is False. That junk is called mojibake.
Q9
You print r.text from a category page and every rating shows â˜… 4.5. What is the first thing to check?
A) r.encoding and the Content-Type header
B) Whether the page needs JavaScript
C) r.status_code, because this means the page is a 404
D) Your timeout value
Why: Three junk characters in place of one symbol means UTF-8 bytes decoded with a Western European table, usually because the server did not name a charset. Set r.encoding = "utf-8" or parse r.content.
B is wrong: JavaScript changes which elements exist, not how a character decodes.
C is wrong: The page arrived; a 404 would give you a different page, not garbled stars.
D is wrong: A timeout raises an exception. It cannot change the characters.
Q10
What does this print? (prepare() only builds the request; nothing is sent.)
params = {"status": "returned", "since": "2025-12-01"}
prepared = requests.Request("GET", "http://127.0.0.1:8000/orders",
                            params=params).prepare()
print(prepared.url)
http://127.0.0.1:8000/orders?status=returned&since=2025-12-01
Why: params becomes the query string: a ?, then name=value pairs joined by &, in the order of the dictionary. Nothing here needs encoding, so the values appear as written.
Q11
A site's robots.txt says Disallow: /staff/ and Crawl-delay: 1. The staff page has no login. What should your collection script do?
A) Fetch the staff page, but only once
B) Fetch it with a browser's User-Agent so the site cannot tell
C) Skip the staff page, and wait at least one second between its other requests
D) Skip robots.txt: it has no legal force
Why: robots.txt is the owner's request to programs. Nothing technical enforces it, which is exactly why honoring both lines is your job.
A is wrong: Once is still going where you were asked not to go.
B is wrong: Disguising your script to get around a site's wishes breaks two ground rules at once.
D is wrong: Whatever its legal weight where you live, ignoring it is the fastest way to get blocked, and it is not how professionals work.
Q12
What does this print?
resp = requests.Response()
resp.status_code = 503
print(resp.ok)
try:
    resp.raise_for_status()
    print("fine")
except requests.exceptions.HTTPError:
    print("caught")
A) True then fine
B) False then caught
C) False then fine
D) True then caught
Why: ok is True only below 400, and raise_for_status() raises HTTPError for every 4xx and 5xx status. 503 is a server-side error, and it is still an error.
A is wrong: 503 is not a success code.
C is wrong: raise_for_status() does not let 5xx through; only 2xx and 3xx pass quietly.
D is wrong: ok and raise_for_status() always agree: both treat 400 and above as failure.

Warm-up and Exit Ticket Answers

Warm-up (retrieval from Session 15)
  1. How does a window function differ from GROUP BY? Answer: A window function computes over a set of related rows and keeps every row; GROUP BY collapses each group to one row.
  2. Three orders tie for first place. What do ROW_NUMBER, RANK and DENSE_RANK give the fourth row? Answer: ROW_NUMBER 4, RANK 4, DENSE_RANK 2. They differ only in how they treat ties.
  3. You want the top 3 products per category. Why does WHERE rn <= 3 fail in the same query, and what is the fix? Answer: WHERE runs before window functions are computed. Number the rows in a CTE, then filter in the outer query.
  4. In EXPLAIN QUERY PLAN, what is the difference between SCAN and SEARCH? Answer: SCAN reads the whole table; SEARCH jumps to the rows it needs through a primary key or an index.
  5. Name one situation in which an index does not help. Answer: Any one of: the column is wrapped in a function, the LIKE pattern starts with a wildcard, most rows match, the table is small.
Exit ticket
  1. In a pymongo query, what does {"utm": None} match, and which operator asks the precise question? Answer: Documents where utm is null and documents where it is missing. $exists tells the two apart.
  2. requests.get() comes back with status 404. What has happened in your program, and which one line makes the failure loud? Answer: Nothing was raised; you hold a normal response whose body is an error page. r.raise_for_status().
  3. Name any two of the six ground rules. Answer: Any two of: obey robots.txt; read the terms; prefer an API; go slowly and identify yourself; never go around a login or block; no personal data.

What wrong answers reveal. Question 1 answered "only null": the learner is carrying SQL's IS NULL over unchanged; show the first predict item. Question 2 answered "it raises an error": they have not yet separated "the conversation failed" from "the server said no"; rerun demo steps 6 and 7. Question 3 left blank: the ground rules were heard, not read; start Session 17 with them on paper.
