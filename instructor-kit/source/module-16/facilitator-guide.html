Session 16: Documents and HTTP

How to teach the session where the data stops being a file someone prepared. The first half finishes Module 5 with a document database: nested website sessions, queried with dictionaries and aggregation pipelines, and flattened back into pandas. The second half opens Module 6 with the conversation every web page and API is built on: one request, one response, and the habits (rules first, identify yourself, timeout, check the status) that make a program a good guest.

How to Use This Guide

  • Session 16 closes Module 5 and opens Module 6. Before the break learners query a document database (Lesson 5.5); after it they make their first HTTP requests (Lesson 6.1). The link between the halves is JSON: the nested documents of the first hour are what web APIs send in the second.
  • Same rhythm as every session: frame (the mental model, said aloud) → live demo (you type, they follow) → guided lab (the kit lab) → start the lesson project. Finishing the projects, the lessons' exercises, quizzes and journals is homework.
  • Every code block below was run for this guide: mongomock 4.3 and pandas 3.0.6 on data/web_sessions.json; requests 2.34.2 against the practice shop and data/mock_api.py. The output shown is real. Where your room will see something different (dates, the local copy of the shop), the guide says so.
  • Type, do not paste. Ask for a prediction before every line whose output is a number. Two of today's most valuable moments are lines that raise no error and print a wrong answer (a misspelled field in 5.5, a 404 page parsed as data in 6.1).
  • Labs live in labs/module-16/: starters for learners, solutions for you. Teal blocks are hands-on; amber blocks are watch-outs.
The risk in Session 16: quiet wrong answers

Both lessons teach tools that are forgiving in the same dangerous way. A collection accepts a query on a field nobody has and answers 0. requests accepts a 404 and hands you an error page to parse. Learners who have spent five lessons being corrected by SQL's error messages will trust the zero. Say the rule early and repeat it in both halves: "Be suspicious of zero. Look at one real document, or one real response, before you believe a count."

Warm-up

0:00

Warm-up: Retrieval from Session 15

10 min

Five questions on the projector, answered on paper with notes closed (4 minutes), then answers aloud (3 minutes). Retrieval practice works because it is effortful: do not let it turn into a re-teach. Anything more than half the room misses goes on the board as a note for the break.

  1. How does a window function differ from GROUP BY? Answer: A window function computes over a set of related rows and keeps every row; GROUP BY collapses each group to one row.
  2. Three orders tie for first place. What do ROW_NUMBER, RANK and DENSE_RANK give the fourth row? Answer: ROW_NUMBER 4, RANK 4, DENSE_RANK 2. They differ only in how they treat ties.
  3. You want the top 3 products per category. Why does WHERE rn <= 3 fail in the same query, and what is the fix? Answer: WHERE runs before window functions are computed. Number the rows in a CTE, then filter in the outer query.
  4. In EXPLAIN QUERY PLAN, what is the difference between SCAN and SEARCH? Answer: SCAN reads the whole table; SEARCH jumps to the rows it needs through a primary key or an index.
  5. Name one situation in which an index does not help. Answer: Any one of: the column is wrapped in a function, the LIKE pattern starts with a wildcard, most rows match, the table is small.

Homework check (3 minutes). Lesson 5.4 asked everyone to open data/web_sessions.json in a text editor and decide which parts would be awkward to store in one flat table. Take two answers (the list of pages; the cart's items; the utm block that is sometimes missing). That is the bridge: "Today that file stops being awkward." Ask who finished the 5.4 tuning report; note names of anyone who did not start it and check in at the break.

NoSQL with MongoDB

70 min
Objectives (from the lesson)

  • Create indexes on a collection and flatten nested results into a tidy DataFrame

Mental model to say

"A relational database is a set of ledgers. Each ledger has fixed columns, every entry fills the same columns, and the facts about one website visit are spread over several ledgers that point at each other by number. A document database is a filing cabinet of folders. Each folder holds everything about one thing, in whatever shape that thing has: one visit's pages, cart and all. Pull one folder and you have the whole story, with no assembly. And two folders need not contain the same sheets."

Put the lesson's comparison table on the projector and read it as a translation exercise: table → collection, row → document, column → field, primary key → _id, a join to a child table → an embedded list. Then the honest caveat, in one sentence: "Neither is better. Orders, customers and products point at each other constantly, so they live in pinecrest.db. Web sessions are self-contained, nested and irregular, so they suit documents."

One sentence on tooling, so nobody goes looking for a server: "We use mongomock, which imitates MongoDB inside Python. Every line you write is real pymongo code; only the line that connects would change."

Three mistakes to expect
  • A misspelled field or a value in the wrong case returns 0, and they report the 0. {"device.typ": "mobile"} and {"device.type": "Mobile"} both count nothing. Coach: "What does one real document look like? Run coll.find_one({}, {"_id": 0, "device": 1}). Now which values exist? coll.distinct("device.type")." Do not point at the typo; let the document show it.
  • The dollar sign in the wrong place. In a query or $match the field name is the key, with no dollar: {"device.type": "mobile"}. Inside $group, $addFields or $project a field's value is written "$device.type". Learners write "_id": "device.type" and get one group of 2,400. Coach: "How many groups did you expect? How many did you get? What is the _id of the one you got?"
  • Two list conditions without $elemMatch. In the lab the loose query counts 218 and the strict one 81. Learners who skip the strict version report 218 for "a minute or more on the sale page". Coach: "Read your query aloud as a sentence. Does it say the minute was spent on /sale, or on some page?"

Also common: list(cursor) twice (the second is empty: a cursor reads once), and update_one(query, {"reviewed": True}) without $set (ValueError: update only works with $ operators, which is a kindness).

Ground rules: the 2-minute opener for every Module 6 session

Before any fetching code, put these six on the projector and read them aloud, one learner per rule. Say why first: "A program can do in a minute what would take a person a week. A website is somebody's property, runs on somebody's bill, and often holds information about real people."

  1. Read robots.txt and obey it. It is the owner's published request to programs: where they may go and how fast.
  2. Read the terms of use. If they forbid automated collection, the answer is no, however easy the code would be.
  3. Prefer an API or a download when one exists. It is the front door.
  4. Go slowly and say who you are. Pause between requests; send a User-Agent with a way to contact you.
  5. Never go around a login, a paywall or a block. If you are asked to stop, stop.
  6. Do not collect personal data. Names, emails, profiles and photos of real people are protected by law in many places.

Then the reassurance: "Every request in this module goes to the practice shop or to the practice API on your own computer. You have the owner's permission, nothing on them is real, and you cannot break anything. We practice the polite habits here so they are automatic everywhere else." This is not legal advice, and the lesson says so; if someone asks "is scraping legal?", the lesson's FAQ has the careful answer.

Mental model to say

"Think of the counter at a deli. You hand over a slip: what you want, plus a few notes about yourself. A moment later a tray comes back. On top is a ticket with a number that says how it went: order filled, we are out of that, you may not order that, the kitchen is on fire. Under the ticket is the food, if there is any. That is the whole of HTTP. The slip is a request, the tray is a response. The server never calls you; it only answers. And it does not remember your last order unless you remind it."

Draw the three-part shape twice on the board, side by side: first line (method and URL | status code), headers (who is asking | what the answer is), body (usually empty for GET | the page or the JSON). Then the status ranges as "whose move is it": 2xx use it, 3xx nothing to do, 4xx fix your request, 5xx wait and try later.

  13. One function that does it right. Say: "Four habits: say who you are, set a timeout, check the status, expect failure. Typing all four on every call is how they get skipped, so they go in one function. Specific exceptions first, the general one last." Type it together; this is the function Session 17 builds on. 
    def fetch(url, **kwargs):
    """GET a URL politely. Return the response, or None after saying why."""
    kwargs.setdefault("headers", HEADERS)
    kwargs.setdefault("timeout", 10)
    try:
        resp = requests.get(url, **kwargs)
        resp.raise_for_status()
    except requests.exceptions.Timeout:
        print(f"TIMEOUT   {url}")
    except requests.exceptions.HTTPError as err:
        print(f"HTTP {err.response.status_code}  {url}")
    except requests.exceptions.RequestException as err:
        print(f"FAILED    {url} ({type(err).__name__})")
    else:
        return resp
    return None

print(fetch(urljoin(BASE_URL, "category-tents.html")))
print(fetch(urljoin(BASE_URL, "category-golf.html")))
print(fetch(f"{API}/slow", params={"seconds": 3}, timeout=1))

  14. A session, a pause, and the raw bytes on disk. Say: "A Session keeps the connection open and remembers the headers. It does NOT remember a timeout. time.sleep(1) is the crawl delay we read at the start. And we save resp.content, the bytes, so every parsing experiment next session runs without a new request." 
    import time
from pathlib import Path

raw = Path("raw")
raw.mkdir(exist_ok=True)

with requests.Session() as session:
    session.headers.update(HEADERS)
    for name in ["category-tents.html", "category-packs.html"]:
        resp = session.get(urljoin(BASE_URL, name), timeout=10)
        resp.raise_for_status()
        (raw / name).write_bytes(resp.content)
        print(name, resp.status_code, len(resp.content), "bytes saved")
        time.sleep(1)

print(sorted(p.name for p in raw.iterdir()))

Three mistakes to expect
  • Parsing an error page as if it were data. A loop over page-12.html to page-15.html reports 20, 2, 0, 0 products and nobody notices that the zeros are 404s. Coach: "What was the status of that response? Where in your loop would you find out?" The fix is one line after every get.
  • No timeout, or ConnectionError because the API is not running. A cell that says "running" for a minute has a call with no timeout=. A long red message ending in Connection refused means the second terminal was closed. Coach: "Is the API's terminal still open? What does http://127.0.0.1:8000/health show in your browser?"
  • Building the query string by hand, or calling .json() on HTML. f"{API}/products?category=Camp Kitchen" breaks on the space; r.json() on a page gives JSONDecodeError: Expecting value: line 1 column 1 (char 0). Coach: "Print r.url. Print r.headers["Content-Type"]. Print r.text[:200]. What did you really receive?"

Also common: leaving off https:// (MissingSchema), and on the offline copy, stars that print as â˜… (set r.encoding = "utf-8").
