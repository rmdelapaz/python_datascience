Instructor Kit · Facilitator Guide

Session 1: Toolkit and First Arrays

How to teach the first session of Python Data Science. Welcome a room of people who can already write Python functions, loops and small programs; prove that every machine has a working environment and the course data; find out what they remember; then get real work out of the toolkit (a first look at 20,302 orders) and meet the structure everything else in the course is built on, the NumPy array. Learners leave having loaded real files, read three tracebacks from the bottom, measured for themselves why an array beats a list for numbers, and been surprised, once and safely, by a view.

2 lessons 3 hrs session Lessons 0.1–1.1 Session 1 of 21

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's skills) → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Type, do not paste. Every code block in a demo script below was run to produce the output printed under it. Type it live, ask for a prediction before you run it, and read errors from the last line up, out loud.
  • The lessons are the reference. Keep getting_started.html and numpy_arrays_vs_lists.html open in browser tabs for the diagrams (the setup map, the list-versus-array memory picture, the view and copy picture). Labs live in labs/module-01/: _starter.py files are handouts, _solution.py files are yours.
  • Session 1 is different in one way: it opens with 30 minutes of welcome, environment check and diagnostic instead of the usual 10-minute retrieval warm-up. Lesson 0.1's installation steps are done before the session from the setup guide; the room spends its 0.1 time using the toolkit, not installing it.
  • Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes (0.1, 1.1) match the course site.
The #1 risk of Session 1: installation eats the session

Lesson 0.1 is an install lesson, and installs go wrong in ways that are different on every laptop. If you let the room install together on venue Wi-Fi, you will still be fixing machines at the break and Lesson 1.1 will not happen. Three things prevent it. Before: send the setup guide a week ahead and ask every learner to reply with the last line of check_environment.py; chase the ones who do not reply. In the room: the check gets 12 minutes and no more; a machine that is not ready gets a partner, not your attention. After: the NOT READY output is a numbered list the learner can follow at home, and you check it again at the start of Session 2. The second risk is quieter: a learner whose notebook kernel is not the course environment, who gets through today on an old pandas and then sees different output from the lesson pages for weeks. The version lines in the check are there to catch exactly that.

Diagnostic answers and how to read the tally

Answers: D1 A) ['Sat', 'Sun'] ['Tue', 'Wed']; D2 C) [1, 2, 3, 4] [1, 2, 3]; D3 B) 3 2; D4 D) 54.0 55.0; D5 A) 2 434.9; D6 B) 5962.05962.0.

  • D1 (slicing) and D2 (names and copies) feed straight into Lesson 1.1 today. If a third of the room misses D2, slow down at the views step of the 1.1 demo and connect it explicitly: "b = a gave two names for one list; an array slice does the same thing for part of an array."
  • D3 (dictionaries) and D5 (comprehensions) are the loop-and-count habits that NumPy and pandas replace. Misses here are not urgent: say so.
  • D4 (functions, defaults, return) matters every time a library call takes keyword arguments. Two or more misses: narrate the arguments of read_csv and genfromtxt out loud in the demos ("skip_header=1: a keyword argument, like rate=0.10").
  • D6 (text from files) predicts trouble with dtypes. Misses here: make a point of printing .dtype in every demo step.
  • Anyone with three or more wrong: not a problem to announce. Pair them with a strong neighbor today, and at the wrap-up hand them labs/module-01/l0_1-orientation/diagnostic_starter.py as extra homework: six small functions with a checker, one per skill (diagnostic_solution.py is your reference). Watch-outs
  • Do not debug one machine in front of the room. Two minutes per machine, then pair them and move on. The trap table in Before the Session covers nearly everything you will see.
  • Mixed backgrounds. Some learners finished Intermediate Python last week; some learned Python at work years ago. The diagnostic is for them as much as for you.
  • "I already use pandas." Welcome them and give them a job: helper during the environment check, and the stretch tasks in each lab. Ask them to let Module 1 build the array model before reaching for DataFrame shortcuts.
  • Versions. The lessons print output from Python 3.12, NumPy 2.5, pandas 3.0. A learner on older versions will see different output (pandas 3 changed how text columns and copies behave). The check prints every version: compare there first.

Three mistakes to expect, and how to coach each
  • The kernel or the terminal is not the course environment. Symptom: ModuleNotFoundError: No module named 'pandas', or a pandas version that starts with 2. Coach with a question, not a fix: "What does your prompt start with?" and, in a notebook, "Which kernel does the top-right corner name?" Then have them run import sys; print(sys.executable): the path should contain .venv.
  • Python is working in a different folder. Symptom: FileNotFoundError for a file they can see in the file browser, usually because JupyterLab was started from the home folder or the zip was extracted into pinecrest-data/data. Coach: "Ask Python where it is: print(Path.cwd()). Is there a data folder inside that folder?" Do not let them paste an absolute path: it works today and breaks the lesson code tomorrow.
  • Cells run out of order, or a name that is almost right. Symptom: NameError for a variable that is plainly on the screen, or KeyError: 'Status'. Coach: "Read me the last line." Then: "When did the cell that creates it last run?" (Restart and run all.) For a KeyError: "Print orders.columns and copy the name." Praise reading the error before asking for help; that habit is objective five.

Arrays vs Lists

75 min
Objectives (from the lesson page)
  • Explain how a NumPy array stores numbers differently from a Python list, and why that makes it smaller and faster
  • Create arrays from lists, from scratch, and from a CSV file, and read their dtype, shape, ndim and size
  • Select elements, rows and columns with indexing and slicing in one and two dimensions
  • Predict whether an operation gives you a view or a copy, and make a copy when you need one
  • Measure memory and speed yourself and choose between a list and an array for a task

Mental model to say

Say: "A list is a public parking lot. Motorcycles, sedans and delivery trucks all park there, each in its own space, and the attendant keeps a clipboard saying which vehicle is where. An array is the starting grid of a race: every car the same class, bumper to bumper in numbered positions. Nobody needs a clipboard, and because the grid is uniform the whole field can move as one."

Turn the picture into the three rules you will repeat all session, and write them on the board: one type (the dtype), fixed size (arrays do not grow), whole-array operations (no loop). Add a fourth line under them for the second half: a slice is a window, not a photocopy.

Why it matters, in one breath: "pandas stores every column as an array. Matplotlib plots arrays. SciPy computes on arrays. Understand this one container and the rest of the course stops looking like magic spells."

Three mistakes to expect, and how to coach each
  • Expecting a slice to be a copy. Symptom: "my original numbers changed and I never touched them." There is no error message, which is what makes it hard. Coach: "Run np.shares_memory(original, piece). What does True mean?" Then: "Where should the .copy() go?" In the lab this is the whole of Lab B, so let pairs find it before you explain it again.
  • Rows and columns the wrong way round. Symptom: week2[1] when they want Bend's column (it gives Tuesday's row), or IndexError: index 5 is out of bounds for axis 1 with size 4. Coach: "Say it out loud: rows, comma, columns. Print .shape. Which number is the stores?" Have them point at the row and the column on the printed table with a finger before typing.
  • A silent type change. Symptom: 102.9 stored in an integer array comes back as 102; a column that prints with quotes and refuses .mean(); a result of nan. None of these raise an error. Coach: "What does .dtype say?" and for nan: "What does np.isnan(x).sum() say?" The habit to build is asking the array before asking the instructor.

Checks for understanding

Ask these out loud during the demo and the lab (cold-call gently, or think-pair-share):

  1. An array of one million int64 values: how many bytes of data? Answer: 8,000,000. Eight bytes each, and nothing else per element.
  2. sales has shape (3, 4): days by stores. What is the shape of sales[:, 1], and what does it hold? Answer: (3,): one store's value on each of the three days.
  3. I slice first = revenue[:28] and set first[0] = 0. What happened to revenue? Answer: Its first value is now 0 too: a slice is a view. revenue[:28].copy() would have protected it.
  4. You are reading values one at a time and do not know how many are coming. List or array? Answer: Collect in a list, convert once with np.array(the_list), compute on the array.
  5. The mean of a column prints nan. What do you check, and what do you use instead? Answer: np.isnan(x).sum() to count the missing values, then np.nanmean(x).
