2.5 · Merging and Joining: self-check

Q1
What does this print (the lengths of an inner, a left and an outer merge)?
a = pd.DataFrame({"k": [1, 2, 3], "x": ["p", "q", "r"]})
b = pd.DataFrame({"k": [2, 3, 3, 4], "y": [10, 20, 30, 40]})
print(len(a.merge(b, on="k")), len(a.merge(b, on="k", how="left")),
      len(a.merge(b, on="k", how="outer")))
A) 2 3 4
B) 3 3 5
C) 3 4 5
D) 3 4 4
Why: Key 2 matches once and key 3 matches twice: 3 rows in the inner join. The left join also keeps key 1 with no partner: 4 rows. The outer join adds key 4 from the right: 5 rows.
A is wrong: That counts matching keys, not rows. Key 3 appears twice on the right, so it produces two rows.
B is wrong: A left join keeps the unmatched left row (key 1), so it has one more row than the inner join.
D is wrong: The outer join also keeps key 4, which exists only in the right table.
Q2
You want to add each customer's loyalty tier to orders without losing any order, and you want the merge to fail loudly if customers ever contains a duplicated id. Which call does both?
A) orders.merge(customers, on="customer_id")
B) orders.merge(customers, on="customer_id", how="left", validate="many_to_one")
C) orders.merge(customers, on="customer_id", how="inner", validate="one_to_one")
D) pd.concat([orders, customers])
Why: how="left" keeps every order, and validate="many_to_one" checks that customer_id is unique in the right-hand table, raising MergeError if it is not.
A is wrong: The default is an inner join: 739 orders with no customer record disappear, and nothing checks for duplicate ids.
C is wrong: An inner join loses the unmatched orders, and one_to_one fails at once because a customer has many orders.
D is wrong: concat stacks the two tables on top of each other; it does not match rows by key.
Q3
What does this print?
o = pd.DataFrame({"order": [1, 2], "total": [100, 50]})
i = pd.DataFrame({"order": [1, 1, 1, 2], "sku": ["a", "b", "c", "d"]})
m = o.merge(i, on="order")
print(m["total"].sum(), m.drop_duplicates("order")["total"].sum())
350 150
Why: The merged table has one row per line, so order 1's total of 100 appears three times: 100 + 100 + 100 + 50 = 350. Going back to one row per order before summing gives the true 150.
Q4
orders.merge(customers, on="customer_id", how="outer", indicator=True) shows 739 rows marked left_only. What are they?
A) Orders whose customer_id has no row in customers
B) Customers who have never placed an order
C) Orders that matched more than one customer
D) Duplicate orders that the merge removed
Why: left_only means the key was found only in the left table, the one before .merge: orders with no customer record (the closed accounts).
B is wrong: Those are the right_only rows: keys found only in customers (1,058 of them).
C is wrong: Rows that match are marked both, however many partners they have.
D is wrong: A merge never removes duplicates, and the indicator does not report them.
Q5
What does this print?
a = pd.DataFrame({"store": ["Boise"], "rev": [100]})
b = pd.DataFrame({"store": ["Bend"], "rev": [80], "visitors": [300]})
c = pd.concat([a, b], ignore_index=True)
print(c.shape, c["visitors"].isna().sum())
(2, 3) 1
Why: concat stacks the rows and matches columns by name. The first table has no visitors column, so its row gets NaN there: 2 rows, 3 columns, 1 missing value.
Q6
daily has the columns date and store; weather has date and city (the same four place names). Each has one row per place per day. Which call attaches the weather to every sales row?
A) daily.merge(weather, on=["date", "store"])
B) daily.merge(weather, on="date", how="left")
C) pd.concat([daily, weather], ignore_index=True)
D) daily.merge(weather, left_on=["date", "store"], right_on=["date", "city"], how="left", validate="one_to_one")
Why: The key is the pair (date, place), and the place column has a different name in each table, so the key columns are named for each side with left_on and right_on.
A is wrong: on= needs the same names in both tables; weather has no store column, so this raises KeyError: 'store'.
B is wrong: Matching on the date alone pairs every store's sales with all four cities' weather: four times the rows.
C is wrong: concat stacks the tables into one long table with half-empty columns; it does not match rows.

2.5 · Predict, then run

P1
An outer join with an indicator.
left = pd.DataFrame({"k": [1, 2, 2], "a": ["x", "y", "z"]})
right = pd.DataFrame({"k": [2, 2, 3], "b": [10, 20, 30]})
m = left.merge(right, on="k", how="outer", indicator=True)
print(len(m), (m["_merge"] == "both").sum(), (m["_merge"] == "left_only").sum())
6 4 1
Why: Key 2 appears twice on each side, so it makes 2 × 2 = 4 rows marked both: a many-to-many match. Key 1 exists only on the left (1 row) and key 3 only on the right (1 row). 4 + 1 + 1 = 6.
P2
Missing keys.
a = pd.DataFrame({"k": [1.0, np.nan], "a": ["x", "y"]})
b = pd.DataFrame({"k": [np.nan, np.nan], "b": ["p", "q"]})
print(len(a.merge(b, on="k")), len(a.merge(b, on="k", how="left")))
2 3
Why: In a pandas merge a missing key matches every other missing key (unlike SQL). The one left row with NaN matches both right rows: 2 rows in the inner join. The left join adds the unmatched key 1: 3 rows. Remove or fill missing keys before merging on a column that has them.
P3
An average after a merge.
o = pd.DataFrame({"order": [1, 2], "total": [300, 100]})
i = pd.DataFrame({"order": [1, 1, 1, 2], "qty": [1, 1, 1, 1]})
print(o["total"].mean(), o.merge(i, on="order")["total"].mean())
200.0 250.0
Why: The two orders average 200. After the merge order 1 appears three times (once per line), so the mean becomes (300 + 300 + 300 + 100) / 4 = 250. Orders with more lines are counted more often. Compute order-level statistics on the orders table.

2.5 · The lesson page's Quick Quiz

These are the five questions at the end of the lesson page (three options each), with the lesson's own explanation.

2.5 Q1
What does this print (the lengths of an inner, a left and an outer merge)?
ql = pd.DataFrame({"k": [1, 2, 2, 3], "a": ["w", "x", "y", "z"]})
qr = pd.DataFrame({"k": [2, 2, 4], "b": ["p", "q", "r"]})
print(len(ql.merge(qr, on="k")), len(ql.merge(qr, on="k", how="left")), len(ql.merge(qr, on="k", how="outer")))
A) 2 4 5
B) 4 4 5
C) 4 6 7
Why: Key 2 is repeated on both sides, so it makes 2 x 2 = 4 rows: that is the inner join. A left join adds the unmatched left keys 1 and 3 for 6. An outer join also adds right key 4 for 7.
2.5 Q2
You merge orders (20,302 rows) with customers using the default settings and get 19,563 rows. What happened?
A) The default inner join dropped 739 orders whose customer has no row in customers
B) pandas removed 739 duplicate orders during the merge
C) 739 customers had no orders, so they were left out
Why: The default is an inner join, which keeps only keys present in both tables. 739 orders have a customer_id with no row in customers, so they were dropped without any message.
2.5 Q3
After orders.merge(items, on="order_id"), the sum of order_total is $11.0 million, though the orders table sums to $4.0 million. Why?
A) Some orders had no matching item lines
B) Each order's total is repeated on every one of its item lines, so it is counted several times
C) The item lines include revenue that the orders table left out
Why: The merge is one-to-many: each order row is repeated once per item line, and its order_total with it. Summing the repeated column counts an order with three lines three times.
2.5 Q4
What does validate="many_to_one" check in orders.merge(customers, on="customer_id", validate="many_to_one")?
A) That every order finds a matching customer
B) That customer_id is unique in orders
C) That customer_id is unique in customers
Why: many_to_one allows repeated keys on the left and requires each key to appear at most once on the right. If customers had a duplicated id the merge would raise a MergeError instead of silently duplicating orders.
2.5 Q5
You have twelve monthly files with identical columns and want one table of all their rows. Which tool fits?
A) pd.concat(list_of_tables, ignore_index=True)
B) Eleven calls to merge on the date column
C) pd.merge_asof on the date column
Why: concat stacks tables on top of each other, matching columns by name. Collect the twelve DataFrames in a list and call it once, with ignore_index=True to renumber the rows.

2.6 · Pivot Tables and Reshaping: self-check

Q7
What does this print?
t = pd.DataFrame({"store": ["a", "a", "b"], "year": [2024, 2024, 2025], "amt": [10, 30, 5]})
p = t.pivot_table(index="store", columns="year", values="amt")
print(p.loc["a", 2024], p.shape)
A) 20.0 (2, 2)
B) 40 (2, 2)
C) 20.0 (3, 2)
D) A ValueError: Index contains duplicate entries
Why: No aggfunc was given, so the cells hold the mean: store a in 2024 is the mean of 10 and 30. Two stores by two years makes a 2 by 2 grid (two of its cells are empty).
B is wrong: 40 is the sum. The default aggregation of pivot_table is the mean.
C is wrong: The grid has one row per distinct store (2), not one per source row.
D is wrong: That error comes from pivot(), which cannot combine rows. pivot_table() combines them.
Q8
What does this print?
w = pd.DataFrame({"month": ["Jan", "Feb"], "Boise": [5, 6], "Bend": [3, 4], "Online": [1, 2]})
tidy = w.melt(id_vars="month", var_name="store", value_name="rev")
print(tidy.shape, tidy["rev"].sum())
(6, 3) 21
Why: Two rows times three store columns gives six rows. The tidy table has three columns: month, store and rev. Melting moves values without changing them, so they still add up to 21.
Q9
In pd.crosstab(orders["channel"], orders["status"], normalize="index"), the cell in row online, column returned is 0.069. What does it mean?
A) Of all returned orders, 6.9% were online
B) 6.9% of all orders are online orders that were returned
C) Online orders are 6.9% more likely to be returned than store orders
D) Of online orders, 6.9% were returned
Why: normalize="index" divides each cell by its row total, so every row adds up to 1: the cell is a share of the online orders.
A is wrong: That is the column percentage, normalize="columns" (77.9% on the course data).
B is wrong: That is normalize="all": a share of the grand total.
C is wrong: The cell is a share, not a comparison. The comparison is 6.9% against 3.4% for stores.
Q10
A pivot that counts order lines by category and month, with margins=True, shows a grand total of 44,881. The source table has 45,490 rows. What is the most likely explanation?
A) fill_value=0 removed the lines in empty cells
B) margins=True leaves the largest category out of the total
C) 609 lines have a missing category (or month), and rows with a missing key are dropped silently
D) pivot_table removes duplicate rows before counting
Why: A pivot, like a groupby, leaves out rows whose row or column key is missing. On the course data 609 lines use discontinued SKUs that have no category after a left merge. Label them and pivot again.
A is wrong: fill_value only changes how empty cells are displayed; it removes nothing.
B is wrong: Margins are computed from all the rows that reached the pivot.
D is wrong: pivot_table never removes duplicates; it aggregates them.
Q11
What does this print?
idx = pd.MultiIndex.from_product([["a", "b"], [2024, 2025]])
s = pd.Series([1, 2, 3, 4], index=idx)
u = s.unstack()
print(u.shape, u.loc["b", 2024])
(2, 2) 3
Why: unstack() takes the innermost index level (the year) and swings it up into the columns: two rows (a, b) by two columns (2024, 2025). The value for b in 2024 was the third one, 3.
Q12
orders.pivot(index="store", columns="status", values="order_total") raises ValueError: Index contains duplicate entries, cannot reshape. What is the right response?
A) Call orders.drop_duplicates() first, then pivot() again
B) Decide how to combine the rows and use pivot_table(..., aggfunc="sum")
C) Sort the table by store and status, then pivot() again
D) Convert store and status to the category dtype
Why: Thousands of orders share each store and status, and pivot() only rearranges: it cannot put several rows in one cell. pivot_table() with an explicit aggfunc says how to combine them.
A is wrong: The orders are not duplicate rows (each has its own id). And dropping on store and status would throw away almost all of them.
C is wrong: Sorting does not change how many rows land in each cell.
D is wrong: The dtype of the keys is not the problem; the number of rows per cell is.

2.6 · Predict, then run

P1
An empty cell.
t = pd.DataFrame({"pay": ["card", "cash", "card"], "ch": ["web", "shop", "shop"],
                  "n": [1, 1, 1]})
p = t.pivot_table(index="pay", columns="ch", values="n", aggfunc="count")
print(p.shape, p.isna().sum().sum(), p.loc["card", "web"])
(2, 2) 1 1.0
Why: Two payment methods by two channels is a 2 by 2 grid. Nobody paid cash on the web, so that one cell is NaN, and the NaN turns the whole web column into floats: the count for card on the web prints as 1.0. fill_value=0 would make it an honest 0 and keep the counts whole.
P2
Labels after a pivot.
t = pd.DataFrame({"month": ["Jan", "Feb", "Mar", "Apr"], "store": ["a"] * 4,
                  "rev": [1, 2, 3, 4]})
print(t.pivot(index="month", columns="store", values="rev").index.tolist())
['Apr', 'Feb', 'Jan', 'Mar']
Why: Pivot methods sort their row and column labels, and text sorts alphabetically: Apr, Feb, Jan, Mar. No error is raised. Pivot on the month number, or reindex with the labels in calendar order.
P3
A margin of means.
t = pd.DataFrame({"store": ["a", "a", "a", "b"], "amt": [10, 10, 10, 50]})
p = t.pivot_table(index="store", values="amt", aggfunc="mean", margins=True)
print(p["amt"].tolist(), t.groupby("store")["amt"].mean().mean())
[10.0, 50.0, 20.0] 30.0
Why: The store means are 10 and 50. The margin All is the mean of all four rows, (10 + 10 + 10 + 50) / 4 = 20, not the mean of the two store means, 30. Store a has three times as many rows, so it counts three times as much.

2.6 · The lesson page's Quick Quiz

These are the five questions at the end of the lesson page (three options each), with the lesson's own explanation.

2.6 Q1
A colleague writes orders.pivot_table(index="store", columns="channel", values="order_total") and titles the result "Revenue by store and channel". What is wrong?
A) The call fails, because index and columns must be lists
B) The cells are average order values, because the default aggfunc is the mean
C) The cells are counts of orders, because nothing was summed
Why: With no aggfunc, pivot_table uses the mean. The cells are average order values, so calling the table revenue is wrong. Writing aggfunc='sum' gives revenue.
2.6 Q2
What is in the Bend row, 2024 column of the table this code prints?
toy = pd.DataFrame({"store": ["Boise", "Boise", "Bend"],
                    "year": [2024, 2025, 2025],
                    "sales": [10, 20, 30]})
print(toy.pivot_table(index="store", columns="year", values="sales", aggfunc="sum"))
A) NaN, because no row has that store and year
B) 0, because the sum of no rows is zero
C) Nothing: the code raises an error because the grid is incomplete
Why: No row has store Bend and year 2024, so there is nothing to sum and the cell is NaN. Adding fill_value=0 would show 0 instead.
2.6 Q3
df.pivot(index="date", columns="store", values="revenue") raises ValueError: Index contains duplicate entries, cannot reshape. What does that tell you?
A) Some revenue values are missing
B) The date column is text and must be converted first
C) At least one date and store pair appears on more than one row
Why: pivot only rearranges, so each date and store pair may appear once. Duplicates mean either the data has repeated rows to investigate, or you need pivot_table with an aggfunc to combine them.
2.6 Q4
A wide table has 12 rows and the columns Month, Boise, Bend, Flagstaff, Asheville, Online. How many rows does table.melt(id_vars="Month") have?
A) 60
B) 72
C) 12
Why: Month is kept as the identifier and the other 5 columns are stacked, so each of the 12 months appears once per store: 12 x 5 = 60 rows, with columns Month, variable and value.
2.6 Q5
A pivot of average order value by store with margins=True shows store means of 175.10, 172.47, 177.21, 182.39 and 203.20, and an All value of 193.17. The plain average of the five store means is 182.07. Why is All different?
A) It is a rounding error that grows with the number of rows
B) The margin leaves out the rows with missing values, so it uses fewer orders
C) All is the mean of every order, so the store with the most orders counts the most
Why: Margins apply the aggfunc to all the underlying rows. The store with the 203.20 mean has far more orders than the others, so it pulls the overall mean toward itself.

Warm-up Answers

  1. In what order do you repair a damaged table? Answer: Structure (headers, stray rows, duplicates), then text, numbers, dates, and last the missing values.
  2. What does pd.to_numeric(s, errors="coerce") do with the value free, and why is that useful? Answer: It turns it into NaN instead of raising an error, so it works as a detector: values that became NaN but were not empty are the ones to look at.
  3. orders.dropna() kept 2,085 of 20,302 rows. Why, and what should you write? Answer: It drops every row with a gap in any column, and most orders have no promo code. Name the columns that matter: dropna(subset=[...]).
  4. You need each order's total next to its store's average order. Which groupby tool gives one value per original row? Answer: transform (for example orders.groupby("store")["order_total"].transform("mean")).
  5. Grouped by promo_code, the group sizes add up to 2,148, but there are 20,302 orders. What happened? Answer: Rows whose key is missing are dropped by default. dropna=False keeps them as a group.

Exit Ticket Answers

  1. You merge orders (20,302 rows) with customers using the default settings and get 19,563 rows. What happened, and what would you write instead? Answer: The default inner join dropped the 739 orders whose customer_id has no row in customers. Write orders.merge(customers, on="customer_id", how="left", validate="many_to_one") and count the rows.
  2. After orders.merge(items, on="order_id"), the sum of order_total is $11.0 million instead of $4.0 million. Why? Answer: The result has one row per order line, so each order's total is repeated on every one of its lines and counted several times. Sum order-level columns on the orders table (or after drop_duplicates("order_id")).
  3. A count pivot with margins=True has a grand total of 44,881, but the source table has 45,490 rows. What does that tell you, and what do you do? Answer: 609 rows have a missing value in the row or column key and were dropped silently. Find them, give them an honest label (for example fillna("Discontinued")), and pivot again until the corner matches the source.

Common Wrong Answers and What They Reveal

  • Q1 answered 2 3 4. They count keys, not rows: key 3 appears twice on the right, so it makes two rows. Have them write out the rows of the inner join by hand.
  • Q3 answered 150 150. They do not yet see that the merged table repeats order-level values. Ask what one row of m is, then have them print m.
  • Q4 answered B ('customers who have never placed an order'). Left and right are swapped in their head. left_only means the key exists only in the table before .merge: here, orders.
  • Q2 answered A (the default merge). They have the mechanics but not the habit. Ask how many rows that call returns on the course data (19,563) and where the other 739 went.
  • Q7 answered B (40 (2, 2)). The spreadsheet habit: a pivot sums. In pandas the default is the mean.
  • Q8 answered (2, 4) 21 or (6, 2) 21. melt is still fuzzy: each store column becomes rows, and the result has the id column plus two new ones. Melt a three-row table by hand.
  • Q9 answered A ('of all returned orders, 6.9% were online'). Row and column percentages are confused. Ask which total the cell was divided by: with normalize="index", its row.
  • Exit ticket 3 answered 'the margins are wrong'. They trust the source less than the grid. The margin is computed correctly from the rows that reached the pivot; the question is which rows did not.
  • Lab customer_profiles: 3,792 rows after the merge. The default inner join. Ask what the row count should have been, and what how= says.
  • Lab payment_returns: 0.0 in the cash/Online rate cell. fill_value=0 was copied from the count pivot. Ask: zero percent of what?
