Session 6: Merging and Reshaping

How to teach the session where tables are connected and reshaped. First learners bring customers, orders, order lines and products together by their keys, and learn to notice when a merge quietly loses rows or multiplies them. Then they turn long tables into grids a person can read with pivot_table and crosstab, turn grids back into rows with melt, and learn to read a tidy-looking table with suspicion.

The rest of each project, the lessons' exercises, quizzes and journals are homework.
  • The lessons are timed at 95 and 85 minutes for a solo learner; the room has 75 for each. The demo scripts are compressed paths through the lesson pages on the lessons' own tables, so every number on the projector matches the page (pandas 3.0.6).

  • Starters go to learners; every *_solution.py stays with you. debug_merges.py is broken on purpose.
The #1 risk of Session 6: a merge or a pivot that runs and is wrong

Every serious mistake today is silent. A default inner join drops 739 orders. A one-to-many merge turns $4.0 million into $11.0 million. A pivot without aggfunc shows averages under a title that says revenue. A pivot quietly leaves out $34,228 of sales because their category is missing. Two reconciliation habits cover all four, and you should say them until the room says them back: "Count before, count after" for every merge, and "Does the corner match the source?" for every pivot. The second risk is cognitive load in 2.5: do not teach merge_asof in the room. One sentence, and point at the lesson.

Warm-up: Retrieval from Session 5

10 min
Five retrieval questions (no notes, 5 minutes)

Slide 3. Paper only, notebooks closed, then one minute with a neighbor before you take answers.

  1. In what order do you repair a damaged table? Answer: Structure (headers, stray rows, duplicates), then text, numbers, dates, and last the missing values.
  2. What does pd.to_numeric(s, errors="coerce") do with the value free, and why is that useful? Answer: It turns it into NaN instead of raising an error, so it works as a detector: values that became NaN but were not empty are the ones to look at.
  3. orders.dropna() kept 2,085 of 20,302 rows. Why, and what should you write? Answer: It drops every row with a gap in any column, and most orders have no promo code. Name the columns that matter: dropna(subset=[...]).
  4. You need each order's total next to its store's average order. Which groupby tool gives one value per original row? Answer: transform (for example orders.groupby("store")["order_total"].transform("mean")).
  5. Grouped by promo_code, the group sizes add up to 2,148, but there are 20,302 orders. What happened? Answer: Rows whose key is missing are dropped by default. dropna=False keeps them as a group.

Objectives (the lesson's own words)

Mental model to say

Say: "Leave skis for tuning at a Pinecrest store and you get a numbered ticket. The same number is tied to the skis. Nobody writes your name on the skis: the number connects the two. A key is that ticket number, a column that appears in both tables. A merge walks down one table and, for each row, finds the rows in the other table holding the same ticket. Two questions decide everything that follows: what if a ticket has no match, and what if a ticket matches more than once?" Draw the map from the lesson on the board and leave it up: customers →(customer_id)→ orders →(order_id)→ order_items ←(sku)← products. Read each arrow as "one row here can match many rows there". Under it write the habit for the block: "Count before. Count after."

Three mistakes to expect
  • An inner join used as an accidental filter. No error. Symptom: a total that is a few percent short (19,563 rows instead of 20,302), found weeks later or never. Coach: "How many rows did your main table have before the merge? How many after? Which rows went, and why?" The cure is two habits: how="left" when you are adding columns to a main table, and a row count after every merge. Then indicator=True to look at what did not match.
  • Summing or averaging a repeated column after a one-to-many merge. No error. Symptoms: order totals that sum to $11.0 million instead of $4.0 million; an 'average order total' of $242.67 instead of $194.60. Coach: "Finish the sentence: one row of this table is one ___. Is order_total a fact about a line or about an order?" Have them aggregate each table to the level they need before merging, or total only columns that belong to the row's own level.
  • Keys that do not line up. These raise errors, which is the easy kind. ValueError: You are trying to merge on str and int64 columns (convert one side; ignore the hint about pd.concat). KeyError: 'store' (the other table calls it city: left_on / right_on). MergeError: Merge keys are not unique in left dataset (the validate= claim names the wrong side). Coach: "Print the dtype and three values of the key on each side." And one quiet relative: missing keys match each other in pandas, so drop or fill NaN keys before merging on a column that has them.

Mental model to say

Say: "A logbook records one event per line: this order, on this date, at this store, for this amount. It is long and narrow, it grows by adding lines, and it is easy for a program to filter, group and merge. That layout is called long, or tidy. A scoreboard arranges a summary in a grid so a person can compare across a row or down a column at a glance. It is short and wide, and it is what goes into a report. Analysis happens in the logbook. Communication happens on the scoreboard. pivot_table turns a logbook into a scoreboard, and melt turns a scoreboard back into a logbook." Write the four pivot questions on the board: rows? columns? values? how to combine? Learners say all four aloud before they write any pivot today.

  • Forgetting that the default aggregation is the mean. No error. Symptom: a table titled 'Revenue by store' whose cells are around $180. Coach: "Read me your aggfunc. Checks for understanding
  1. Say the four things every pivot table needs. Answer: What each row is (index), what each column is (columns), which number goes in the cells (values), and how many rows are combined into one cell (aggfunc).
  2. What is in the cells if you leave out aggfunc? Answer: The mean. Always write aggfunc=.
  3. When does pivot() work, and when do you need pivot_table()? Answer: pivot() only rearranges and needs at most one row per cell; with several rows per cell you must say how to combine them, which is pivot_table().
  4. How can you tell that a table is wide rather than tidy? Answer: Its column headers are pieces of data (store names, months, years) rather than names of measurements.

Exit ticket (3 questions, on paper or sticky notes, 5 minutes)
  1. You merge orders (20,302 rows) with customers using the default settings and get 19,563 rows. What happened, and what would you write instead? Answer: The default inner join dropped the 739 orders whose customer_id has no row in customers. Write orders.merge(customers, on="customer_id", how="left", validate="many_to_one") and count the rows.
  2. After orders.merge(items, on="order_id"), the sum of order_total is $11.0 million instead of $4.0 million. Why? Answer: The result has one row per order line, so each order's total is repeated on every one of its lines and counted several times. Sum order-level columns on the orders table (or after drop_duplicates("order_id")).
  3. A count pivot with margins=True has a grand total of 44,881, but the source table has 45,490 rows. What does that tell you, and what do you do? Answer: 609 rows have a missing value in the row or column key and were dropped silently. Find them, give them an honest label (for example fillna("Discontinued")), and pivot again until the corner matches the source.
