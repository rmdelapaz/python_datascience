2.9 · Feature Engineering Basics: self-check

Q1
Marketing asks which customers will order again, so one row of the feature table is a customer. Which of these is not a valid column for that table as it stands?
A) Days from the customer's signup to the cutoff date
B) The order_total of each of the customer's orders
C) The number of orders the customer placed before the cutoff
D) The share of the customer's orders that were placed online
Why: A customer has many orders, so "the order total" is many values, not one fact about the customer. Aggregate it first (a sum, a mean, a maximum) and it becomes a customer feature.
A is wrong: One number per customer: a fine feature (tenure).
C is wrong: One number per customer, and it respects the cutoff.
D is wrong: The mean of a True/False column per customer: one number each.
Q2
What does this print?
ages = pd.Series([18, 24, 25, 40])
bands = pd.cut(ages, bins=[17, 24, 34, 120], labels=["18-24", "25-34", "35+"])
print(bands.tolist())
['18-24', '18-24', '25-34', '35+']
Why: By default each bin includes its right edge and excludes its left: (17, 24], (24, 34], (34, 120]. So 24 is still in the first band and 25 starts the second. That is why the first edge is 17, not 18.
Q3
What does this print?
x = pd.Series([0, 10, 20, 30])
print(pd.cut(x, bins=[0, 10, 20]).isna().sum())
A) 0
B) 1
C) 2
D) 4
Why: The bins are (0, 10] and (10, 20]. The value 0 is not in (0, 10] because the left edge is excluded, and 30 is beyond the last edge. Both become NaN, with no warning.
A is wrong: Two values fall outside the bins; cut does not stretch the edges to fit.
B is wrong: 30 is outside, and so is 0: the left edge of the first bin is excluded unless you pass include_lowest=True.
D is wrong: 10 and 20 sit exactly on right edges, which are included.
Q4
customers has 4,850 rows. per_customer, built with orders.groupby("customer_id").agg(...), has 3,942 rows. What does customers.merge(per_customer, on="customer_id") return with the default settings?
A) 4,850 rows, with NaN for customers who never ordered
B) 3,942 rows, one for every customer id in the orders
C) 8,792 rows, every row of both tables
D) 3,792 rows: every customer who never ordered is gone
Why: The default is an inner join, which keeps only ids found in both tables. The 1,058 customers with no orders vanish (and so do the 150 order ids with no account). For a feature table, use how="left" from the table that defines the unit, and check that the row count did not change.
A is wrong: That is what how="left" gives, and it is what you want.
B is wrong: 150 of those ids belong to closed accounts with no row in customers, so they cannot match either.
C is wrong: A merge matches rows; it does not stack the two tables.
Q5
A method needs numbers. You have loyalty_tier (Basic, Silver, Gold) and acquisition_channel (five values with no order). Which encoding is appropriate?
A) Ordered integer codes for the tier; one yes/no column per channel with pd.get_dummies
B) Integer codes 0 to 4 for the channel, in alphabetical order; one yes/no column per tier
C) Integer codes for both, because they take the least space
D) Standardize both columns to mean 0 and standard deviation 1
Why: The tier is ordinal: 0, 1, 2 says Gold is above Silver is above Basic, which is true. The channel is nominal: numbering it would tell a model that one channel is "twice" another, so each channel gets its own yes/no column.
B is wrong: This has it backwards: it invents an order for the channels and throws away the real order of the tiers.
C is wrong: Small is not the goal. Codes on a nominal column state an order that does not exist.
D is wrong: Scaling works on numbers. Text has to be encoded first, and scaling does not fix a made-up order.
Q6
You build features as of the cutoff 2025-07-01 to predict who orders in the following six months. A colleague's n_orders counts all of each customer's orders in the file. What happens?
A) An error: pandas refuses to aggregate rows dated after the cutoff
B) Nothing important: more data makes a better feature
C) The feature looks more predictive than it is, because orders after the cutoff are in both the feature and the target
D) The feature becomes useless, because the extra rows add noise
Why: This is the "rows from the future" leak. Anyone who ordered after the cutoff has a higher count because of it, so the count partly contains the answer. It will look excellent in testing and fail on a real today. Filter to order_date < cutoff before aggregating.
A is wrong: Leaks never raise an error. That is what makes them dangerous.
B is wrong: On a real cutoff date those rows do not exist yet, so the feature cannot be computed as tested.
D is wrong: The opposite: it becomes suspiciously good. "Too good" is the warning sign.

2.9 · Predict, then run: answers

Predict 2.9.1
The same three values, binned twice. What does each line print?
v = pd.Series([10, 20, 30])
edges, names = [0, 10, 20, 30], ["a", "b", "c"]
print(pd.cut(v, bins=edges, labels=names).tolist())
print(pd.cut(v, bins=edges, labels=names, right=False).tolist())
['a', 'b', 'c']
['b', 'c', nan]
Why: By default each bin includes its right edge: 10 is in (0, 10], 20 in (10, 20], 30 in (20, 30]. With right=False each bin includes its left edge instead, so 10 moves to [10, 20), 20 to [20, 30), and 30 is no longer inside any bin: it becomes NaN with no warning.
Predict 2.9.2
Three customers, one of whom never ordered. What are the two lists?
people = pd.DataFrame({"id": [1, 2, 3]})
bought = pd.DataFrame({"id": [1, 1, 3], "total": [10.0, 20.0, 7.0]})
per = bought.groupby("id").agg(n=("total", "count"), avg=("total", "mean"))
t = people.merge(per, on="id", how="left")
t["n"] = t["n"].fillna(0).astype(int)
print(t["n"].tolist(), t["avg"].tolist())
[2, 0, 1] [15.0, nan, 7.0]
Why: The left merge keeps customer 2 with NaN in both new columns. The count is filled with 0, which is a fact. The average is left missing: there is no average of zero orders.
Predict 2.9.3
What are the column names, and what does each column add up to?
d = pd.get_dummies(pd.Series(["web", "store", "web"]), dtype=int)
print(d.columns.tolist(), d.sum().tolist(), d.sum(axis=1).tolist())
['store', 'web'] [1, 2] [1, 1, 1]
Why: One column per category, in alphabetical order: store, then web. Column sums count the rows in each category (1 and 2). Every row has exactly one 1, so each row sums to 1.

3.1 · Line, Scatter and Bar Charts: self-check

Q7
Question: "Do products with more reviews tend to have higher ratings?" Which chart answers it?
A) A line chart of rating against review count
B) A scatter plot: one dot per product, review count against rating
C) A bar chart with one bar per product
D) A histogram of the ratings
Why: Two numeric columns, and the question is whether they move together: one dot per row, nothing joined, because the products have no order.
A is wrong: A line joins points in order and suggests one product leads to the next.
C is wrong: 242 bars compare products one by one; they do not show a relationship between two measures.
D is wrong: A histogram shows one column's distribution. The review counts are not in it.
Q8
What does this print?
fig, ax = plt.subplots()
bars = ax.bar(["a", "b", "a", "b", "a"], [1, 5, 3, 2, 2])
print(len(bars), len(fig.axes))
plt.close(fig)
5 1
Why: ax.bar draws one bar per value it is given and never aggregates: five bars, piled up at two x positions. The figure still has one Axes.
Q9
A tutorial writes plt.title("Revenue"). You are holding the chart in a variable ax. What do you write?
A) ax.set_title("Revenue")
B) ax.title("Revenue")
C) fig.set_title("Revenue")
D) ax.title = "Revenue"
Why: On an Axes the labeling methods start with set_: set_title, set_xlabel, set_ylabel, set_xlim.
B is wrong: ax.title is the title object itself; calling it raises TypeError: 'Text' object is not callable.
C is wrong: A Figure has no set_title; the title of one chart belongs to its Axes.
D is wrong: This replaces the title object with a string and draws nothing.
Q10
A histogram of 20,302 order totals with bins=40 shows almost everything in three bars, on an axis that runs to $5,000. What is the best fix?
A) bins=400, so that the bars are narrower
B) Delete the large orders from the DataFrame before plotting
C) range=(0, 1000), and say in the title how many orders are not shown
D) Switch to a bar chart with one bar per order
Why: A few very large orders stretch the range. range= puts the 40 bins where the orders are, and the title tells the reader what was left out.
A is wrong: The axis still runs to $5,000, with most of it empty.
B is wrong: The bulk orders are real. Removing rows changes the data; choosing a range only changes the view.
D is wrong: 20,302 bars is not a distribution, and ax.bar does not count anything.
Q11
What does this print?
fig, ax = plt.subplots()
counts, edges, patches = ax.hist([1, 2, 2, 3, 3, 3, 9], bins=4, range=(0, 8))
print(counts.tolist(), len(edges))
plt.close(fig)
[1.0, 5.0, 0.0, 0.0] 5
Why: Four bins over 0 to 8 are each 2 wide: 0 to 2, 2 to 4, 4 to 6, 6 to 8. The value 1 is in the first; 2, 2, 3, 3, 3 are in the second. The 9 is outside the range and is silently left out. Four bins have five edges.
Q12
A scatter plot of 2,903 store-days shows a solid blob in the lower left: you cannot tell 5 overlapping dots from 500. Which change fixes it?
A) A larger figsize
B) linewidth=0.8 and linestyle="--"
C) bins=40 and range=(0, 1000)
D) A smaller s and an alpha below 1
Why: This is overplotting. Smaller dots overlap less, and see-through dots make dense regions darker, so density becomes visible.
A is wrong: A bigger figure spreads the same solid dots; the dense region is still a blob.
B is wrong: Those style a line. A scatter has none.

Predict 3.1.3
Three dates given as text, out of order. Where does Matplotlib put them on the x axis?
fig, ax = plt.subplots()

Warm-up Answers

  1. You resample daily revenue to monthly totals. What do you print beside every total? Answer: The count of days with a value. Sums skip NaN silently, so a month with missing days looks like a weak month.
  2. What does wide.asfreq("D") do to a table with dates in the index? Answer: It gives every calendar day a row. Days that had no row appear, filled with NaN, and you then decide what each gap means.
  3. On a gap-free daily Series, how many NaN values does s.rolling(7).mean() have, and where? Answer: Six, at the start. A 7-row window is full for the first time on row 7.
  4. Write a 7-day average of rev that is safe for judging today. Answer: rev.shift(1).rolling(7).mean(). Shift first, so today is not inside its own baseline.
  5. A long table holds four stores stacked in one column. What three things do you do, in order, to get each store's own 7-day average? Answer: Sort (by store, then date), group (by store), window (inside transform). The first rows of each group should come out NaN.

Exit Ticket Answers

  1. Before you build any feature, what is the first thing you decide? Answer: The unit of analysis: what one row of the table represents (a customer, an order, a store-day). Every feature must be one fact about that unit.
  2. State the cutoff rule in one sentence. Answer: For every feature: could I have computed this value on the cutoff date, using only what existed then? If not, it leaks.
  3. Name the chart for each question: (a) how did it change over time, (b) do two numbers move together, (c) which group is bigger, (d) what values are typical and how spread out are they? Answer: (a) line, ax.plot; (b) scatter, ax.scatter; (c) bar, ax.bar or ax.barh, after aggregating; (d) histogram, ax.hist, on the raw rows.

Reading the tickets: for question 1, "load the data" or "choose the features" means the unit of analysis has not landed; start Session 9 by asking what one row is in the nine-panel project. For question 2, accept any wording with "on that date" and "only what existed then". For question 3, the common slip is (c) and (d) swapped: bar and histogram look alike and answer different questions. Those learners should redo self-check Q8 and Q11.
