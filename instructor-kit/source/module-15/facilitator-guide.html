How to Use This Guide

  • Two SQL lessons that look advanced and are not: window functions are the pandas transform, rank, shift, cumsum and rolling that learners already know, and query optimization is careful measuring. Say both of those things early.
  • Same rhythm as every session: Frame → Live demo (you type, they follow) → Guided lab (new practice from the kit) → Start the project. The lesson projects are finished at home.
  • Every code block below was run on the course data. Times in the 5.4 demo come from the author's machine: they are printed so you know the size of the effect, and yours will differ. Plans and row counts will not.
  • Labs live in labs/module-15/: starters for learners, solutions for you. Teal blocks are hands-on, amber blocks are watch-outs.
  • Keep sql_window_functions.html and sql_query_optimization.html open for the train picture, the frame table, the B-tree diagram and the seven-day moving-average chart (shown, not typed).
The #1 risk of Session 15: answers that are wrong in one row, and speed claims from one stopwatch reading

A missing PARTITION BY or the default frame with ties produces a table that is right in almost every row. Teach the three questions (partition, order, frame) until the room says them with you. In 5.4 the risk is the opposite kind: learners will believe a single timing. The kit never asserts a time; it asserts plans and identical results. Hold the room to the same standard.

Known environment traps

Plan wording. SQLite 3.36 and later say SCAN orders; older versions say SCAN TABLE orders. Same meaning. A stale plan after DROP INDEX: Python's sqlite3 caches prepared statements by their text; connect with cached_statements=0 (as the lesson, the demo and the labs do) or open a new connection. index ... already exists when a cell runs twice: use CREATE INDEX IF NOT EXISTS. Windows and OneDrive folders: a working copy inside a synced folder can be locked by the sync client (database is locked, or PermissionError on the copy). Work in a local folder. Timings on laptops in power-saving mode or on shared machines jump around; best-of-N absorbs most of it. Never let a learner conclude from a single number. The shipped database changed: if a learner ran CREATE INDEX on data/pinecrest.db itself, later lessons' plans will differ. Fix: unzip pinecrest-data.zip again (or python data/make_data.py).

Five retrieval questions (Lessons 5.1 and 5.2)
  1. In one sentence each: what does WHERE filter, and what does HAVING filter? Answer: WHERE filters rows before grouping; HAVING filters groups after GROUP BY. (Today adds a third stage: window functions run after both, in the SELECT step.)
  2. orders has 20,302 rows and 739 have no customer row. How many rows from JOIN customers, and from LEFT JOIN customers? Answer: 19,563 and 20,302.
  3. Total revenue came out as $10.3 million instead of $3.7 million after joining order_items. What happened, and what is the rule? Answer: Fan-out: each order's total was repeated once per line, then summed. Sum a column at the level where it lives; aggregate first (a CTE), then join.
  4. Why does WHERE employee_id NOT IN (SELECT manager_id FROM employees) return 0 rows? Answer: The list contains a NULL (the CEO's manager_id), and a comparison with NULL is unknown, so NOT IN is never true. Use NOT EXISTS or filter the NULLs out of the list.
  5. A value travels into SQL through a placeholder. What can a placeholder NOT stand for, and what do you do then? Answer: A table name, a column name or a keyword. Check the name against a fixed list of allowed names in Python, and only then put it in the query text.

Mental model to say

"GROUP BY is the conductor's report: 'car 3 has 48 passengers'. The passengers have become a number. A window function leaves you in your seat and lets you look around. Through the window you can see the rest of your car, your partition; you know who sits in front of you and behind you, the order; and you can choose to look only at the two seats ahead, the frame. You get your answer, and you are still a passenger with a seat."

Draw a train car on the board with three labels: PARTITION BY (which car), ORDER BY (seat order), ROWS BETWEEN (how far you look). Leave it up through the break.

Live demo (you type, they follow): eleven windows on Pinecrest's orders

  1. Setup and a version check (1m). Say: "Read-only again, the same show() helper. Window functions need SQLite 3.25 or later; this line checks."

import pandas as pd

conn = sqlite3.connect("file:data/pinecrest.db?mode=ro", uri=True)

def show(sql, params=()):
    """Run a query and print the result as a table."""
    print(pd.read_sql(sql, conn, params=params).to_string(index=False))

print(sqlite3.sqlite_version_info >= (3, 25, 0))

  2. OVER (PARTITION BY): a group value on every row (3m). Say: "Each order next to its own store's average. Five orders in, five rows out, each carrying a number computed from thousands of other rows." 
    show("""

           ROUND(AVG(order_total) OVER (PARTITION BY store), 1) AS store_avg,
           ROUND(order_total - AVG(order_total) OVER (PARTITION BY store), 2)
               AS vs_avg
    FROM orders
    WHERE status = 'completed'
    ORDER BY order_id
    LIMIT 4
""")

   100003    Online         75.9      203.2 -127.30
   100004    Online        399.8      203.2  196.60

    Write the comparison on the board: GROUP BY store gives 5 rows; OVER (PARTITION BY store) gives 18,762. pandas twin: groupby("store")["order_total"].transform("mean").

  4. Three ways to rank, and what they do with ties (3m). Say: "The two cheapest items in Tents share a price. Predict the three columns for those two rows."

           ROW_NUMBER() OVER (ORDER BY price) AS row_number,
           RANK()       OVER (ORDER BY price) AS rank,
           DENSE_RANK() OVER (ORDER BY price) AS dense_rank

    "RANK is a race: two golds, no silver. DENSE_RANK does not skip. ROW_NUMBER picks arbitrarily among ties unless the ORDER BY breaks them": point at the two footprints, numbered in an order nothing in the query decided. pandas: rank(method="min" / "dense" / "first").

  5. Top N per group: number, wrap, filter (4m). Say: "The two best-selling products in every category. ORDER BY ... LIMIT 2 gives two rows in total, not two per category. The recipe has three steps, and step 2 is not optional." 
    show("""
    WITH product_revenue AS (
        SELECT p.category, p.name,
               ROUND(SUM(i.quantity * i.unit_price), 2) AS revenue
        FROM order_items AS i
        JOIN orders AS o ON o.order_id = i.order_id
        JOIN products AS p ON p.sku = i.sku
        WHERE o.status = 'completed'
        GROUP BY p.sku
    ),
    ranked AS (
        SELECT *,
               ROW_NUMBER() OVER (PARTITION BY category ORDER BY revenue DESC) AS rn
        FROM product_revenue
    )

    FROM ranked
    WHERE rn <= 2

    LIMIT 6
""")

  6. LAG and LEAD: the neighbors (3m). Say: "Monthly revenue is the series for the next three steps. Store the CTE in a Python string so we never retype it." 
    MONTHLY = """
    WITH monthly AS (
        SELECT strftime('%Y-%m', order_date) AS month,
               ROUND(SUM(order_total), 2)    AS revenue
        FROM orders
        WHERE status = 'completed'
        GROUP BY month
    )
"""
show(MONTHLY + """
    SELECT month, revenue,
           LAG(revenue) OVER (ORDER BY month) AS prev_month,
           ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
                 / LAG(revenue) OVER (ORDER BY month), 1) AS pct_change
    FROM monthly
    ORDER BY month
    LIMIT 4
""")
      month   revenue  prev_month  pct_change
2024-01 106287.63         NaN         NaN
2024-02 104687.91   106287.63        -1.5
2024-03 128400.63   104687.91        22.7
2024-04 129716.87   128400.63         1.0

    "January 2024 has nothing before it: NULL, the honest answer." pandas: shift(1) and pct_change(). One difference to say aloud: pandas shifts by position, so you must sort first; SQL takes the order from the OVER.

  7. LAG within a group: days between a customer's orders (2m). Say: "With PARTITION BY, 'previous' means previous within the group. julianday() turns a date into a day count." 
    show("""
    WITH gaps AS (
        SELECT order_date,
               LAG(order_date) OVER (PARTITION BY customer_id
                                     ORDER BY order_date, order_id) AS prev_date
        FROM orders
    )
    SELECT COUNT(*)         AS orders,
           COUNT(prev_date) AS with_earlier,
           ROUND(AVG(julianday(order_date) - julianday(prev_date)), 1) AS avg_days
    FROM gaps
""")
     orders  with_earlier  avg_days
  20302         16360      83.1

    20,302 orders minus 3,942 first orders = 16,360 gaps, averaging about 83 days. "order_id breaks ties when a customer orders twice in one day, so the result is the same every run."

  8. Running total and year to date (3m). Say: "Give an aggregate window an ORDER BY and it covers the partition from the start to the current row: a running total. Partition by year and it restarts each January."

           ROUND(SUM(revenue) OVER (ORDER BY month
             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW), 2) AS running_total,
           ROUND(SUM(revenue) OVER (PARTITION BY substr(month, 1, 4) ORDER BY month
             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW), 2) AS year_to_date

    "I wrote the frame out on purpose. In ten minutes you will see why." pandas: cumsum(), and groupby(year).cumsum() for year to date.

  9. Frames: a moving average, and what the first rows do (3m). Say: "The frame is the part of the partition the function looks at: from here to here. Three months, and a column that counts how many rows the frame really held." 
    show(MONTHLY + """
    SELECT month, revenue,
           ROUND(AVG(revenue) OVER (ORDER BY month
                 ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3,
           COUNT(*) OVER (ORDER BY month
                 ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)     AS rows_in_frame,
           ROUND(AVG(revenue) OVER (ORDER BY month
                 ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING), 2) AS prior_3_avg
    FROM monthly
    ORDER BY month
    LIMIT 4
""")
      month   revenue  moving_avg_3  rows_in_frame  prior_3_avg
2024-01 106287.63     106287.63              1          NaN
2024-02 104687.91     105487.77              2    106287.63
2024-03 128400.63     113125.39              3    105487.77

    Two points. (1) SQL averages whatever part of the frame exists: January's "three-month average" is one month. pandas rolling(3) gives NaN there unless min_periods=1. (2) A frame that ends at 1 PRECEDING never sees the current row: the leak-free feature from Lesson 2.8, shift(1).rolling(3, min_periods=1).

Three mistakes to expect
  • Filtering on a window function in the same query. WHERE ROW_NUMBER() OVER (...) <= 3 raises OperationalError: misuse of window function ROW_NUMBER(), and giving it an alias does not help. Coach with Session 14's running order: "Where do window functions run? After WHERE. So the filter needs another SELECT around it: a CTE."
  • A missing PARTITION BY. LAG over several series without a partition compares one series with the last row of another (demo step 11). No error, one wrong row in the middle of a correct table. Coach: "How many series are in this table? Then what is the partition?"
  • The default frame with ties, and an order that does not decide. A running total ordered by date gives tied rows the same total; ROW_NUMBER over a date with two orders on one day numbers them arbitrarily. Coach: "Is your ORDER BY unique? Add the key as a tiebreaker. Aggregating over an ordered window? Write the ROWS frame." The Silver lab depends on both.

Mental model to say

"A table is a thick reference book whose pages are in the order they were written. To find every mention of 'crampons' you have one strategy: start at page 1 and read to the end. That is a scan. An index is the alphabetical list at the back: each term, then the pages where it appears. Jump to 'crampons', turn straight to those pages. That is a search. The index is extra paper, and somebody has to update it every time a page changes."

Then the method, which matters more than any single index: "SQL says WHAT you want; the planner decides HOW. We will ask it how, change one thing, and measure again. Read the plan, form a guess, change one thing, measure." Write that sentence on the board.

Set expectations about numbers: "On a 3.5 MB database everything is fast. We look at the plan first and the stopwatch second, and every time I print a time I will say: your numbers will differ."

Live demo (you type, they follow): plans, indexes and the stopwatch

A second notebook, session15_tuning.ipynb. The demo creates indexes, so step 1 copies the database to pinecrest_tuning.db first. Nine cells; the marked minutes add up to 30. The times below are from the author's machine; yours will differ and that is the point of best-of-N.

  1. A copy, a plan printer, a stopwatch (3m). Say: "This lesson creates indexes, so it works on a copy. Two helpers: plan() prints the engine's strategy, timed() runs a query many times and keeps the best. And one detail in the connect line, which I will explain in step 7." 
    import os
import shutil
import sqlite3
import time
import pandas as pd

shutil.copy("data/pinecrest.db", "pinecrest_tuning.db")
conn = sqlite3.connect("pinecrest_tuning.db", cached_statements=0)

def plan(sql, params=()):
    """Print the query plan, one step per line."""
    for row in conn.execute("EXPLAIN QUERY PLAN " + sql, params):
        print("   ", row[3])

def timed(sql, param_list, repeat=5):
    """Best time in milliseconds to run the query once per item of param_list."""
    best = float("inf")
    for _ in range(repeat):
        start = time.perf_counter()
        for params in param_list:
            conn.execute(sql, params).fetchall()
        best = min(best, time.perf_counter() - start)
    return best * 1000

    plan() here prints the steps without indentation; the lesson's version indents nested steps.

  2. Reading a plan: SCAN and SEARCH (3m). Say: "EXPLAIN QUERY PLAN returns the strategy instead of running the query. Nothing is read or changed, so it is always safe. Two verbs do nearly all the work."

print("by another column")

print("filter, then sort")

by another column

    SCAN: read every row and test each. SEARCH: jump. TEMP B-TREE: a separate sort. "SCAN is not a dirty word: for a yearly total it is the best plan. It is a problem when you wanted a few rows and paid for all of them."

  3. One index, the plan and the stopwatch (4m). Say: "The classic slow query here: the lines of one order. order_items has 45,490 rows and no index on order_id. Two hundred lookups, before and after."

  4. Joins: the inner loop should be a SEARCH (3m). Say: "A join runs as a nested loop: for each row of the outer table, find the matches in the inner one. The plan lists the outer table first. One customer's history, with one index, then two." 
    HISTORY_SQL = """
    SELECT o.order_id, o.order_date, i.sku, i.quantity
    FROM orders AS o

    WHERE o.customer_id = ?

print("index on order_items(order_id) only:")

plan(HISTORY_SQL, (12673,))

    SCAN o
    SEARCH i USING INDEX idx_order_items_order_id (order_id=?)

    "No scans at all: search for the customer's few orders, then search for each order's lines. This is the plan you want behind a 'show me one customer' page. And notice: the planner chose the outer table, not the order in your FROM clause."

  5. Composite index and the leftmost prefix (4m). Say: "A store manager's report filters on a store and a date range. One index on two columns, in the order a phone book uses: last name, then first name."

    "The index is sorted by order_date, not by strftime('%Y-%m', order_date). Keep the bare column on one side of the comparison." A pattern that starts with % and a column where most rows match (status: 92% completed) are the other two cases; they are in the lesson, as reading.

  7. DROP INDEX and plan again: why cached_statements=0 (2m). Say: "Experiments need undoing. Drop the composite index and ask for the same plan text again." 
    conn.execute("DROP INDEX idx_orders_store_date")

    "Back to SCAN, as it should be. Python's sqlite3 normally caches prepared statements by their text, and a cached one can still carry the plan it was made with while the index existed. That is why this connection was opened with cached_statements=0. Harmless in normal work; confusing in a lesson about plans. A new connection does the same job."

  8. ANALYZE: statistics for the planner (3m). Say: "So far the planner has chosen with no knowledge of the data. ANALYZE measures it. Watch a date-only query on a three-column index."

             "ON orders (store, order_date, order_total)")

    "The statistics told the planner that store has only five values, so five small searches, one per store, beat a scan: a skip-scan, ANY(store)." The sqlite_stat1 table and what indexes cost in file size and insert time are reading; the project measures the size.

  9. Ask for less: aggregate where the data lives (5m). Say: "The cheapest row is the one you never fetch. Item revenue by store, two ways." 
    def pandas_way():
    df = pd.read_sql("SELECT * FROM order_items AS i "
                     "JOIN orders AS o ON o.order_id = i.order_id", conn)
    df = df[df["status"] == "completed"]
    return (df["quantity"] * df["unit_price"]).groupby(df["store"]).sum().round(2)

def sql_way():
    return pd.read_sql("""
        SELECT o.store, ROUND(SUM(i.quantity * i.unit_price), 2) AS revenue
        FROM order_items AS i JOIN orders AS o ON o.order_id = i.order_id
        WHERE o.status = 'completed'
        GROUP BY o.store""", conn).set_index("store")["revenue"]

for func in (pandas_way, sql_way):
    start = time.perf_counter()
    result = func()
    print(f"{func.__name__}: {(time.perf_counter() - start) * 1000:.1f} ms")
print("same numbers:", (pandas_way() - sql_way()).abs().max() < 0.01)

sql_way: 14.0 ms
same numbers: True

    "Same answer; one moved 45,490 rows into Python, the other five." Three habits for the board: name your columns, LIMIT while exploring, one query not a loop of queries. The second lab is about the third.

Three mistakes to expect
  • Assuming the index is used. Creating an index proves nothing; the planner may ignore it (a function on the column, a wildcard at the start, a filter that matches most rows). Coach: "Show me the plan line for the query it was meant for. Which index does it name?" In the lab, the city-only query still scans after the composite index.
  • Trusting one timing. A single before and after can show only the cache warming up. Coach: "How many times did you run it? Which number did you keep?" Both labs time with best-of-several and print "your numbers will differ"; nothing in the kit asserts a time.
  • A stale plan after DROP INDEX, or editing the shipped database. Re-asking the same plan text on a connection that caches statements can show the old plan; the demo and labs connect with cached_statements=0. And an index created on data/pinecrest.db itself changes the file every later lesson expects. Coach: "Which file is your connection open on?" Always a copy.

Exit ticket (3 questions; answers)
  1. orders has 20,302 rows and 5 stores. How many rows from SELECT store, AVG(order_total) FROM orders GROUP BY store, and from SELECT store, AVG(order_total) OVER (PARTITION BY store) FROM orders? Answer: 5 and 20,302. GROUP BY collapses the rows; a window function keeps every row and attaches the group value to it.
  2. Give the three steps of "top N per group". Answer: Number the rows with ROW_NUMBER() OVER (PARTITION BY group ORDER BY measure DESC, tiebreaker); put that in a CTE; filter the CTE with WHERE rn <= N. (WHERE cannot see a window function in the same SELECT.)
  3. You have just created an index. Name two things you check before saying it helped. Answer: Any two of: the plan for the query it was meant for now says SEARCH ... USING INDEX (or COVERING INDEX) instead of SCAN; best-of-several timings before and after; the query returns exactly the same rows; what it costs in file size and write speed.
