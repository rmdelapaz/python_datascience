5.3 · SQL Window Functions: self-check

Q1
Which pandas line gives the same column as SUM(order_total) OVER (PARTITION BY store), one value on every order row?
A) orders.groupby("store")["order_total"].sum()
B) orders.groupby("store")["order_total"].transform("sum")
C) orders["order_total"].cumsum()
D) orders["order_total"].rolling(5).sum()
Why: transform returns one value per original row, aligned with the rows, exactly like a window function. A window keeps every row; GROUP BY (and .sum() after groupby) collapses them.
A is wrong: That returns five numbers, one per store: the GROUP BY version.
C is wrong: That is a running total over all rows, SUM(...) OVER (ORDER BY ...), with no partition.
D is wrong: That is a moving sum of five rows, unrelated to the store.
Q2
What does this print?
rows = conn.execute("""
    SELECT v, ROW_NUMBER() OVER (ORDER BY v DESC, id),
           RANK() OVER (ORDER BY v DESC), DENSE_RANK() OVER (ORDER BY v DESC)
    FROM (SELECT 1 AS id, 50 AS v UNION ALL SELECT 2, 70
          UNION ALL SELECT 3, 50 UNION ALL SELECT 4, 40)
    ORDER BY v DESC, id
""").fetchall()
print(rows[-1])
(40, 4, 4, 3)
Why: Order: 70, 50, 50, 40. ROW_NUMBER never repeats: 4. RANK gives both 50s the rank 2 and skips 3, so 40 is 4. DENSE_RANK does not skip: 70 is 1, the 50s are 2, 40 is 3.
Q3
SELECT ... ROW_NUMBER() OVER (PARTITION BY category ORDER BY revenue DESC) AS rn FROM ... WHERE rn <= 2 fails. Why, and what is the fix?
A) WHERE runs before window functions are computed; compute rn in a CTE and filter it in the outer query
B) ROW_NUMBER needs a ROWS BETWEEN frame; add one
C) rn is a reserved word; rename it
D) PARTITION BY cannot be combined with ORDER BY; remove the partition
Why: Window functions are computed in the SELECT step, after WHERE. The fix is the recipe: number in a CTE, then filter outside it.
B is wrong: Ranking functions ignore the frame entirely.
C is wrong: rn is an ordinary name; the error says "misuse of aliased window function rn".
D is wrong: PARTITION BY with ORDER BY is exactly how you number rows within groups.
Q4
Which frame averages the three months before the current one, without the current month (no leakage)?
A) ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
B) ROWS BETWEEN 3 PRECEDING AND 1 PRECEDING
C) ROWS BETWEEN 3 PRECEDING AND CURRENT ROW
D) ROWS BETWEEN 1 FOLLOWING AND 3 FOLLOWING
Why: The frame ends one row before the current row, so the current month never sees itself. It is the SQL form of shift(1).rolling(3, min_periods=1).mean().
A is wrong: Three months including the current one: a moving average, not a prior average.
C is wrong: Four rows, including the current one.
D is wrong: The three months AFTER: that looks into the future.
Q5
What does this print? (Two rows share d = 1.)
sql = """SELECT d, x, SUM(x) OVER (ORDER BY d)
         FROM (SELECT 1 AS d, 10 AS x UNION ALL SELECT 1, 20
               UNION ALL SELECT 2, 5)
         ORDER BY d, x"""
print([row[2] for row in conn.execute(sql)])
[30, 30, 35]
Why: The default frame (RANGE ... CURRENT ROW) includes every row that ties with the current one in the window's order, so both d = 1 rows see 10 + 20. With ORDER BY d, x ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW the answer would be [10, 30, 35].
Q6
A SQL column is AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 3 PRECEDING AND CURRENT ROW). A colleague computes df["revenue"].rolling(4).mean(). Where do they disagree?
A) On every row: SQL counts rows, pandas counts days
B) Nowhere: the two are identical
C) Only on the last row, because SQL has no following rows
D) On the first three rows: SQL averages the rows that exist, pandas gives NaN until four rows exist
Why: SQL uses whatever part of the frame exists. pandas rolling(4) needs a full window unless you add min_periods=1, which reproduces the SQL column.
A is wrong: Both count rows here (ROWS in SQL, an integer window in pandas).
B is wrong: They agree from the fourth row on, not before.
C is wrong: The frame looks backward; the last row has a full frame in both.

5.4 · Query Optimization: self-check

Q7
Which plan line means the engine answered from the index alone and never opened the table?
A) SCAN orders
B) SEARCH orders USING INDEX idx_orders_store_date (store=?)
C) SEARCH orders USING COVERING INDEX idx_orders_store_date_total (store=? AND order_date>? AND order_date<?)
D) USE TEMP B-TREE FOR ORDER BY
Why: COVERING means the index holds every column the query needs, so the table is not touched.
A is wrong: A SCAN reads every row of the table.
B is wrong: A plain index search finds the rows in the index, then fetches each one from the table.
D is wrong: That is a sorting step, not a way of finding rows.
Q8
orders has an index on (store, order_date) and no other. Which filter can NOT seek in it?
A) WHERE order_date = '2025-07-04'
B) WHERE store = 'Bend'
C) WHERE store = 'Bend' AND order_date = '2025-07-04'
D) WHERE store = 'Bend' AND order_date >= '2025-07-01'
Why: The leftmost-prefix rule: dates are sorted only within each store, so there is no single place to jump to for a date alone (before ANALYZE, the plan is a SCAN of the index).
B is wrong: The first column of a composite index works on its own.
C is wrong: Both columns, equality on each: the best case.
D is wrong: Equality on the first column and a range on the second: exactly what the index was built for.
Q9
After DROP INDEX, you run the same EXPLAIN QUERY PLAN text again on the same connection and it still names the dropped index. What is going on?
A) The DROP did not happen until you commit
B) SQLite keeps dropped indexes until VACUUM
C) Python's sqlite3 reused its cached prepared statement, planned while the index existed; connect with cached_statements=0 or open a new connection
D) EXPLAIN QUERY PLAN always shows the plan from the first time a query ran
Why: The connection caches prepared statements by their text. Lesson 5.4 opens its connection with cached_statements=0 so that every plan is made afresh, which matters only in a lesson about plans.
A is wrong: DROP INDEX takes effect on your connection at once; committing makes it permanent for others.
B is wrong: VACUUM reclaims space; the index is gone from the schema as soon as it is dropped.
D is wrong: EXPLAIN plans the statement it is given; the stale answer comes from the cache in Python, not from SQLite.
Q10
What does this print?
conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t (a INTEGER, b TEXT)")
conn.execute("CREATE INDEX idx_t_a ON t (a)")
sql = "EXPLAIN QUERY PLAN SELECT * FROM t WHERE a + 0 = 5"
print(conn.execute(sql).fetchone()[3])
SCAN t
Why: The index is sorted by a, not by a + 0. Arithmetic or a function around the column hides it from the index; WHERE a = 5 would give SEARCH t USING INDEX idx_t_a (a=?). The same happens with strftime('%Y', order_date) = '2025': write a range on the bare column.
Q11
A table receives thousands of inserts a minute and has nine indexes, most added "to be safe". What does each extra index cost?
A) Nothing: indexes only affect reads
B) Wrong query results when two indexes cover the same column
C) A full table scan on every SELECT
D) Slower inserts and a larger file, because every index is a sorted copy that must be kept up to date
Why: The lesson measured it: the same 45,490-row load got slower and the file larger with every index added. Index for the queries that are slow and matter; drop the rest.
A is wrong: Every insert, update and delete must update every index.
B is wrong: Results stay correct; only speed and size change.
C is wrong: Indexes never force a scan; the planner may simply not use them.
Q12
Before adding an index a query took 12 ms; after, 4 ms, each measured once. What should you do before reporting "3 times faster"?
A) Nothing: the numbers speak for themselves
B) Run ANALYZE and report the plan instead of times
C) Repeat each measurement several times, take the best, and check the plan changed from SCAN to SEARCH
D) Measure on a different computer
Why: Single timings vary, and the first run is often slowest because later runs find pages already in memory. Best-of-N timings plus a changed plan are evidence; one pair of numbers is not.
A is wrong: One before and one after can show nothing but the cache warming up.
B is wrong: ANALYZE gives the planner statistics; it does not replace measuring.
D is wrong: Another machine gives different absolute numbers and the same noise problem.

Warm-up and Exit Ticket

Warm-up: retrieval from Session 14
  1. In one sentence each: what does WHERE filter, and what does HAVING filter? Answer: WHERE filters rows before grouping; HAVING filters groups after GROUP BY. (Today adds a third stage: window functions run after both, in the SELECT step.)
  2. orders has 20,302 rows and 739 have no customer row. How many rows from JOIN customers, and from LEFT JOIN customers? Answer: 19,563 and 20,302.
  3. Total revenue came out as $10.3 million instead of $3.7 million after joining order_items. What happened, and what is the rule? Answer: Fan-out: each order's total was repeated once per line, then summed. Sum a column at the level where it lives; aggregate first (a CTE), then join.
  4. Why does WHERE employee_id NOT IN (SELECT manager_id FROM employees) return 0 rows? Answer: The list contains a NULL (the CEO's manager_id), and a comparison with NULL is unknown, so NOT IN is never true. Use NOT EXISTS or filter the NULLs out of the list.
  5. A value travels into SQL through a placeholder. What can a placeholder NOT stand for, and what do you do then? Answer: A table name, a column name or a keyword. Check the name against a fixed list of allowed names in Python, and only then put it in the query text.
Exit ticket
  1. orders has 20,302 rows and 5 stores. How many rows from SELECT store, AVG(order_total) FROM orders GROUP BY store, and from SELECT store, AVG(order_total) OVER (PARTITION BY store) FROM orders? Answer: 5 and 20,302. GROUP BY collapses the rows; a window function keeps every row and attaches the group value to it.
  2. Give the three steps of "top N per group". Answer: Number the rows with ROW_NUMBER() OVER (PARTITION BY group ORDER BY measure DESC, tiebreaker); put that in a CTE; filter the CTE with WHERE rn <= N. (WHERE cannot see a window function in the same SELECT.)
  3. You have just created an index. Name two things you check before saying it helped. Answer: Any two of: the plan for the query it was meant for now says SEARCH ... USING INDEX (or COVERING INDEX) instead of SCAN; best-of-several timings before and after; the query returns exactly the same rows; what it costs in file size and write speed.
Common wrong answers and what they reveal
  • "5 rows" for the window query (exit 1, Q1). The learner still reads OVER as a kind of GROUP BY. Show the two results side by side and count.
  • Filtering in the same SELECT (Q3, exit 2). The running order from Session 14 has not absorbed the window step. Add it to the board: FROM, WHERE, GROUP BY, HAVING, windows, SELECT, ORDER BY, LIMIT.
  • [10, 30, 35] for the tie item (Q5). The answer for an explicit ROWS frame, which means the learner has not met the default frame's RANGE behavior. That is the bug they will ship in a running total.
  • "The index makes it faster" with no plan (exit 3, Q12). Belief without evidence. Ask for the plan line and a best-of-N time every time.
  • SEARCH for the arithmetic item (Q10). The learner thinks an index is about a column name, not about sorted values. Ask: "Is the index sorted by a, or by a + 0?"
