Three questions for every window

Partition: which rows belong together? Order: in what order, and is it unique? Frame: how many of those rows does the function look at? Say them before you type the OVER.

Lessons

5.3

SQL Window Functions

Key ideas
  • A window function computes over a set of related rows and keeps every row; GROUP BY collapses them. Any aggregate becomes a window function with OVER (...).
  • OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ...): which rows belong together, in what order, and how many of them to look at. An empty OVER () is one window holding every row.
  • ROW_NUMBER, RANK, DENSE_RANK differ only in ties: 1, 2, 3, 4 · 1, 1, 3, 4 · 1, 1, 2, 3.
  • Top N per group: number the rows in a CTE, then filter outside it. WHERE runs before window functions exist.
  • LAG and LEAD read the previous and next row. Partition by the series, or one series reads another's rows.
  • Running totals and moving averages need an explicit ROWS frame. The default frame treats rows that tie in the order as one.
  • SQL uses partial frames at the start of a series; pandas rolling gives NaN there unless min_periods=1. A frame ending at 1 PRECEDING never sees the current row.
  • End every window's ORDER BY with a unique column so results are the same every run.

Worked example: each store's weakest month, and how weak it was

Store managers ask: "Which month was our worst, and how far below our own average was it?" That is a bottom-1 per group (ROW_NUMBER ordered by revenue ascending) and a group average on the same row. (conn and show are the lesson's read-only connection and helper.)

show("""
    WITH store_month AS (
        SELECT store, strftime('%Y-%m', order_date) AS month,
               ROUND(SUM(order_total), 2) AS revenue
        FROM orders
        WHERE status = 'completed' AND store <> 'Online'
        GROUP BY store, month
    ),
    ranked AS (
        SELECT store, month, revenue,
               ROW_NUMBER() OVER (PARTITION BY store ORDER BY revenue, month) AS rn,
               ROUND(AVG(revenue) OVER (PARTITION BY store), 2) AS store_avg
        FROM store_month
    )
    SELECT store, month AS weakest_month, revenue, store_avg,
           ROUND(100.0 * revenue / store_avg, 1) AS pct_of_avg
    FROM ranked
    WHERE rn = 1
    ORDER BY store
""")
    store weakest_month  revenue  store_avg  pct_of_avg

    Boise       2024-01 11237.18   18474.45        60.8

Reading it. Each store's weakest month ran at 53% to 61% of that store's own monthly average. Three of the four are in January or February; Asheville's is July 2025. Ordering by revenue, month makes the choice unique even if two months tied. The average and the rank sit on the same row because both are windows over the same partition; with GROUP BY you would have needed two queries and a join.

5.4

Query Optimization

Key ideas
  • SQL is declarative: you say what you want; the planner chooses how. EXPLAIN QUERY PLAN shows its choice without running the query.
  • SCAN reads every row; SEARCH jumps. A scan is fine when you need most of the table, and a problem when you wanted a few rows.
  • An index is a sorted copy of some columns plus a pointer to each row. Primary keys are indexed automatically; foreign keys and filter columns usually are not.
  • Joins run as nested loops. The inner step runs once per outer row, so it should be a SEARCH. The planner chooses the table order, not your FROM clause.
  • Composite indexes follow the leftmost-prefix rule: (a, b) serves a, or a and b, but not b alone. Equality columns first, the range or sort last. A covering index answers without opening the table.
  • An index cannot help when the column is inside a function or arithmetic, a pattern starts with %, most rows match, or the table is tiny.
  • ANALYZE gives the planner statistics. Every index costs write speed and file size.
  • Measure properly: best of several runs, plan before and after, identical results. Work on a copy; open it with cached_statements=0 when you drop indexes and re-plan.
  • Ask for less: name your columns, aggregate in SQL, and send one query instead of a loop of queries.

Worked example: should the product lookup get an index?

The shop's search box filters products by brand and price. One composite index, the plan before and after, and a fair timing. NOT INDEXED tells SQLite to ignore indexes, so the "without" timing runs on the same connection. (conn, plan and timed are the lesson's, on the working copy.)

LOOKUP = "SELECT name, price FROM products WHERE brand = ? AND price < ?"
plan(LOOKUP, ("Tallgrass", 50))
conn.execute("CREATE INDEX IF NOT EXISTS idx_products_brand_price "
             "ON products (brand, price)")
conn.commit()
plan(LOOKUP, ("Tallgrass", 50))
print("rows:", len(conn.execute(LOOKUP, ("Tallgrass", 50)).fetchall()), "of",
      conn.execute("SELECT COUNT(*) FROM products").fetchone()[0], "products")
NO_INDEX = "SELECT name, price FROM products NOT INDEXED WHERE brand = ? AND price < ?"
t_without = timed(NO_INDEX, [("Tallgrass", 50)] * 500)
t_with = timed(LOOKUP, [("Tallgrass", 50)] * 500)
print(f"500 lookups: {t_without:.1f} ms without the index, {t_with:.1f} ms with it")
conn.execute("DROP INDEX idx_products_brand_price")
conn.commit()
    SCAN products
    SEARCH products USING INDEX idx_products_brand_price (brand=? AND price<?)
rows: 11 of 242 products
500 lookups: 7.4 ms without the index, 4.5 ms with it

Reading it. The plan changed from SCAN to SEARCH, and 500 lookups got a few milliseconds faster in total (your numbers will differ). With 242 products the whole table fits in a few pages: scanning it is nearly as fast as any index, and a few milliseconds over 500 searches is nothing a shop page would notice. This is the fourth case in "When an Index Does Not Help": a small table. The honest recommendation is no index, and the cell drops it again.

Glossary

Window function: a function computed over a set of rows related to the current row, returning one value per row. Partition: the group of rows a window function looks within (PARTITION BY). Frame: the part of the partition the function actually uses for the current row (ROWS BETWEEN ... AND ...). ROW_NUMBER / RANK / DENSE_RANK: numbering that never repeats / repeats on ties and skips / repeats on ties without skipping. LAG / LEAD: the value from the previous / next row of the window. Running total: a sum from the first row of the partition to the current row. Moving average: an average over a frame that slides with the current row. NTILE: deals ordered rows into a number of nearly equal buckets. Query planner: the part of the engine that chooses how to run a query. EXPLAIN QUERY PLAN: returns the planner's chosen strategy instead of running the query. SCAN / SEARCH: read every row / jump to matching rows using an index or the primary key. Index: a separate sorted structure of one or more columns that lets the engine find rows without reading the whole table. Composite index: an index on several columns, usable from the leftmost column onward. Covering index: an index that contains every column a query needs, so the table is not read. Selectivity: how small a share of the rows a filter keeps; indexes pay off on selective filters. ANALYZE: gathers statistics about tables and indexes for the planner. N+1 problem: running one query for a list and then one more query per item, instead of one combined query.
