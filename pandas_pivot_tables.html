🗂️ Two Shapes for the Same Facts

Pinecrest's operations manager does not want 20,302 order rows. She wants one small grid: stores down the side, years across the top, revenue in the cells. The data you load and the table you present are usually different shapes, and most of this lesson is about moving between them on purpose.

💡 Mental Model: The Logbook and the Scoreboard

A logbook records one event per line: this order, on this date, at this store, for this amount. It is long and narrow, it grows by adding lines, and it is easy for a program to filter, group and merge. This layout is called long or tidy.

A scoreboard arranges a summary in a grid so a person can compare across a row or down a column at a glance. It is short and wide, and it is what goes into a report.

Analysis happens in the logbook. Communication happens on the scoreboard. pivot_table() turns a logbook into a scoreboard, and melt() turns a scoreboard back into a logbook.

🤔 Why This Matters

Reshaping is not decoration. Many questions are only easy in one shape: "which store grew fastest?" wants the two years side by side, while "average revenue per month across all stores" wants one column of numbers to group. Analysts who can flip a table from one shape to the other in a line of code spend their time on the question instead of on the layout.

The answer is correct, and it is still a logbook: ten lines, one per store and year. To compare 2024 with 2025 your eyes have to hop between lines. Now ask for the same numbers as a grid.

table = done.pivot_table(index="store", columns="year", values="order_total", aggfunc="sum")
print(table)

Same ten numbers, arranged so that each store's two years sit next to each other. Every pivot table answers four questions:

ArgumentThe question it answersHere
indexWhat should each row be?"store"
columnsWhat should each column be?"year"
valuesWhich number goes in the cells?"order_total"
aggfuncMany rows land in each cell. How are they combined?"sum"

If you can say those four things in a sentence ("for each store, by year, the sum of order totals"), you can write the pivot. A pivot table is a groupby on the row and column keys whose result has been spread into a grid. Nothing new is being calculated.

The Result Is an Ordinary DataFrame

The grid is not a picture. It has an index (the stores) and columns (the years, as integers), and everything you know about DataFrames works on it.

⚠️ Know What a Row of Your Source Means

orders.csv holds every online order, but only the in-store orders made by signed-in account holders. So the store rows here describe account-holder purchases, not everything that went through the registers. All in-store sales live in daily_sales.csv, where Asheville's change is -5.0%, not -13.3%. A pivot can only summarize the rows it is given. Before you present one, be able to finish the sentence "one row of the source is ...".

🧮 Choosing the Aggregation

Leave aggfunc out and see what you get.

print(done.pivot_table(index="store", columns="year", values="order_total").round(2))

Output

year         2024    2025
store
Asheville  181.13  168.61
Bend       168.08  176.75
Boise      179.48  175.19
Flagstaff  176.76  186.87
Online     201.01  205.09

No error, and a completely different table. The default aggfunc is "mean", so these are average order values, about $168 to $205, not revenue. This default surprises people coming from spreadsheets, where a pivot sums unless told otherwise.

✅ A Habit Worth Having

Always write aggfunc=, even when you want the mean. The next person to read your code (probably you, in a month) should not have to remember a default to know what the numbers are.

Different Functions for Different Columns

A pivot does not need a columns= argument at all. With only index, it is a compact way to write a grouped summary, and a dictionary gives each value column its own function.

                             aggfunc={"order_id": "count", "order_total": "median", "discount_pct": "mean"})

➕ Empty Cells and Totals

How do customers pay at each store? Count orders by payment method and store.

pay = orders.pivot_table(index="payment_method", columns="store", values="order_id", aggfunc="count")
print(pay)

Output

store           Asheville    Bend   Boise  Flagstaff  Online
payment_method
card                835.0  1050.0  1533.0     1021.0  7953.0
cash                293.0   370.0   577.0      374.0     NaN
digital_wallet      181.0   203.0   325.0      209.0  3876.0
gift_card           104.0   102.0   159.0      112.0  1025.0

One cell is NaN: there are no rows at all with cash and Online, because you cannot hand cash to a website. A pivot shows NaN wherever a row-and-column combination never occurs in the data. That one NaN also forced every count to become a float (835.0), since NaN cannot live in an integer column.

For a count, "no rows" honestly means zero, so say so with fill_value. And ask for totals with margins=True.

pay = orders.pivot_table(index="payment_method", columns="store", values="order_id",
                         aggfunc="count", fill_value=0, margins=True, margins_name="Total")
print(pay)

Output

payment_method
card                  835  1050   1533       1021    7953  12392

gift_card             104   102    159        112    1025   1502
Total                1413  1725   2594       1716   12854  20302

The bottom-right corner, 20,302, is the number of rows in orders. That is a free sanity check: if the grand total of a count pivot is not the number of rows you started with, some rows fell out, and you should find out why before reading anything else.

⚠️ Zero and "Nothing There" Are Different Claims

fill_value=0 is right for counts and sums: no orders means 0 orders and $0. It is wrong for averages. An "average cash order online of $0.00" would be a false statement about orders that do not exist. Leave means as NaN, or display them as a dash in the final report.

Totals of Averages Are Not Averages of Totals

Margins use the same aggfunc as the cells, applied to all the underlying rows. Watch what that means for a mean.

aov = done.pivot_table(index="store", columns="year", values="order_total",
                       aggfunc="mean", margins=True).round(2)
print(aov)

print(round(done["order_total"].mean(), 2))                         # every completed order
print(round(done.groupby("store")["order_total"].mean().mean(), 2)) # the five store means, averaged

Output

The All corner is the mean of all 18,762 completed orders, which matches the first check. It is not the average of the five numbers above it. People reading the table often get it wrong, so it is worth a sentence in your report.

🔢 Counting with crosstab

"How many of each combination?" is so common that it has its own function. pd.crosstab() takes two columns (as Series, not as names) and counts.

print(pd.crosstab(orders["channel"], orders["status"], margins=True))

Output

status   cancelled  completed  returned    All
channel
online         360      11604       890  12854
store           37       7158       253   7448
All            397      18762      1143  20302

Raw counts are hard to compare here because online has almost twice as many orders. What you want is each row as percentages of its own total, and normalize does that.

pct = pd.crosstab(orders["channel"], orders["status"], normalize="index") * 100
print(pct.round(1))

Output

status   cancelled  completed  returned
channel
online         2.8       90.3       6.9
store          0.5       96.1       3.4

Now the comparison is fair, and a finding appears: 6.9% of online orders are returned, against 3.4% of store orders. Buying without trying things on has a cost.

normalize=Each cell is a share ofAnswers
"index"its row total (rows sum to 1)"Of online orders, what share were returned?"
"columns"its column total (columns sum to 1)"Of returned orders, what share were online?"
"all"the grand total"What share of all orders are online returns?"

The first two answer different questions, and mixing them up is one of the most common ways to misread a table. Try the other direction.

by_col = pd.crosstab(orders["channel"], orders["status"], normalize="columns") * 100
print(by_col.round(1))

Output

status   cancelled  completed  returned
channel
online        90.7       61.8      77.9
store          9.3       38.2      22.1

"77.9% of returns are online" sounds dramatic, but 63.3% of all orders are online, so most of that number is just size. The row percentages (6.9% against 3.4%) are the ones that compare like with like.

The extra five were never NaN in the file: they are store-days with no row at all (Bend's export failed for three days in August 2024, and Flagstaff's for two in January 2025). In a logbook, a missing line is invisible. On a grid, it is an empty square you can see. 🫠 Wide to Tidy with melt

Data often arrives already wide, because a person built it in a spreadsheet for other people to read. The finance team's 2025 summary is a typical case.

sheet = pd.read_excel("data/sales_2025.xlsx", sheet_name="Monthly Sales", skiprows=3)
print(sheet.head(4))
print(sheet.shape)

It reads nicely. Now try to answer "what was total revenue per month?" or "which store-month was the best?" and you will find yourself writing code that names five columns one by one. The trouble is that Boise, Bend and the rest are not really five different variables. They are five values of one variable, the sales channel, that have been spread across the header.

💡 Tidy Data in Three Rules

A table is tidy when (1) each variable is a column, (2) each observation is a row, and (3) each cell holds one value. Here the variables are month, store and revenue, so a tidy version has exactly those three columns. A quick test: if a column header is a piece of data (a store name, a year, a month) rather than the name of a measurement, the table is wide.

melt() is the tool. You tell it which columns identify a row (id_vars) and it stacks all the others into two new columns: one holding the old header, one holding the value.

tidy = sheet.melt(id_vars="Month", var_name="store", value_name="revenue")
print(tidy.head(4))
print(tidy.shape)

Output

1   Feb  Boise   218456

(60, 3)

back = tidy.pivot(index="Month", columns="store", values="revenue")

Melting Several Measurements

The customer survey is wide in a different way: five satisfaction questions, each in its own column. Melting them lets you treat "which question" as a variable.

survey = pd.read_csv("data/survey.csv")
sat_cols = ["sat_overall", "sat_selection", "sat_price", "sat_staff", "sat_website"]

answers = survey.melt(id_vars=["response_id", "store", "age_group"], value_vars=sat_cols,

print(answers.head(3))

📚 stack and unstack

pivot_table and melt work with column names. unstack() and stack() do the same two moves using the index, which is handy straight after a groupby.

Remember by_store_year, the grouped Series from the start of the lesson? Its index has two levels, store and year. unstack() takes the innermost level and swings it up to become the columns.

print(by_store_year.unstack())

Output

year             2024        2025
store
Asheville   127336.98   110442.39
Bend        136989.18   147586.07
Boise       212140.12   231246.73
Flagstaff   129032.48   171547.87
Online     1077800.75  1280183.70

That is the first pivot table of this lesson, built a different way. groupby([...]).sum().unstack() and pivot_table(..., aggfunc="sum") are two spellings of one idea. To move a different level, name it: by_store_year.unstack("store") puts stores across the top instead.

stack() is the reverse. It takes the column labels and pushes them down into the index, giving a long Series.

pay_counts = orders.pivot_table(index="payment_method", columns="store", values="order_id", aggfunc="count")
long_again = pay_counts.stack()
print(long_again.head(7))
print(len(long_again), long_again.isna().sum())

Output

payment_method  store
card            Asheville     835.0
                Bend         1050.0
                Boise        1533.0
                Flagstaff    1021.0
                Online       7953.0
cash            Asheville     293.0
                Bend          370.0
dtype: float64

⚠️ stack() Keeps Empty Cells

The grid had 4 × 5 = 20 cells, and the stacked Series has 20 rows, including cash / Online as NaN. Older tutorials say stack() silently drops missing values, and show a dropna= argument. In the pandas you installed, stack() keeps every cell and passing dropna= raises an error. If you do not want the empty rows, say so yourself: pay_counts.stack().dropna().

To turn a stacked Series into an ordinary tidy table, name it and reset the index.

print(long_again.dropna().rename("orders").reset_index().head(3))

Output

  payment_method      store  orders
0           card  Asheville   835.0
1           card       Bend  1050.0
2           card      Boise  1533.0

🔍 Reading a Pivot Honestly

A pivot table looks authoritative. It is small, aligned and full of decimals. That is exactly why it deserves suspicion: every cell hides the rows behind it. Two short examples show what can hide.

In the survey grid, the Online row has a staff satisfaction score of 4.07. Put the count next to the mean.

staff = answers[answers["item"] == "sat_staff"].groupby("store")["score"].agg(["mean", "count", "size"])
staff.columns = ["mean", "answered", "asked"]
staff["answered_pct"] = (staff["answered"] / staff["asked"] * 100).round(0)
print(staff.round(2))

Flagstaff  4.02       206    213          97.0
Online     4.07       248    824          30.0

(With a single key and no column split, a plain groupby is the simplest tool.) "count" counts non-missing values, while "size" counts rows, so the difference is the people who skipped the question. Only 30% of online shoppers rated the staff, which makes sense: most of them never met any. The 4.07 is the opinion of the minority who did. It is not wrong, but it should not sit in a report beside the store scores as if it meant the same thing. A mean without its count is half a fact.

A Total That Hides the Story

Does buying footwear make an order more likely to be returned? Every footwear SKU starts with FTW, so you can flag the orders that contain one, then pivot the return rate. The mean of a True/False column is the share that are True.

items = pd.read_csv("data/order_items.csv")
footwear_orders = items.loc[items["sku"].str.startswith("FTW"), "order_id"].unique()

orders["has_footwear"] = orders["order_id"].isin(footwear_orders)
orders["returned"] = orders["status"] == "returned"

rate = orders.pivot_table(index="has_footwear", columns="channel", values="returned",
                          aggfunc="mean", margins=True) * 100
print(rate.round(1))

Output

channel       online  store   All
has_footwear
False            4.8    3.3   4.2
True            14.4    3.8  10.7
All              6.9    3.4   5.6

Read only the All column and you would report "footwear orders are returned 10.7% of the time against 4.2%" and move on. The inside of the table says something much more specific: online, footwear triples the return rate (14.4% against 4.8%). In stores it makes no real difference (3.8% against 3.3%). People can try shoes on in a store. The margin averaged two very different situations into one misleading number.

💡 Six Questions Before You Trust a Pivot

  1. What is one row of the source? An order, an order line, a store-day? Summing the wrong grain double counts.
  2. What is the aggregation? Sum, mean, count, median? Is it written in the code and in the table's title?
  3. How many rows are behind each cell? Pivot the count beside the mean. A cell built from 12 rows is an anecdote.
  4. What do the empty cells mean? Zero, not applicable, or missing data? Do not let fill_value=0 decide for you.
  5. Do the totals reconcile? The grand total of a sum or count should match the source. If it does not, rows were dropped.
  6. Does a total hide a difference inside it? Split by one more variable before you believe a margin.

⚠️ Common Mistakes

Reshaping errors are some of the most informative in pandas once you know how to read them. Each of these has stopped every analyst at least once. None of them means you are doing badly.

1. Using pivot() on Data with Repeats

orders.pivot(index="store", columns="status", values="order_total")

Error

ValueError: Index contains duplicate entries, cannot reshape

What it means: thousands of orders share the same store and status, and pivot() has no idea which one belongs in the cell. Fix: decide how to combine them and use pivot_table(..., aggfunc="sum"). If you believed the pairs were unique, the error has just told you something about your data: df.duplicated(["store", "status"]).sum() counts the repeats.

2. Forgetting That the Default Is the Mean

You saw this in Choosing the Aggregation. There is no error, only a table of averages labeled as if it were revenue. Fix: always write aggfunc=, and sanity-check one cell by hand: done[(done["store"] == "Boise") & (done["year"] == 2025)]["order_total"].sum().

3. Averaging a Text Column

orders.pivot_table(index="store", columns="channel", values="status")

Error

TypeError: dtype 'str' does not support operation 'mean'

What it means: with no aggfunc, pandas tried to take the mean of status, which is text. Fix: you almost certainly wanted to count. Use aggfunc="count", or pd.crosstab(orders["store"], orders["status"]).

4. Reaching into Two-Level Columns with One Label

multi[2025]

Error

KeyError: 2025

What it means: after aggfunc=["sum", "mean", "count"] the top level of the columns holds the function names, and 2025 lives one level down. Fix: go through the top level first, multi["sum"][2025], or use the tuple multi[("sum", 2025)]. Print multi.columns whenever you are unsure what the labels are.

5. Melting Without Saying What Identifies a Row

print(sheet.melt().head(3))
print(sheet.melt().shape)

Output (not what you wanted)

  variable value
0    Month   Jan
1    Month   Feb
2    Month   Mar
(72, 2)

What happened: with no id_vars, every column was melted, including Month. The month names are now mixed into the value column and no row knows which month it belongs to. Fix: sheet.melt(id_vars="Month", ...). The id columns are the ones you want repeated on every row.

6. Months in Alphabetical Order

You met this in Wide to Tidy with melt: Apr, Aug, Dec, Feb. There is no error, and a careless reader sees a "trend" that is only the alphabet. Fix: pivot on the month number (dt.month) and rename at the end, or reindex with the labels in calendar order.

❓ Common Questions at This Stage

If a pivot table is a groupby, which one should I use?

Use groupby when the result feeds more code: it stays long and is easy to filter and merge. Use pivot_table when the result is for reading, when you want totals, or when you need two things side by side to do arithmetic across them (this year against last year). Many analysts group first and call .unstack() at the last moment.

My pivot has two header rows. How do I get plain column names back?

Two header rows means the columns are a MultiIndex. Join the levels into single names: multi.columns = [f"{func}_{year}" for func, year in multi.columns] gives sum_2024, sum_2025, mean_2024 and so on. To turn the row labels back into an ordinary column, use .reset_index().

Is wide data "wrong"?

No. Wide is the right shape for a report, for arithmetic between columns, and for some time series work, as you will see next lesson. Tidy is the right shape for storing, filtering, grouping, merging and most charting. The skill is not preferring one. It is noticing which one you have and converting without fuss.

What does the name next to the column labels mean, like year above store?

When pandas prints a pivot, the top-left corner shows two names: the name of the column labels (year) and, on the line below, the name of the index (store). They are labels for the axes, not data. If the extra name gets in the way when you export, remove it with table.columns.name = None.

📝 Lesson Summary

🎓 Key Takeaways

  • Long (tidy) data has one row per observation and is for analysis; wide data spreads one variable across the header and is for reading
  • pivot_table(index, columns, values, aggfunc) is a groupby spread into a grid; its default aggfunc is the mean, so always write it
  • margins=True adds totals computed from all the underlying rows; fill_value=0 suits counts and sums, not averages
  • pd.crosstab() counts combinations, and normalize turns counts into row, column or overall shares that answer different questions
  • pivot() only rearranges and fails on duplicates; that error is information about your data
  • melt(id_vars, value_vars) turns header labels back into a column; stack() and unstack() do the same moves on index levels, and stack() keeps empty cells
  • Pivots sort labels, so month and weekday names come out alphabetical: pivot on numbers or reindex
  • Missing keys are dropped silently. Reconcile the grand total with the source, and show counts beside means

If you had to stop and think about which argument was index and which was columns, or drew the table on paper before writing the melt, you were doing it the way working analysts do. What matters more than speed is what you did in the project: you noticed a total that did not add up and refused to move on until it did. That instinct is worth more than any method name.
