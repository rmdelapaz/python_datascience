🏛️ Why a Database?

So far, every dataset in this course has arrived as a file that you read whole: pd.read_csv("data/orders.csv") loads all 20,302 orders into memory, and then you filter. That works well until the data has 200 million rows, or changes every second, or is shared by forty people at once. At that point the data lives in a database, and your job as an analyst changes from "load the file" to "ask for what you need".

💡 Mental Model: The Binder and the Librarian

A CSV file is a photocopied binder. To find last March's returned orders you carry the whole binder to your desk and flip through every page yourself.

A database is a library with a librarian at the desk. You hand over a request slip ("returned orders, March, Boise store, sorted by total") and the librarian brings back only those pages. You never see the shelves. The request slip is written in SQL, and the librarian is the database engine.

The librarian does more than fetch. A relational database also:

  • Keeps many tables in one place, with the keys that connect them (an order's customer_id points at a customer).
  • Enforces rules as data goes in: a column declared NOT NULL cannot be left empty, and a primary key cannot repeat.
  • Returns only the rows and columns you ask for, which matters when the table is far bigger than your computer's memory.
  • Makes changes all-or-nothing through transactions, so a half-finished update never becomes visible.

SQL (say "sequel" or spell it out, both are fine) has been the language of relational databases for decades, and it is the most widely requested skill in data job postings after spreadsheets. The good news: you already know the ideas. Filtering, sorting, grouping and merging are what you did in Module 2. This module teaches you to say the same things in a second language.

The Engine in This Course: SQLite

SQLite is a complete SQL database engine that lives inside a single file and needs no server, no password and no installation: Python's standard library includes it as the sqlite3 module. Pinecrest Outfitters' relational data ships as data/pinecrest.db. Nearly everything you write against it works unchanged on PostgreSQL, MySQL and other server databases; the differences are small and are listed near the end.

🔌 Connecting with sqlite3

Start a new notebook in your project folder. The first step is a habit to keep for this whole module: work on a copy of the database. Some lessons create tables and indexes, and you want the original file to stay exactly as documented.

import shutil
import sqlite3
import pandas as pd

pd.set_option("display.width", 150)
pd.set_option("display.max_columns", 20)

shutil.copy("data/pinecrest.db", "pinecrest_work.db")    # a private working copy

conn = sqlite3.connect("pinecrest_work.db")
print(conn)
print("SQLite library version:", sqlite3.sqlite_version)

Output (your address and version will differ)

<sqlite3.Connection object at 0x70cd1bfdaa70>
SQLite library version: 3.53.1

sqlite3.connect() returns a connection: an open line to the database file. Everything you do goes through it. The version printed is the SQLite engine bundled with your Python, which is separate from the Python version.

graph TD A["Your Python code"] --> B["Connection: an open line"] B --> C["Cursor: runs one statement"] C --> D["SQL text goes to the engine"] D --> E["Engine reads pinecrest_work.db"] E --> F["Rows come back as tuples"]

What Is in There?

Every SQLite database keeps a catalog of its own contents in a table called sqlite_master. Ask it for the table names:

cur = conn.execute("SELECT name FROM sqlite_master WHERE type = 'table' ORDER BY name")
print(cur.fetchall())

Output

[('customers',), ('employees',), ('inventory',), ('order_items',), ('orders',), ('products',)]

That was your first SQL query. Read it left to right: select the name column, from the sqlite_master table, where type is 'table', ordered by name. Four of the six tables are old friends from the CSV files. employees and inventory exist only in the database.

To see a table's columns, use SQLite's PRAGMA table_info command. Each row describes one column: position, name, declared type, whether it is NOT NULL, its default, and whether it is part of the primary key.

for row in conn.execute("PRAGMA table_info(orders)"):
    print(row)

Output

(0, 'order_id', 'INTEGER', 0, None, 1)
(1, 'customer_id', 'INTEGER', 1, None, 0)
(2, 'order_date', 'TEXT', 1, None, 0)
(3, 'channel', 'TEXT', 1, None, 0)
(4, 'store', 'TEXT', 1, None, 0)
(5, 'status', 'TEXT', 1, None, 0)
(6, 'payment_method', 'TEXT', 1, None, 0)
(7, 'promo_code', 'TEXT', 0, None, 0)
(8, 'discount_pct', 'INTEGER', 1, None, 0)
(9, 'shipping_cost', 'REAL', 1, None, 0)
(10, 'order_total', 'REAL', 1, None, 0)

💡 SQLite Has Only a Few Storage Types

INTEGER, REAL (float), TEXT and BLOB (raw bytes), plus NULL for "no value". There is no date type, so order_date is stored as text like 2024-03-05. Because that format sorts correctly as text, date comparisons still work. Booleans are stored as 0 and 1.

🖱️ Cursors and Rows

Running a statement gives you a cursor: a pointer that walks through the result one row at a time. The rows are not fetched until you ask, which is how a database can answer a query whose result would not fit in memory.

cur = conn.cursor()
cur.execute("SELECT order_id, store, order_total FROM orders")

print(cur.fetchone())        # the next row
print(cur.fetchone())        # the one after that
print(cur.fetchmany(3))      # the next three, as a list
rest = cur.fetchall()        # everything that is left
print(len(rest))

Output

(100001, 'Flagstaff', 434.9)
(100002, 'Asheville', 278.9)
[(100003, 'Online', 75.9), (100004, 'Online', 399.8), (100005, 'Online', 26.71)]
20297

Each row is a plain tuple, in the order of the columns you selected. Two rows plus three rows plus 20,297 makes the 20,302 orders: a cursor moves forward only, and once a row is fetched it is gone from the cursor. When the rows run out, fetchone() returns None and fetchall() returns an empty list.

conn.execute(...), which you used a moment ago, is a shortcut that creates a cursor, runs the statement and returns the cursor. You will see both styles. A cursor is also iterable, so a for loop is the natural way to read rows:

cur = conn.execute("SELECT order_id, store, order_total FROM orders LIMIT 3")
print([col[0] for col in cur.description])     # the column names

for order_id, store, total in cur:
    print(order_id, store, total)

Output

['order_id', 'store', 'order_total']
100001 Flagstaff 434.9
100002 Asheville 278.9
100003 Online 75.9

Rows You Can Read by Name

Position-only tuples get confusing with wide tables. Setting the connection's row_factory to sqlite3.Row makes every row answer to column names as well as positions.

conn.row_factory = sqlite3.Row

row = conn.execute("SELECT order_id, store, order_total FROM orders LIMIT 1").fetchone()
print(row["store"], row["order_total"])
print(row[0], row.keys())
print(dict(row))

Output

Flagstaff 434.9
100001 ['order_id', 'store', 'order_total']
{'order_id': 100001, 'store': 'Flagstaff', 'order_total': 434.9}

From here on, reading results by hand would get tedious, and you already own a better display tool. pandas can run a query and hand back a DataFrame. This tiny helper prints one, and it is all you need for the next two sections. (Later in the lesson you will look at pd.read_sql properly.)

def show(sql, params=()):
    """Run a query and print the result as a table."""
    print(pd.read_sql(sql, conn, params=params).to_string(index=False))

show("SELECT order_id, order_date, store, status, order_total FROM orders LIMIT 4")

Output

 order_id order_date     store    status  order_total
   100001 2024-01-01 Flagstaff completed        434.9
   100002 2024-01-01 Asheville completed        278.9
   100003 2024-01-01    Online completed         75.9
   100004 2024-01-01    Online completed        399.8

🔎 SELECT: Choosing, Filtering, Sorting

Almost all analysis in SQL is one statement, SELECT, with a handful of optional clauses that always appear in the same order. You will build it up one clause at a time. SQL keywords are not case sensitive; writing them in capitals is a convention that makes queries easier to scan. Line breaks and indentation mean nothing to the engine, so use them freely.

Columns: SELECT ... FROM

List the columns you want, or * for all of them. AS renames a column in the result, and you can compute new ones. LIMIT stops after that many rows, like .head().

show("""
    SELECT name,
           price,
           cost,
           ROUND(price - cost, 2) AS margin
    FROM products
    LIMIT 4
""")

Output

                               name  price   cost  margin
   Granite Fork Drift 1-Person Tent 299.95 187.74  112.21
Cedar Notch Ridgeline 2-Person Tent 217.95 131.94   86.01
   Pinecrest Solstice 3-Person Tent 459.95 301.97  157.98
    Wrenfield Skyline 4-Person Tent 294.95 149.42  145.53

Rows: WHERE

WHERE keeps the rows for which a condition is true. It is the boolean mask of SQL. Text values go in single quotes, equality is a single =, and conditions combine with AND, OR and NOT.

show("""
    SELECT name, price, rating
    FROM products
    WHERE category = 'Tents'
      AND price < 250
      AND rating >= 4.5
""")

Output

                              name  price  rating
          Quillback Wayfinder Tarp 132.95     4.9
Quillback Alpenglow Tent Footprint  67.95     5.0

Three more comparison tools cover most everyday filters: IN for "one of these", BETWEEN for an inclusive range, and LIKE for text patterns, where % stands for any run of characters.

show("""
    SELECT order_id, order_date, store, order_total
    FROM orders
    WHERE store IN ('Bend', 'Boise')
      AND order_date BETWEEN '2025-07-04' AND '2025-07-05'
      AND order_total > 500
""")

show("SELECT name, price FROM products WHERE name LIKE '%down%'")

Output

The date filter works on text because YYYY-MM-DD strings sort in calendar order. And notice that '%down%' matched "Down Jacket": in SQLite, LIKE ignores case for the letters A to Z.

Order: ORDER BY, and DISTINCT

ORDER BY sorts the result, ascending unless you add DESC. Without it, the order of rows is not guaranteed, even if it looks stable today. ORDER BY with LIMIT is the SQL way to say "top N".

show("""

    FROM orders
    WHERE status = 'completed'
    ORDER BY order_total DESC, order_id
    LIMIT 5
""")

show("SELECT DISTINCT payment_method FROM orders ORDER BY payment_method")

✅ You Already Speak This

If a query feels foreign, translate it into pandas in your head. WHERE is a boolean mask, ORDER BY is sort_values, LIMIT is head. The ideas are the same ones you practiced for nine lessons. Only the spelling is new, and spelling comes with repetition.

🧮 Aggregating and Grouping

An aggregate function turns many rows into one value. The five you will use daily are COUNT, SUM, AVG, MIN and MAX.

show("""
    SELECT COUNT(*)                   AS orders,
           ROUND(SUM(order_total), 2) AS revenue,
           ROUND(AVG(order_total), 2) AS avg_order,
           MIN(order_date)            AS first_day,
           MAX(order_date)            AS last_day
    FROM orders
    WHERE status = 'completed'
""")

Output

 orders    revenue  avg_order  first_day   last_day
  18762 3624306.27     193.17 2024-01-01 2025-12-31

18,762 completed orders and $3,624,306.27 of revenue: the same totals you have computed with pandas, answered by the engine in one row. COUNT has three forms worth knowing apart:

show("""
    SELECT COUNT(*)             AS all_rows,
           COUNT(phone)         AS with_phone,
           COUNT(DISTINCT city) AS cities
    FROM customers
""")

Output

 all_rows  with_phone  cities
     4850        4570      35

COUNT(*) counts rows. COUNT(column) counts rows where that column is not NULL (280 customers have no phone on file). COUNT(DISTINCT column) counts different values, like .nunique(). All aggregate functions skip NULL, just as pandas skips NaN.

GROUP BY: One Row per Group

GROUP BY is split-apply-combine, the idea from Lesson 2.4: split the rows into groups, apply the aggregates to each group, combine into one row per group.

show("""
    SELECT store,
           COUNT(*)                   AS orders,
           ROUND(SUM(order_total), 2) AS revenue,
           ROUND(AVG(order_total), 2) AS avg_order
    FROM orders
    WHERE status = 'completed'
    GROUP BY store
    ORDER BY revenue DESC
""")

Output

    store  orders    revenue  avg_order
   Online   11604 2357984.45     203.20
    Boise    2502  443386.85     177.21
Flagstaff    1648  300580.35     182.39
     Bend    1650  284575.25     172.47
Asheville    1358  237779.37     175.10

The pandas version, for comparison, is orders[orders["status"] == "completed"].groupby("store")["order_total"].agg(["count", "sum", "mean"]). The rule to remember for SQL: every column in the SELECT list must either be in the GROUP BY or be inside an aggregate function. Anything else has no single value per group.

You can group by an expression too. SQLite's strftime pulls parts out of a date string, here the year:

show("""
    SELECT strftime('%Y', order_date) AS year,
           channel,
           COUNT(*)                   AS orders,
           ROUND(SUM(order_total), 2) AS revenue
    FROM orders
    WHERE status = 'completed'
    GROUP BY year, channel
    ORDER BY year, channel
""")

Output

year channel  orders    revenue
2024  online    5362 1077800.75
2024   store    3430  605498.76
2025  online    6242 1280183.70
2025   store    3728  660823.06

HAVING: Filtering the Groups

WHERE filters rows before they are grouped, so it cannot mention an aggregate. To filter on a group's result, use HAVING, which runs after grouping.

show("""
    SELECT category,
           COUNT(*)             AS products,
           ROUND(AVG(price), 2) AS avg_price
    FROM products
    WHERE stock_status != 'out_of_stock'      -- rows: only products we can sell
    GROUP BY category
    HAVING COUNT(*) >= 25                     -- groups: only the larger categories
    ORDER BY avg_price DESC
""")

Output

    category  products  avg_price
     Apparel        33     101.01
    Footwear        26      92.95
Camp Kitchen        28      66.76
 Accessories        30      55.18

Two dashes start a comment in SQL. The query has both kinds of filter, each doing its own job.

The Order You Write and the Order It Runs

The clauses must be written in a fixed order: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. The engine thinks about them in a different order, and knowing it explains most beginner errors.

🛡️ Parameters and SQL Injection

Real queries are rarely fixed text. The store name comes from a dropdown, the date from a form, the customer id from a loop. The value has to get into the query somehow, and how you do that is the most important safety habit in this module.

The Right Way: Placeholders

Write a ? where each value belongs and pass the values separately, as a tuple. The engine receives the SQL text and the values through different channels, so a value can never be mistaken for part of the command.

store = "Flagstaff"
min_total = 1000

cur = conn.execute(
    "SELECT order_id, order_date, order_total FROM orders WHERE store = ? AND order_total > ? ORDER BY order_total DESC",
    (store, min_total),
)
for row in cur:
    print(tuple(row))

Output

(114132, '2025-06-20', 1126.75)
(114679, '2025-07-06', 1083.7)
(115617, '2025-08-05', 1043.85)

With more than two or three values, named placeholders are easier to read. Write :name in the SQL and pass a dictionary.

show(
    """
    SELECT status, COUNT(*) AS orders
    FROM orders
    WHERE store = :store AND order_date >= :since
    GROUP BY status
    """,
    {"store": "Asheville", "since": "2025-12-01"},
)

Output

   status  orders
cancelled       1
completed      60
 returned       4

The Wrong Way, Demonstrated Safely

It is tempting to build the query with an f-string. Here is a customer lookup written that way, and what happens when the "last name" is not a last name.

def count_customers_unsafe(last_name):
    sql = f"SELECT COUNT(*) FROM customers WHERE last_name = '{last_name}'"    # DO NOT do this
    return conn.execute(sql).fetchone()[0]

def count_customers_safe(last_name):
    sql = "SELECT COUNT(*) FROM customers WHERE last_name = ?"
    return conn.execute(sql, (last_name,)).fetchone()[0]

print(count_customers_unsafe("Soto"), count_customers_safe("Soto"))

sneaky = "nobody' OR '1'='1"
print(count_customers_unsafe(sneaky), count_customers_safe(sneaky))

Output

45 45
4850 0

For an honest name both functions agree. For the crafted input, the unsafe function matched every one of the 4,850 customers. Look at the SQL it built:

SELECT COUNT(*) FROM customers WHERE last_name = 'nobody' OR '1'='1'

The quote inside the input closed the string early, and the rest of the input became SQL: OR '1'='1' is true for every row. This is SQL injection. If that function returned names and emails instead of a count, the visitor would now have the whole customer list. With other inputs an attacker can read other tables or change data. The safe function treated the same input as one odd-looking name and correctly found nobody.

🛑 The Rule

Never put a value into SQL with an f-string, .format(), % or +. Always use placeholders. This applies even when the value "comes from your own code": names such as O'Brien break hand-built SQL with no attacker involved, and habits are what protect you on the day the input is not yours.

💡 What Placeholders Cannot Do

A placeholder stands for a value, never for a table name, a column name or a keyword. If the column to sort by comes from a user, check it against a list of allowed names in Python first, and only then put it in the query text: if sort_col not in {"order_total", "order_date"}: raise ValueError(...).

✍️ Writing Data and Transactions

Analysts mostly read, but you will sometimes save a result table, load a lookup list or stage cleaned data. Three statements change data: INSERT, UPDATE and DELETE, and CREATE TABLE makes a new table. All of this happens in your working copy.

conn.execute("""
    CREATE TABLE store_targets (
        store          TEXT NOT NULL,
        quarter        TEXT NOT NULL,
        target_revenue REAL NOT NULL,
        PRIMARY KEY (store, quarter)
    )
""")

targets = [
    ("Boise", "2025-Q1", 720000.0),
    ("Bend", "2025-Q1", 505000.0),
    ("Flagstaff", "2025-Q1", 470000.0),
]
conn.executemany("INSERT INTO store_targets VALUES (?, ?, ?)", targets)
conn.commit()

show("SELECT * FROM store_targets")

Output

    store quarter  target_revenue
    Boise 2025-Q1        720000.0
     Bend 2025-Q1        505000.0
Flagstaff 2025-Q1        470000.0

executemany runs one statement once per tuple in the list, with placeholders, of course. The line that makes it permanent is conn.commit().

Transactions: All or Nothing

When you change data, sqlite3 quietly opens a transaction. Your changes are visible to your own connection but are not saved to the file until you commit(). If something goes wrong you can rollback() and the database returns to the last commit, as if nothing had happened.

Python makes this automatic. (You met with for files in Intermediate Python; a connection uses it for a different job.) Used in a with statement, a connection commits if the block finishes and rolls back if it raises.

with conn:
    conn.execute("INSERT INTO store_targets VALUES (?, ?, ?)", ("Asheville", "2025-Q1", 390000.0))
    conn.execute("INSERT INTO store_targets VALUES (?, ?, ?)", ("Boise", "2025-Q1", 999999.0))   # duplicate key

Error

IntegrityError: UNIQUE constraint failed: store_targets.store, store_targets.quarter
show("SELECT store, quarter FROM store_targets")

Output

    store quarter
     Bend 2025-Q1
    Boise 2025-Q1
Flagstaff 2025-Q1

The second insert broke the primary key rule (Boise already has a 2025-Q1 target), so the engine refused it. Because both inserts were in one transaction, the Asheville row was rolled back too. That is the point: a batch of related changes either all happen or none do.

⚠️ with conn: Does Not Close the Connection

For files, with open(...) closes the file. For sqlite3, with conn: only ends the transaction. The connection stays open, which is convenient in a notebook. To close it as well, call conn.close() when you are done, or wrap it in contextlib.closing:

from contextlib import closing

with closing(sqlite3.connect("pinecrest_work.db")) as tmp_conn:
    n = tmp_conn.execute("SELECT COUNT(*) FROM store_targets").fetchone()[0]
print(n)

try:
    tmp_conn.execute("SELECT 1")
except sqlite3.ProgrammingError as e:
    print("ProgrammingError:", e)

Output

3
ProgrammingError: Cannot operate on a closed database.

🧰 SQLAlchemy: One Interface, Many Databases

sqlite3 speaks only to SQLite. Each other database has its own Python driver with its own small differences. SQLAlchemy is a library that sits on top of the drivers and gives you one consistent way to connect, run SQL and manage transactions, whatever the engine. It is also what pandas prefers to talk to. You installed it in Lesson 0.1.

You start by creating an engine from a database URL. The engine is a factory for connections; creating it does not connect yet.

import sqlalchemy
from sqlalchemy import create_engine, text, inspect

engine = create_engine("sqlite:///pinecrest_work.db")
print(sqlalchemy.__version__)
print(engine.dialect.name)
print(inspect(engine).get_table_names())

Output

2.1.4
sqlite
['customers', 'employees', 'inventory', 'order_items', 'orders', 'products', 'store_targets']

The URL reads dialect://location. For SQLite the location is a file path, so there are three slashes: two for the URL and one that starts a relative path. inspect() is SQLAlchemy's portable way to list tables and columns, so you do not need each engine's own catalog tables.

To run SQL, borrow a connection with with engine.connect() and wrap the SQL in text(). Parameters are always the :name style, passed as a dictionary, on every database.

query = text("""
    SELECT store, COUNT(*) AS returned
    FROM orders
    WHERE status = :status AND order_date >= :since
    GROUP BY store
    ORDER BY returned DESC
""")

with engine.connect() as sa_conn:
    result = sa_conn.execute(query, {"status": "returned", "since": "2025-01-01"})
    print(list(result.keys()))
    for row in result:
        print(row.store, row.returned)

Output

['store', 'returned']
Online 467
Boise 36
Bend 34
Flagstaff 30
Asheville 30

Rows from SQLAlchemy behave like named tuples: row.store, row[0], and row._mapping["store"] all work. Here the with block does close the connection (it returns it to the engine's pool).

For changes, use engine.begin() instead: it opens a connection and a transaction, commits at the end of the block, and rolls back on an error.

with engine.begin() as sa_conn:
    sa_conn.execute(
        text("INSERT INTO store_targets VALUES (:store, :quarter, :target)"),
        [
            {"store": "Asheville", "quarter": "2025-Q1", "target": 390000.0},
            {"store": "Online", "quarter": "2025-Q1", "target": 600000.0},
        ],
    )

with engine.connect() as sa_conn:
    print(sa_conn.execute(text("SELECT COUNT(*) FROM store_targets")).scalar())

Output

5

Passing a list of dictionaries runs the statement once per dictionary. .scalar() returns the first column of the first row, which is handy for single-number answers.

💡 What About the ORM?

SQLAlchemy has a second, larger half, the ORM, which maps tables to Python classes. Application developers use it heavily. For analysis you rarely need it: writing SQL with text() and reading results into pandas is the common, well-supported path, and it is the one this course takes.

🐼 SQL and pandas Together

The usual division of labor: let the database do the heavy filtering, joining and aggregating, then bring a manageable result into pandas for statistics, reshaping and charts.

Reading: pd.read_sql

pd.read_sql(sql, connection) runs a query and returns a DataFrame. It accepts a SQLAlchemy connection (the general case) or a plain sqlite3 connection.

query = text("""

Writing: DataFrame.to_sql

to_sql saves a DataFrame as a table. The two arguments to set every time are if_exists ("fail" is the default; "replace" drops and recreates the table; "append" adds rows) and index=False, unless you want the index stored as a column.

with engine.connect() as sa_conn:
    by_month = pd.read_sql(text("""
        SELECT strftime('%Y-%m', order_date) AS month,
               COUNT(*)                      AS orders,
               ROUND(SUM(order_total), 2)    AS revenue
        FROM orders
        WHERE status = 'completed'
        GROUP BY month
        ORDER BY month
    """), sa_conn)

by_month["avg_order"] = (by_month["revenue"] / by_month["orders"]).round(2)

rows = by_month.to_sql("monthly_summary", engine, if_exists="replace", index=False)
print(rows)

show("SELECT * FROM monthly_summary ORDER BY revenue DESC LIMIT 3")

⚠️ if_exists="replace" Deletes First

It drops the existing table and everything in it, then creates a new one from your DataFrame. That is what you want for a summary you regenerate. It is a disaster if you mistype the name of a real table. On a shared database, write only to tables that are yours to replace.

⚠️ Common Mistakes

Everyone who learns SQL from Python meets these. Each message is the engine telling you precisely what it could not do.

1. A Typo in the File Name Creates a New, Empty Database

oops = sqlite3.connect("pinecrest_wrok.db")      # typo: "wrok"
oops.execute("SELECT COUNT(*) FROM orders")

Error

OperationalError: no such table: orders

What it means: sqlite3.connect does not complain about a file that does not exist. It creates an empty database with that name, and the error only appears when you query a table that is not in it. Fix: check the path (and delete the stray empty file). To make a missing file an error, open it read-only with a URI: sqlite3.connect("file:pinecrest_work.db?mode=ro", uri=True).

import os
oops.close()
os.remove("pinecrest_wrok.db")      # tidy up the accidental file

2. A String Where a Tuple of Parameters Belongs

conn.execute("SELECT COUNT(*) FROM orders WHERE store = ?", "Boise")

Error

ProgrammingError: Incorrect number of bindings supplied. The current statement uses 1, and there are 5 supplied.

What it means: the parameters must be a sequence, and a string is a sequence, of five characters. Fix: a one-item tuple needs a trailing comma: ("Boise",). A list, ["Boise"], also works.

3. An Aggregate in WHERE

conn.execute("SELECT store, COUNT(*) FROM orders WHERE COUNT(*) > 2000 GROUP BY store")

Error

OperationalError: misuse of aggregate: COUNT()

What it means: WHERE runs before the groups exist, so there is nothing to count yet. Fix: conditions on aggregates go in HAVING, after GROUP BY.

4. Passing a Plain String to SQLAlchemy

with engine.connect() as sa_conn:
    sa_conn.execute("SELECT COUNT(*) FROM orders")

Error

ObjectNotExecutableError: Not an executable object: 'SELECT COUNT(*) FROM orders'

What it means: SQLAlchemy 2 does not run bare strings. Fix: wrap the SQL in text("..."). Many older tutorials show the bare-string form, which no longer works.

5. Forgetting to Commit

There is no error message for this one, which is what makes it expensive. A second connection stands in for "your colleague" or "your script tomorrow".

other = sqlite3.connect("pinecrest_work.db")
count_sql = "SELECT COUNT(*) FROM store_targets"

conn.execute("INSERT INTO store_targets VALUES (?, ?, ?)", ("Bend", "2025-Q2", 560000.0))
print("mine:", conn.execute(count_sql).fetchone()[0], " theirs:", other.execute(count_sql).fetchone()[0])

conn.commit()
print("mine:", conn.execute(count_sql).fetchone()[0], " theirs:", other.execute(count_sql).fetchone()[0])
other.close()

Output

mine: 6  theirs: 5
mine: 6  theirs: 6

What happened: before the commit, only your own connection could see the new row. Had you closed the notebook at that moment, the row would have been lost. Fix: do writes inside with conn: (or with engine.begin()), so the commit cannot be forgotten.

6. Double Quotes Around Text

In standard SQL, single quotes mean a text value and double quotes mean a name (of a column or table). SQLite is forgiving and often accepts WHERE store = "Boise", but PostgreSQL will answer column "Boise" does not exist. Fix: single quotes for text, always. Wrapping your SQL in Python triple double quotes makes that easy.

def store_scorecard(engine, store, year):
    """Headline numbers for one store and one calendar year, as a one-row DataFrame."""
    params = {"store": store, "start": f"{year}-01-01", "end": f"{year + 1}-01-01"}
    with engine.connect() as c:
        card = pd.read_sql(HEADLINE_SQL, c, params=params)
        status = pd.read_sql(STATUS_SQL, c, params=params).set_index("status")["orders"]
    card.insert(0, "store", store)
    card.insert(1, "year", year)
    card["return_rate_pct"] = round(100 * status.get("returned", 0) / status.sum(), 1)
    return card

with engine.connect() as c:

❓ Common Questions at This Stage

If pandas can do all of this, why learn SQL?

Because the data is usually in a database before it is anywhere else, and often it is too large or too sensitive to copy out whole. SQL lets the database do the work where the data lives. It is also a shared language: analysts, engineers and dashboard tools all read it. In practice you will use both, SQL to fetch and reduce, pandas to analyze and plot.

Should I use sqlite3 or SQLAlchemy?

For a quick look at a SQLite file, sqlite3 is fine and needs nothing installed. For anything you will keep, share, or point at another database later, use a SQLAlchemy engine with text(). The code is nearly the same length, and switching databases becomes a one-line change.

Is SQLite a "real" database?

Yes. It is among the most widely deployed software in the world: it is inside phones, browsers and countless applications. Its limits are about concurrency (one writer at a time) and administration (no users or permissions), not about SQL. It is a good choice for analysis files, prototypes and teaching, and a poor one for a busy multi-user application.

Do I need to close connections in a notebook?

For a local SQLite file, leaving one connection open while you work is normal; close it (or restart the kernel) when you finish. For a server database, connections are a limited shared resource, so use with engine.connect() blocks, which hand each connection back as soon as the block ends.

Why did my query return rows in a different order this time?

Without ORDER BY, a database may return rows in any order it finds convenient, and that can change when the data, an index or the engine version changes. If order matters, say so with ORDER BY, and include a tiebreaker column so the result is fully determined.

🎓 Key Takeaways

  • A database answers questions and returns only what you ask for; SQL is the language of the request
  • sqlite3.connect() gives a connection; statements run through cursors, and rows come back as tuples (or sqlite3.Row)
  • A query is written SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT, and runs starting from FROM
  • WHERE filters rows before grouping; HAVING filters groups after it
  • Values go into SQL through placeholders (? or :name), never through string formatting
  • Changes are saved only on commit; with conn: and with engine.begin(): commit or roll back for you
  • SQLAlchemy's create_engine, engine.connect() and text() work the same way on every database
