🧠 How a Query Runs

SQL is a declarative language: you describe the result you want, not the steps to get it. Somebody still has to choose the steps. That somebody is the query planner, a part of the engine that looks at your query, at the tables, and at the indexes available, and picks a strategy. The same query can run a hundred times faster or slower depending on what the planner has to work with.

graph TD A["Your SQL text"] --> B["Parser: is it valid SQL?"] B --> C["Planner: compare possible strategies"] C --> D["Chosen plan"] D --> E["Executor: read tables and indexes"] E --> F["Rows returned"]

💡 Mental Model: The Book With No Index

A table is a thick reference book whose pages are in the order they were written. To find every mention of "crampons" you have exactly one strategy: start at page 1 and read to the end. That is a scan.

An index is the alphabetical list at the back: each term, followed by the page numbers where it appears. Now the strategy is: jump to "crampons" in the list (fast, because the list is sorted), then turn straight to those pages. That is a search. The index is extra paper, and somebody has to update it every time a page is added. Those two facts are this entire lesson.

In SQLite, a table really is stored in order of one number, the rowid (for a table with an INTEGER PRIMARY KEY, such as orders.order_id, the primary key is the rowid). Finding a row by rowid is fast. Finding rows by anything else means reading the whole table, unless an index on that column exists. As shipped, pinecrest.db has no indexes beyond its primary keys. That was deliberate, and you are about to feel why.

Setup: A Copy, a Plan Printer and a Stopwatch

This lesson creates indexes, so it works on a copy. Two small helpers do the measuring: plan() prints the engine's strategy, and timed() runs a query once per parameter set and reports the best of several attempts, the same best-of-N approach as timeit in Lesson 1.1.

import os
import shutil
import sqlite3
import time
import pandas as pd

pd.set_option("display.width", 150)

shutil.copy("data/pinecrest.db", "pinecrest_tuning.db")
conn = sqlite3.connect("pinecrest_tuning.db", cached_statements=0)

def plan(sql, params=()):
    """Print the query plan, one step per line, indented to show nesting."""
    depth = {0: 0}
    for step_id, parent, _, detail in conn.execute("EXPLAIN QUERY PLAN " + sql, params):
        depth[step_id] = depth[parent] + 1
        print("   " * depth[parent] + detail)

def timed(sql, param_list, repeat=5):
    """Best time in milliseconds to run the query once for every item of param_list."""
    best = float("inf")
    for _ in range(repeat):
        start = time.perf_counter()
        for params in param_list:
            conn.execute(sql, params).fetchall()
        best = min(best, time.perf_counter() - start)
    return best * 1000

print(sqlite3.sqlite_version)

Output (your version may differ)

3.53.1

💡 Two Details in That Setup

cached_statements=0 turns off Python's cache of prepared statements for this connection. With the cache on, asking for the plan of a query a second time, after dropping an index, can show you the old plan. That is harmless for normal work and confusing in a lesson about plans.

The plan wording shown here is from SQLite 3.36 or later. Older versions say SCAN TABLE orders where newer ones say SCAN orders; the meaning is the same.

🔍 Reading EXPLAIN QUERY PLAN

Put EXPLAIN QUERY PLAN in front of any query and SQLite returns its strategy instead of running the query. Nothing is read or changed, so it is always safe. Here is the raw result for a lookup by primary key.

for row in conn.execute("EXPLAIN QUERY PLAN SELECT * FROM orders WHERE order_id = ?", (100500,)):
    print(row)

Output

(2, 0, 33, 'SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)')

Each row is one step: an id, the id of its parent step (for nesting), an unused number, and a sentence. The sentence is what matters, and the plan() helper prints only that. Two verbs do nearly all the work:

The plan saysIt meansCost grows with
SCAN ordersRead every row of the table and test each oneThe size of the table
SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)Jump straight to the row by its rowidAlmost nothing
SEARCH t USING INDEX i (col=?)Find matching entries in index i, then fetch those rows from the tableThe number of matching rows
SEARCH t USING COVERING INDEX i (...)The index alone has every column needed; the table is not touchedThe number of matching rows
SCAN t USING INDEX i or USING COVERING INDEX iStill reads everything, but walks the index (useful for its order, or because it is smaller than the table)The size of the table
USE TEMP B-TREE FOR ORDER BY (or GROUP BY, DISTINCT)The rows must be sorted in a temporary structure before they can be returnedThe number of rows sorted

Now compare three queries on orders through the helper.

print("1. by primary key")
plan("SELECT * FROM orders WHERE order_id = ?", (100500,))

print("2. by another column")
plan("SELECT * FROM orders WHERE customer_id = ?", (12673,))

print("3. filter, then sort")
plan("SELECT * FROM orders WHERE store = ? ORDER BY order_date", ("Bend",))

Output

1. by primary key
SEARCH orders USING INTEGER PRIMARY KEY (rowid=?)
2. by another column
SCAN orders
3. filter, then sort
SCAN orders
USE TEMP B-TREE FOR ORDER BY

Read them line by line. Query 1 is a direct jump. Query 2 has no index on customer_id, so every one of the 20,302 orders is examined to find one customer's handful. Query 3 scans, keeps Bend's rows, and then needs a separate sorting step, the TEMP B-TREE, before it can return anything.

✅ SCAN Is Not a Dirty Word

If a query needs most of a table (a yearly total, a GROUP BY over everything), reading all of it once is the best plan. A scan is a problem only when you wanted a few rows and paid for all of them. The question to ask of every SCAN line is: "how much of this table did I actually need?"

📇 What an Index Does

The classic slow query in this database is "the lines of one order". order_items has 45,490 rows and its primary key is order_item_id, so a filter on order_id gets no help.

ITEMS_SQL = "SELECT * FROM order_items WHERE order_id = ?"
plan(ITEMS_SQL, (100500,))

order_ids = [(100000 + 100 * k,) for k in range(1, 201)]      # 200 different orders
before = timed(ITEMS_SQL, order_ids)
print(f"200 lookups: {before:.1f} ms")

Output (your timing will differ)

SCAN order_items
200 lookups: 148.5 ms

Each lookup reads all 45,490 rows to return two or three. Two hundred lookups read about nine million rows. On a table this small that is a fraction of a second; on a table a thousand times larger, the same page of a web app would take minutes.

Create an index on the column you search by. The name is yours to choose; a common convention is idx_table_column.

conn.execute("CREATE INDEX idx_order_items_order_id ON order_items (order_id)")
conn.commit()

plan(ITEMS_SQL, (100500,))
after = timed(ITEMS_SQL, order_ids)
print(f"200 lookups: {after:.1f} ms   ({before / after:.0f} times faster)")

Output (your timing will differ)

SEARCH order_items USING INDEX idx_order_items_order_id (order_id=?)
200 lookups: 1.3 ms   (117 times faster)

SCAN became SEARCH ... USING INDEX, and the time dropped by about two orders of magnitude. You did not change the query at all. The planner noticed the new index and chose a better strategy by itself, and the result is the same rows as before.

An index is a separate, sorted structure (a B-tree) holding the indexed column and the rowid of each row. Because it is sorted, finding a value takes a handful of steps even among millions of entries, the way you find a word in a dictionary without reading it. The diagram also shows why this particular index was missing in the first place: order_id repeats in order_items, so it could not be the primary key.

💡 Primary Keys and UNIQUE Columns Are Indexed Automatically

That is why lookups by orders.order_id, customers.customer_id and products.sku were fast all along. The columns you usually have to index yourself are foreign keys (the "many" side of a join, such as order_items.order_id and orders.customer_id) and the columns you filter and sort by most.

🔗 Indexes and Joins

SQLite runs a join as a nested loop: for each row of one table (the outer loop), find the matching rows of the other (the inner loop). The plan lists the outer table first and the inner one indented beneath it. The inner step runs once per outer row, so it had better be a SEARCH.

Here is a customer's order history with its lines. To see where the engine starts from nothing, temporarily remove the index you just made.

HISTORY_SQL = """
    SELECT o.order_id, o.order_date, i.sku, i.quantity
    FROM orders AS o
    JOIN order_items AS i ON i.order_id = o.order_id
    WHERE o.customer_id = ?
"""
customers = [(10001 + 20 * k,) for k in range(200)]      # 200 customer ids

conn.execute("DROP INDEX idx_order_items_order_id")
print("No indexes:")
plan(HISTORY_SQL, (12673,))
t0 = timed(HISTORY_SQL, customers[:20], repeat=3) * 10    # 20 lookups, scaled to 200

conn.execute("CREATE INDEX idx_order_items_order_id ON order_items (order_id)")
print("Index on order_items(order_id):")
plan(HISTORY_SQL, (12673,))
t1 = timed(HISTORY_SQL, customers)

conn.execute("CREATE INDEX idx_orders_customer_id ON orders (customer_id)")
conn.commit()
print("Plus index on orders(customer_id):")
plan(HISTORY_SQL, (12673,))
t2 = timed(HISTORY_SQL, customers)

print(f"200 histories: {t0:.0f} ms, then {t1:.0f} ms, then {t2:.1f} ms")

Output (your timings will differ)

No indexes:
SCAN i
SEARCH o USING INTEGER PRIMARY KEY (rowid=?)
Index on order_items(order_id):
SCAN o
SEARCH i USING INDEX idx_order_items_order_id (order_id=?)
Plus index on orders(customer_id):
SEARCH o USING INDEX idx_orders_customer_id (customer_id=?)
SEARCH i USING INDEX idx_order_items_order_id (order_id=?)
200 histories: 388 ms, then 90 ms, then 3.1 ms

Three plans for one unchanged query:

  1. No indexes. The planner makes the best of it: scan all 45,490 lines and look up each line's order by primary key to check the customer. Backwards from how you wrote it, and slow.
  2. Index on the lines. Now it scans the 20,302 orders for the customer, and for each of that customer's orders searches the lines. Better: the inner loop is a search.
  3. Both indexes. Search for the customer's few orders, then search for each order's lines. No scans at all. This is the plan you want for a "show me one customer" page.

⚠️ The Planner Reorders Your Joins

The order of tables in your FROM clause is not the order of execution. The planner picks the outer and inner tables for you, as the first plan showed. Read the plan to see what it chose; do not assume.

🧬 Composite and Covering Indexes

Composite: More Than One Column

A store manager's report filters on two things: a store and a date range. An index can cover several columns, and their order matters, exactly as it does in a phone book sorted by last name and then first name.

REPORT_SQL = "SELECT order_id, order_total FROM orders WHERE store = ? AND order_date BETWEEN ? AND ?"
week = [("Bend", "2025-07-01", "2025-07-07")] * 200

plan(REPORT_SQL, week[0])
t_before = timed(REPORT_SQL, week)

conn.execute("CREATE INDEX idx_orders_store_date ON orders (store, order_date)")
conn.commit()

plan(REPORT_SQL, week[0])
t_after = timed(REPORT_SQL, week)
print(f"200 reports: {t_before:.0f} ms before, {t_after:.1f} ms after")

Output (your timings will differ)

SCAN orders
SEARCH orders USING INDEX idx_orders_store_date (store=? AND order_date>? AND order_date<?)
200 reports: 116 ms before, 2.5 ms after

The plan line tells you how much of the index is being used: store=? for the first column, then a range on order_date. The engine jumps to "Bend, July 1" in the index and reads forward to "Bend, July 7".

What can this one index do for other queries?

print("store only:")
plan("SELECT order_id FROM orders WHERE store = ?", ("Bend",))

print("date only:")
plan("SELECT order_id FROM orders WHERE order_date = ?", ("2025-07-04",))

print("store, sorted by date:")
plan("SELECT * FROM orders WHERE store = ? ORDER BY order_date", ("Bend",))

Output

store only:
SEARCH orders USING COVERING INDEX idx_orders_store_date (store=?)
date only:
SCAN orders USING COVERING INDEX idx_orders_store_date
store, sorted by date:
SEARCH orders USING INDEX idx_orders_store_date (store=?)
  • Store only: a SEARCH. The first column of a composite index works on its own.
  • Date only: a SCAN (of the index, but a scan of everything all the same). The dates are sorted only within each store, so there is no single place to jump to, just as a phone book is no help for finding everyone named "Maria".
  • Store, sorted by date: a SEARCH, and the TEMP B-TREE FOR ORDER BY from earlier is gone. Within one store, the index is already in date order, so no sorting step is needed.

💡 The Leftmost-Prefix Rule

An index on (a, b, c) can serve filters on a, on a, b, and on a, b, c, but not on b or c alone. When you design one, put columns compared with = first and the column with a range (BETWEEN, >, <) or the sort last.

Covering: The Index Answers by Itself

Notice that the "store only" plan said USING COVERING INDEX. The query asked only for order_id (the rowid, which every index entry carries), so the engine never opened the table at all. You can design for that. The weekly revenue total needs order_total; add it to the index and the table is out of the picture.

TOTAL_SQL = "SELECT COUNT(*), SUM(order_total) FROM orders WHERE store = ? AND order_date BETWEEN ? AND ?"

plan(TOTAL_SQL, week[0])
t_plain = timed(TOTAL_SQL, week)

conn.execute("CREATE INDEX idx_orders_store_date_total ON orders (store, order_date, order_total)")
conn.commit()

plan(TOTAL_SQL, week[0])
t_cover = timed(TOTAL_SQL, week)
print(f"200 totals: {t_plain:.2f} ms with the two-column index, {t_cover:.2f} ms with the covering index")

Output (your timings will differ)

SEARCH orders USING INDEX idx_orders_store_date (store=? AND order_date>? AND order_date<?)
SEARCH orders USING COVERING INDEX idx_orders_store_date_total (store=? AND order_date>? AND order_date<?)
200 totals: 1.63 ms with the two-column index, 1.35 ms with the covering index

A modest gain this time, and on your machine it may be within the noise: the big win was going from a scan to a search, and covering only trims the last step of fetching a few rows from the table. The three-column index makes the two-column one redundant (it serves every query the other can, by the leftmost-prefix rule), so remove the older one. Every index you keep has a price, which a later section measures.

conn.execute("DROP INDEX idx_orders_store_date")
conn.commit()

for name, table in conn.execute("SELECT name, tbl_name FROM sqlite_master WHERE type = 'index' AND name LIKE 'idx_%' ORDER BY name"):
    print(f"{name:<30} on {table}")

Output

idx_order_items_order_id       on order_items
idx_orders_customer_id         on orders
idx_orders_store_date_total    on orders

🚧 When an Index Does Not Help

An index is used only when the engine can go to a position in its sorted order. Several perfectly reasonable-looking filters make that impossible.

1. A Function Wrapped Around the Column

Both of these find Bend's orders for July 2025. Look at how much of the index each can use.

print("function on the column:")
plan("SELECT COUNT(*) FROM orders WHERE store = ? AND strftime('%Y-%m', order_date) = ?", ("Bend", "2025-07"))

print("range on the bare column:")
plan("SELECT COUNT(*) FROM orders WHERE store = ? AND order_date >= ? AND order_date < ?", ("Bend", "2025-07-01", "2025-08-01"))

a = conn.execute("SELECT COUNT(*) FROM orders WHERE store = ? AND strftime('%Y-%m', order_date) = ?", ("Bend", "2025-07")).fetchone()[0]
b = conn.execute("SELECT COUNT(*) FROM orders WHERE store = ? AND order_date >= ? AND order_date < ?", ("Bend", "2025-07-01", "2025-08-01")).fetchone()[0]
print("same answer:", a, b)

Output

function on the column:
SEARCH orders USING COVERING INDEX idx_orders_store_date_total (store=?)
range on the bare column:
SEARCH orders USING COVERING INDEX idx_orders_store_date_total (store=? AND order_date>? AND order_date<?)
same answer: 83 83

With strftime(...) around order_date, the index helps only with the store; every one of Bend's orders is then run through the function. The index is sorted by order_date, not by strftime('%Y-%m', order_date). Written as a range on the bare column, the same question uses both columns of the index. Keep the indexed column alone on one side of the comparison and move the calculation to the other side. (If you truly need to filter on an expression, SQLite and PostgreSQL can index the expression itself: CREATE INDEX ... ON orders (strftime('%Y-%m', order_date)).)

2. A Pattern That Starts with a Wildcard

print("LIKE '%Tent%':")
plan("SELECT sku FROM products WHERE name LIKE '%Tent%'")

print("LIKE 'TNT%' on the primary key:")
plan("SELECT sku FROM products WHERE sku LIKE 'TNT%'")

print("the same prefix as a range:")
plan("SELECT sku FROM products WHERE sku >= 'TNT' AND sku < 'TNU'")

Output

LIKE '%Tent%':
SCAN products
LIKE 'TNT%' on the primary key:
SCAN products USING COVERING INDEX sqlite_autoindex_products_1
the same prefix as a range:
SEARCH products USING COVERING INDEX sqlite_autoindex_products_1 (sku>? AND sku<?)

A pattern beginning with % can match anywhere in the text, so sorted order is no help: a dictionary cannot find every word containing "ent". The second result is a SQLite subtlety: because LIKE ignores case and the index does not, even a prefix pattern scans here. Rewriting the prefix as a range uses the primary key's index. (Searching inside text at scale is a job for a full-text index, a separate feature.)

3. A Column with Few Distinct Values

status has three values, and 92% of orders are completed. Index it and compare the index with a plain scan. NOT INDEXED after a table name tells SQLite to ignore indexes, which is handy for exactly this kind of experiment.

conn.execute("CREATE INDEX idx_orders_status ON orders (status)")
conn.commit()

WITH_INDEX = "SELECT AVG(shipping_cost) FROM orders WHERE status = ?"
NO_INDEX = "SELECT AVG(shipping_cost) FROM orders NOT INDEXED WHERE status = ?"
plan(WITH_INDEX, ("completed",))

for status in ["completed", "cancelled"]:
    n = conn.execute("SELECT COUNT(*) FROM orders WHERE status = ?", (status,)).fetchone()[0]
    t_idx = timed(WITH_INDEX, [(status,)] * 20)
    t_scan = timed(NO_INDEX, [(status,)] * 20)
    print(f"{status:<10} {n:>6,} rows   with index {t_idx:6.1f} ms   plain scan {t_scan:6.1f} ms")

Output (your timings will differ)

SEARCH orders USING INDEX idx_orders_status (status=?)
completed  18,762 rows   with index   19.8 ms   plain scan   15.4 ms
cancelled     397 rows   with index    1.1 ms   plain scan    9.4 ms

For the rare value, cancelled (397 rows), the index is a clear win. For completed (18,762 rows) it is no better than reading the table straight through, and often worse: the engine walks the index and then visits nearly every row of the table anyway, in a less convenient order. An index pays off when it lets the engine skip most of the table. This property is called selectivity.

4. A Small Table

employees has 55 rows and products 242. Each fits in a few pages of the file, and scanning a few pages is as fast as any index lookup. Do not index small lookup tables beyond their primary key.

An index on a column helps when......and does little or nothing when
The filter is =, IN, a range, or a prefix on the bare columnThe column is inside a function or arithmetic
The filter keeps a small share of the rowsMost rows match (low selectivity)
The column is a join key on the inner side of the loopThe table is small
The query sorts or groups by the indexed orderThe pattern starts with a wildcard
The index contains every column the query needs (covering)The filter is on a later column of a composite index only

📊 ANALYZE: Statistics for the Planner

So far the planner has been choosing with almost no knowledge of your data: it knows which indexes exist, not how many rows a table has or how many distinct values a column holds. ANALYZE measures those things and stores them in a table named sqlite_stat1, where the planner consults them.

Recall the "date only" query, which could not seek in an index that starts with store. Check its plan and timing, run ANALYZE, and check again.

DATE_SQL = "SELECT COUNT(*) FROM orders WHERE order_date = ?"
days = [("2025-07-04",)] * 200

plan(DATE_SQL, days[0])
t_before = timed(DATE_SQL, days)

conn.execute("ANALYZE")
conn.commit()

plan(DATE_SQL, days[0])
t_after = timed(DATE_SQL, days)
print(f"200 counts: {t_before:.1f} ms before ANALYZE, {t_after:.1f} ms after")

Output (your timings will differ)

SCAN orders USING COVERING INDEX idx_orders_store_date_total
SEARCH orders USING COVERING INDEX idx_orders_store_date_total (ANY(store) AND order_date=?)
200 counts: 83.9 ms before ANALYZE, 1.3 ms after

The plan changed from a SCAN to a SEARCH with ANY(store). The statistics told the planner that store has only five distinct values, so a new strategy became worthwhile: do five small searches, one per store, each jumping to the date. This is called a skip-scan, and SQLite only considers it once ANALYZE has shown that the leading column has few values. Same query, same indexes, better plan, because the planner now knows the shape of the data.

for table, index, stat in conn.execute("SELECT tbl, idx, stat FROM sqlite_stat1 WHERE tbl IN ('orders', 'order_items') ORDER BY tbl, idx"):
    print(f"{table:<12} {index:<30} {stat}")

Output

order_items  idx_order_items_order_id       45490 3
orders       idx_orders_customer_id         20302 6
orders       idx_orders_status              20302 6768
orders       idx_orders_store_date_total    20302 4061 7 1

Each stat starts with the number of rows, followed by the average number of rows that share a value of the first column, then of the first two columns, and so on. For the three-column index: 20,302 orders, about 4,061 per store, about 7 per store and date. For idx_orders_status: about 6,768 rows per status, which is an average. These basic statistics do not record that one status has 18,762 rows and another 397.

plan(WITH_INDEX, ("completed",))

conn.execute("DROP INDEX idx_orders_status")      # it did not earn its keep
conn.commit()

Output

SEARCH orders USING INDEX idx_orders_status (status=?)

So even after ANALYZE, the planner still picks the unhelpful status index for completed. Statistics improve the planner's choices; they do not make it all-knowing. You decided that index was not worth keeping by measuring, and dropping it is the fix.

💡 When to Run ANALYZE

After creating indexes, and again after the data changes a great deal. In SQLite it is manual (PRAGMA optimize, run before closing a connection, does it only when needed). PostgreSQL gathers richer statistics, including the most common values of each column, and refreshes them automatically in the background.

💸 What Indexes Cost

If indexes made everything faster, databases would index every column automatically. They do not, because an index is a second, sorted copy of part of the table, and it must be kept in order on every insert, update and delete.

Measure it. This function builds an empty copy of order_items with a chosen number of indexes, loads the same 45,490 rows into it, and reports the time and the growth of the database file.

rows = conn.execute("SELECT order_id, sku, quantity, unit_price FROM order_items").fetchall()
INDEX_COLUMNS = ["order_id", "sku", "unit_price", "quantity"]

def load_with_indexes(n_indexes):
    conn.execute("DROP TABLE IF EXISTS items_copy")
    conn.execute("VACUUM")                                   # give freed space back, for a fair size
    size_before = os.path.getsize("pinecrest_tuning.db")
    conn.execute("""CREATE TABLE items_copy (order_item_id INTEGER PRIMARY KEY, order_id INTEGER,
                                             sku TEXT, quantity INTEGER, unit_price REAL)""")
    for col in INDEX_COLUMNS[:n_indexes]:
        conn.execute(f"CREATE INDEX idx_copy_{col} ON items_copy ({col})")
    start = time.perf_counter()
    with conn:                                   # commits when the block ends (Lesson 5.1)
        conn.executemany("INSERT INTO items_copy (order_id, sku, quantity, unit_price) VALUES (?, ?, ?, ?)", rows)
    elapsed = (time.perf_counter() - start) * 1000
    added_kb = (os.path.getsize("pinecrest_tuning.db") - size_before) / 1024
    return elapsed, added_kb

for n in [0, 1, 2, 4]:
    ms, kb = load_with_indexes(n)
    print(f"{n} indexes: insert 45,490 rows in {ms:6.1f} ms, file grew by {kb:7,.0f} KB")

conn.execute("DROP TABLE items_copy")
conn.execute("VACUUM")

Output (your timings will differ)

0 indexes: insert 45,490 rows in   22.2 ms, file grew by   1,388 KB
1 indexes: insert 45,490 rows in   34.0 ms, file grew by   1,964 KB
2 indexes: insert 45,490 rows in   52.5 ms, file grew by   2,800 KB
4 indexes: insert 45,490 rows in   89.4 ms, file grew by   4,068 KB

Every index added made the same load slower and the file bigger. With four indexes, the insert takes several times as long as with none, and the indexes together take up more space than the table itself. (The column names in that f-string come from a fixed list in your own code, never from outside input.)

💡 The Trade

An index buys faster reads and pays with slower writes and more storage. For a table that is read constantly and changed rarely, as in most analysis and reporting, indexes are cheap. For a table receiving thousands of inserts a second, each one is a real expense. Bulk loading follows from this: when loading millions of rows into a new table, load first and create the indexes afterward.

🎯 Ask for Less: SQL or pandas?

The cheapest row is the one you never fetch. Indexes help the engine find rows faster, but a great deal of slowness in analysis code has nothing to do with indexes. It comes from moving more data than the question needs out of the database and into Python.

Aggregate Where the Data Lives

Item revenue by store, two ways: pull every joined row into pandas and group there, or ask the database for five rows.

def pandas_way():
    df = pd.read_sql("SELECT * FROM order_items AS i JOIN orders AS o ON o.order_id = i.order_id", conn)
    df = df[df["status"] == "completed"]
    return (df["quantity"] * df["unit_price"]).groupby(df["store"]).sum().round(2)

def sql_way():
    return pd.read_sql("""
        SELECT o.store, ROUND(SUM(i.quantity * i.unit_price), 2) AS revenue
        FROM order_items AS i
        JOIN orders AS o ON o.order_id = i.order_id
        WHERE o.status = 'completed'
        GROUP BY o.store
    """, conn).set_index("store")["revenue"]

def best_of(func, repeat=3):
    best = float("inf")
    for _ in range(repeat):
        start = time.perf_counter()
        result = func()
        best = min(best, time.perf_counter() - start)
    return best * 1000, result

t_pandas, r_pandas = best_of(pandas_way)
t_sql, r_sql = best_of(sql_way)
print(f"SELECT * then pandas: {t_pandas:6.1f} ms")
print(f"GROUP BY in SQL     : {t_sql:6.1f} ms")
print("same numbers:", (r_pandas - r_sql).abs().max() < 0.01)

Output (your timings will differ)

SELECT * then pandas:  147.0 ms
GROUP BY in SQL     :   13.8 ms
same numbers: True

Same answer, many times faster, because 45,490 rows of 16 columns never had to be turned into Python objects and a DataFrame. On a server database the gap is wider still, since those rows would also cross a network.

Do it in SQLDo it in pandas
Filtering rows and choosing columnsStatistics, tests and models (Module 4)
Joining tables that live in the databaseReshaping: pivot, melt, resample
Aggregating large tables down to a summaryCharts
Top N, deduplication, ranking on big dataMessy text cleanup and date parsing
Anything that reduces millions of rows to thousandsExploration, once the data fits comfortably in memory

Three More Habits

  • Name your columns. SELECT * fetches every column, defeats covering indexes, and breaks your code when someone adds a column. Ask for the ones you use.
  • Use LIMIT while exploring. SELECT ... LIMIT 20 shows you the shape of a result without waiting for all of it.
  • One query, not a loop of queries. Fetching a list of ids and then running one query per id in a Python for loop is known as the "N+1 problem". On a server database each round trip costs network time, and a join or an IN (...) does the same work in one trip.

💡 Where PostgreSQL Differs

The ideas carry over unchanged: scans, index searches, composite and covering indexes, selectivity, statistics. The commands differ. PostgreSQL uses EXPLAIN for the plan and EXPLAIN ANALYZE to run the query and report actual times and row counts per step. Its plans name more strategies (Seq Scan, Index Scan, Index Only Scan, Hash Join, Merge Join) where SQLite has nested loops only. Statistics are kept up to date automatically. Those statements are from PostgreSQL's documentation; nothing in this lesson was run on PostgreSQL.

⚠️ Common Mistakes

1. Creating an Index That Already Exists

conn.execute("CREATE INDEX idx_order_items_order_id ON order_items (order_id)")

Error

OperationalError: index idx_order_items_order_id already exists

What it means: you ran the cell twice, which everyone does. Fix: CREATE INDEX IF NOT EXISTS ... makes the statement safe to rerun. The names differ but the trap is the same in reverse: two indexes with different names on the same column are both maintained and only one is ever used. List what exists before adding more.

2. Assuming the Index Is Used

Creating an index proves nothing. The planner may ignore it because of a function on the column, a type or collation mismatch, or because it judged a scan to be cheaper. Fix: after creating an index, rerun EXPLAIN QUERY PLAN on the query it was meant for and read the line. You are looking for the index's name.

3. Trusting One Timing

single_runs = []
for _ in range(5):
    start = time.perf_counter()
    conn.execute("SELECT store, COUNT(*) FROM orders GROUP BY store").fetchall()
    single_runs.append((time.perf_counter() - start) * 1000)
print("five runs of the same query, in ms:", [round(t, 2) for t in single_runs])

Output (your timings will differ)

five runs of the same query, in ms: [0.63, 0.49, 0.49, 0.49, 0.5]

What it shows: identical runs do not take identical time. The first is often the slowest, because later runs find the data already in memory (the operating system and SQLite both cache pages). A single "before" and a single "after" can show an improvement that is only the cache warming up. Fix: repeat, take the best or the median, and compare like with like, as timed() does. Trust the plan first and the stopwatch second.

4. Indexing Every Column "to Be Safe"

You measured the result above: slower writes, a larger file, and more choices for the planner to get wrong. Fix: start from the queries that are actually slow and actually matter, index for those, and drop indexes that no important query uses.

5. Optimizing Before Measuring

Most queries in an analysis are fast enough as first written. Fix: write the clear version, notice which one makes you wait, look at its plan, and tune that. Clever SQL written to save two milliseconds costs the next reader, usually you, far more than it saves.

🛠️ Step 2: Measure the baseline and keep the answers (10 min)

One function measures the whole workload: plan, best-of-three time, and the actual results, which you will need later to prove nothing changed.

def measure(db):
    report = {}
    for name, (sql, param_list) in WORKLOAD.items():
        steps = [row[3] for row in db.execute("EXPLAIN QUERY PLAN " + sql, param_list[0])]
        best = float("inf")
        for _ in range(3):
            start = time.perf_counter()
            results = [db.execute(sql, p).fetchall() for p in param_list]
            best = min(best, time.perf_counter() - start)
        report[name] = {"plan": steps, "ms": best * 1000, "results": results}
    return report

baseline = measure(db)
size_before = os.path.getsize("tuning_project.db")

for name, r in baseline.items():
    print(f"{name}: {r['ms']:.0f} ms")
    for step in r["plan"]:
        print("    " + step)

🛠️ Step 3: Choose and create the indexes (10 min)

Reason from the WHERE and ON clauses. Customer history filters orders by customer_id and joins the lines by order_id. Product sales filters the lines by sku (and then joins to orders by its primary key, which is already fast). 🏋️ Exercise 4: Is a Covering Index Worth It? (Stretch)

The merchandising team often asks for units and revenue of one product: SELECT SUM(quantity), SUM(quantity * unit_price) FROM order_items WHERE sku = ?. Compare three situations for 50 SKUs: no index on sku, a plain index on (sku), and a covering index on (sku, quantity, unit_price). Report the time for each and how much each index adds to the file. Which would you keep?

💡 Hint

Measure the file with os.path.getsize after a commit, before and after each CREATE INDEX. Drop the plain index before creating the covering one so that the planner's choice is clear.

✅ Solution 
SKU_SQL = "SELECT SUM(quantity), SUM(quantity * unit_price) FROM order_items WHERE sku = ?"
skus = conn.execute("SELECT sku FROM products ORDER BY sku LIMIT 50").fetchall()

def file_kb():
    conn.commit()
    return os.path.getsize("pinecrest_tuning.db") / 1024

results = []
size0 = file_kb()
plan(SKU_SQL, skus[0])
results.append(("no index", timed(SKU_SQL, skus), 0.0))

conn.execute("CREATE INDEX idx_items_sku ON order_items (sku)")
plan(SKU_SQL, skus[0])
results.append(("index on (sku)", timed(SKU_SQL, skus), file_kb() - size0))

conn.execute("DROP INDEX idx_items_sku")
conn.execute("VACUUM")
size0 = file_kb()
conn.execute("CREATE INDEX idx_items_sku_cover ON order_items (sku, quantity, unit_price)")
plan(SKU_SQL, skus[0])
results.append(("covering index", timed(SKU_SQL, skus), file_kb() - size0))

for label, ms, kb in results:
    print(f"{label:<16} {ms:7.1f} ms   +{kb:,.0f} KB")

Output (your timings will differ)

SCAN order_items
SEARCH order_items USING INDEX idx_items_sku (sku=?)
SEARCH order_items USING COVERING INDEX idx_items_sku_cover (sku=?)
no index            54.7 ms   +0 KB
index on (sku)       2.9 ms   +728 KB
covering index       0.9 ms   +1,196 KB

Both indexes turn the scan into a search and give most of the gain. The covering index is faster again, because the three sums are computed from the index without visiting the table, and it costs more space. There is no universal answer. If this query runs thousands of times a day, the covering index earns its space; if it runs once a week, the plain one (or none) is the sensible choice. What matters is that you can now put numbers on both sides of the decision.

❓ Common Questions at This Stage

As an analyst, will I be allowed to create indexes at work?

Often not on production databases, and that is reasonable: indexes affect everyone's writes. What you can always do is read the plan, write filters that can use the indexes that exist, fetch less, and bring a specific, measured request to whoever administers the database: "this query scans the orders table; an index on (store, order_date) takes it from 110 ms to 2 ms". That request gets approved far more often than "the database is slow".

Does the order of conditions in my WHERE clause matter?

No. WHERE a = 1 AND b = 2 and WHERE b = 2 AND a = 1 get the same plan; the planner rearranges them. What matters is the order of columns in the index.

I dropped an index and the plan still mentions it. What happened?

Python's sqlite3 module keeps recently used statements prepared, and an EXPLAIN QUERY PLAN statement taken from that cache can report the plan from before the drop. The real query is not affected. Connecting with cached_statements=0, as this lesson does, avoids it; so does opening a new connection.

My numbers show a smaller speedup than the lesson's. Is something wrong?

Probably not. Timings depend on your disk, your processor and what else is running, and this database is small enough that everything fits in memory. Compare the plans: if yours say SEARCH ... USING INDEX where the lesson's do, you have the same improvement. The gap between a scan and a search grows with the size of the table, so on real data it would be far larger than anything you can measure here.

What about the window-function and CTE queries from the last two lessons?

Run plan() on them: it works on any SELECT. You will see extra lines such as CO-ROUTINE or MATERIALIZE for CTEs and subqueries, and USE TEMP B-TREE for the sorting that windows need. The same reading applies: find the SCAN lines and ask whether each one needed the whole table.

📝 Lesson Summary

🎓 Key Takeaways

  • The planner chooses how to run your query; EXPLAIN QUERY PLAN shows the choice without running anything
  • SCAN reads the whole table; SEARCH jumps to the rows it needs through a primary key or an index
  • Index the columns you filter, join and sort by, starting with foreign keys; primary keys are indexed already
  • In a composite index, column order matters: equality columns first, the range or sort column last (the leftmost-prefix rule)
  • A covering index contains every column a query needs, so the table is never opened
  • An index does not help when the column is wrapped in a function, the pattern starts with a wildcard, most rows match, or the table is small
  • Indexes cost storage and slow down every write; keep the ones that earn their place and drop the rest
  • ANALYZE gives the planner statistics, which can change its plans
  • Filter, join and aggregate in SQL; bring a small result to pandas; measure more than once
